# Lessons - onboarding

## 0.2.0 - 2026-08-25 - kp
- Promoted from kp's project-local skill (v0.2.0) to the registry lane as generic v0.3.0. The engine that survived unchanged: the mode question (developer laptop / team self-host / just evaluating), the probe-and-report-as-a-table discipline (including the Claude CLI presence + logged-in smoke `claude -p "say ok"`), the env-file hard rules (merged never overwritten, secrets written but never echoed, "not configured" is a real outcome, any group answerable "later"), boot-verify with read-the-real-port discipline, and the closing capability matrix that must never out-promise the app's own UI.
- Everything project-specific moved to a per-repo overlay at `.claude/onboarding/config.md`: kp's python/jobfit probe and `schemas:gen` toolchain proof, the Gemini/CV-extraction group, both voice planes (ElevenLabs conversation provider + the TTS engines with their language limits), the `setup-eleven-agent.mjs` helper, comms/calendar/observability/security/billing groups, KP_* variable names, the team-mode absolute-DB-path rule, verify URLs, and the matrix row list. The overlay contract distilled kp's group table into typed fields: unlocks / keys / options / verify / without / helper.
- The three-state honesty vocabulary was made explicit in the contract: each group's `without` field must declare exactly one of `fallback:` (degraded, still runs), `hidden:` (removes itself by design), or `hard-required:` (fails loudly naming the variable). In kp v0.2.0 this was implicit per group (comms degraded, voice hid, CV analysis hard-failed) and easy to get wrong when adapting.
- kp's own "Portability note" had proposed a JSON manifest (`onboarding.capabilities.json`); the lane's existing overlay convention (markdown `config.md` with YAML scalars + `##` sections, as `perfect` and `ship-loop` use) won instead, so overlay authors write one format across skills.
- Added a rule kp never needed but the lane demands: no machine-absolute paths in anything the skill writes; overlay-declared absolute-path variables are derived from the repo's location at run time, with the reason stated.
