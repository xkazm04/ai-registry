# Design report craft - what the owner keeps

A **design contest** (a backend or architecture brief whose variants are reports that open in a
browser, not UI prototypes) is judged on the argument and on how the report carries it. This file
is the owner's reading of which reports carried it best, taken from the first four design contests
(2026-09-22: self-repairing extraction, judge-generation equating). The host appends the
**Bar for the report itself** section below to every design-contest brief, after the brief's own
Taste, so each seat starts from what the owner already praised - as a floor, not a template.

## The bar for the report itself

*(Host's reading of the notes above, phrased so it transfers to any design brief.)*

1. **Lead with the positive impact.** The first screen says what the owner gains if this design
   ships - a statement, three bullet points, or two or three numbers - before it explains the
   mechanism. Every report in the first contests explained the problem well and the pay-off
   poorly; the one that put a clear claim "right into the reader's face" was the one praised.
2. **A commented diagram per part of the solution, not a paragraph.** Each mechanism gets its own
   clean diagram (a loop, a state machine, a timeline) with short annotations on the figure. Prose
   explains what the diagram cannot. A section that is three paragraphs of text where a figure
   would do has failed the owner's first rule.
3. **Theme serves the content.** A strong visual identity is welcome only while it keeps text,
   diagrams and highlights legible. A theme that crowds the page, shrinks type or competes with
   the figures degrades good ideas - two praised reports were marked down for exactly this.
4. **A reading system.** A left navigation grouped by topic (position / machine / argument), a
   palette in which body text, diagrams and highlighted components each read clearly, fonts and
   sizes chosen for an hour of reading, inline code used where it clarifies and no more.
5. **Data models as code.** Tables, columns and states shown as formatted code snippets, not as
   prose or bullet lists.
6. **Designed comparison tables.** Space-efficient tables for alternatives, statistics and
   measurements; a pros / cons / risks table laid out so each row is readable at a glance.
7. **Designed claims.** A key claim or quotation gets its own visual treatment, so the argument's
   load-bearing sentences can be found by scanning.
