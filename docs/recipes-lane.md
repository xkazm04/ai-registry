# The `recipes/` lane

Craftsman knowledge: one kind of work done well, written down so any agent can hold it,
run it, and improve it. One directory per recipe, the machine-readable object in
`recipe.json`, the human view rendered beside it in `RECIPE.md`, the reflection in
`LESSONS.md`, and the connector-specific knowledge in `examples/`.

A recipe is not a process definition and it is not configuration. It is **mastery**: the
best current knowledge of how one kind of work is done well. Everything that binds it to
one installation - which connector, which trigger, which credentials, which persona -
happens at adoption and lives on the adopted charter in the consuming application, never
here.

The contract this lane implements is Recipe v3. The authoritative field list is copied
verbatim below; the design rationale lives with the consumer that wrote it
(`scripts/templates/_RECIPE_V3_SPEC.md` in the Personas repository).

## Two layers, and the line between them is the whole design

| | Recipe (this lane) | Charter (adopted instance, in the consuming app) |
| --- | --- | --- |
| owns | need, input, core action, output, activity sequence, outcomes, guidance, connector TYPES, recommended trigger, personalization needs, dependencies, examples | bound connectors, assigned trigger and cadence, credentials, budget, scope, approval gates, persona-specific memory |
| author | the craft (any agent, via versioned proposals) | the operator and the persona that holds it |
| changes by | version bump plus a `LESSONS.md` entry, here | edits in the app; lessons in the charter's memory |
| never carries | a connector id, a cron, a persona | a general lesson somebody else would want |

## The shape

```
recipes/<domain>/<topic>/<slug>/recipe.json    # required - the v3 object
recipes/<domain>/<topic>/<slug>/RECIPE.md      # required - the rendered human view
recipes/<domain>/<topic>/<slug>/LESSONS.md     # required - append-only, one block per run
recipes/<domain>/<topic>/<slug>/examples/      # optional - one file per concrete connector
recipes/index.json                             # GENERATED by scripts/build-recipes-index.mjs
```

`<slug>` is kebab-case and **is** the recipe's identity: the directory name, the
`slug` field and the `RECIPE.md` frontmatter `name` must all agree. A consumer copies
or migrates the directory; an index reads the field. When they disagree, a copy and an
index disagree about what was adopted.

**Depth is nested, and it is exactly three levels.** `recipes/<domain>/<topic>/<slug>/`
is four path segments, and no level holds more than **ten** child directories - the same
browsing cap `knowledge/` runs on, and the same reason: ten is roughly what a reader
takes in at once. Consumers read the generated `recipes/index.json` rather than walking
the tree, which is what makes a nested depth safe here where it would be fatal in
`skills/`. Identity is the bare slug at any depth; location is `<domain>/<topic>` and is
carried in the object's own `path` field so the two can be compared.

## `recipe.json` - the v3 object

Copied from the contract. Every field below is checked by the gate; a field the gate
does not name is allowed and ignored, because this registry guarantees
`compatibility: additive`.

```jsonc
{
  "id": "<stable uuid, unchanged from v2>",
  "slug": "web-analytics-performance-review",      // kebab; registry folder name
  "title": "Web analytics performance review",     // AREA + ACTIVITY, unambiguous on its own
  "version": "0.1.0",                              // semver; 0.x = seed knowledge, matures with use
  "status": "seed",                                // seed | maturing | proven
  "path": "sales_marketing/web-analytics",         // <domain>/<topic> in this lane (<=10 dirs per level)
  "domain": "sales_marketing",                     // the closed 16-family vocabulary (unchanged)

  "description": {
    "need":        "why this work exists, as a claim about what goes wrong without it",
    "input":       "what the work starts from (data, artifacts, signals)",
    "core_action": "the judgment at the center, one or two sentences",
    "output":      "what exists in the world when it is done well"
  },

  "activities": [                                  // COARSE sequence for a high-level diagram. 3..8 items.
    { "id": "collect",  "label": "Pull engagement for posts past the review window", "kind": "observe" },
    { "id": "compare",  "label": "Compare against rolling baselines and platform weights", "kind": "decide" },
    { "id": "flag",     "label": "Flag viral spikes and underperformers", "kind": "act" },
    { "id": "update",   "label": "Update baselines so next review learns from this one", "kind": "deliver" }
  ],

  "outcomes": [ { "id": "...", "statement": "...", "success_criteria": ["..."] } ],
  "guidance": "40-90 words of judgment, never numbered steps, never a tool order.",

  "use_cases": [                                 // 3..6 situations where adopting this pays. The selection signal.
    "A team publishing several times a week across more than one platform, where ...",
    "A founder running content alone, who cannot tell a format that is working from ..."
  ],

  "connector_types": ["analytics", "social"],      // connector CATEGORIES, NEVER a connector id
  "recommended_trigger": { "kind": "self_paced", "rationale": "..." },   // event | time | self_paced
  "personalization_needs": ["what adoption must learn from the adopter, and why"],
  "dependencies": ["ffmpeg"],                      // things adoption must install or verify first
  "input_schema": [ ],                             // the knobs, unchanged from v2

  "examples": [                                    // concrete-solution knowledge lives HERE and only here
    { "title": "Deepgram as the transcription connector",
      "connector": "deepgram", "connector_type": "transcription",
      "notes": "what was learned mapping this recipe onto that specific connector" }
  ],

  "lessons": [],                                   // append-only; promoted from charter memory by proposal
  "provenance": { "from_recipes": [], "from_templates": [], "source_template_id": "" }
}
```

### `activities` is a shape, not a runbook

Three to eight items, linear, branch-free. No decision nodes, no edges, no conditions.
Each `kind` is one of `observe`, `decide`, `act`, `deliver`, and a label is a phrase
rather than an instruction. If it needs a branch it is a runbook and it does not belong
in a recipe. The predecessor field this replaced (`useCaseFlow`) was a node and edge
graph, which is a script for a machine; this is a shape a reader and a diagram can take
in at a glance.

### `use_cases` is the selection signal

Three to six, required. `need` and `core_action` describe **the craft**; `use_cases`
describe **the situations that should reach for it**, and they are not the same sentence.
A corpus of two hundred recipes is selected FROM, by an operator scanning for what fits
their week and by an agent proposing an adoption, and neither can tell from a well-written
`need` whether this recipe is for them.

Each entry names a **situation and why the work pays there**: who is in it, what is going
wrong or about to, and what this recipe changes about that. An audience is not a use case:
"marketing teams" names a group, and every recipe in the domain would claim it. The gate
requires three to six entries and notes anything under six words, which is the length at
which a bare noun phrase stops being possible.

Write them last, after the four description fields and the guidance, so they describe the
recipe that exists rather than the one that was planned. `RECIPE.md` renders them under
`## Where this is worth adopting`.

They are deliberately **not** in `recipes/index.json`. The index is loaded whole to pick a
recipe by shape (domain, topic, connector types, trigger); use cases are prose, four of
them per recipe would multiply the index by an order of magnitude, and the index already
tells a reader where to open the recipe.

### `description` is four fields, always

`need`, `input`, `core_action`, `output`, in that order, every time. `guidance` carries
the judgment prose and nothing else.

### Connector types, not connectors

`connector_types` holds the consuming catalog's plural `categories` vocabulary -
`transcription`, `analytics`, `social`, `email`, `messaging`, `database`, `storage`,
`knowledge_base`, `monitoring`, `source_control`, `ci_cd`, `calendar`, `finance`,
`research`, `devops`, `productivity`, `marketing`, `notifications`, `cloud`, `ai`,
`voice_generation` and the rest. Adoption resolves a type to any connector whose
`categories` include it.

The vocabulary is **not closed by this gate**, deliberately: it lives in the consuming
application's connector catalog, this registry cannot see that catalog, and a hard list
copied here would go stale the first time a connector is added there. The gate checks
the shape and reports a value outside the set it last recorded as a note. One value is a
hard failure: **`desktop` is not a connector and never appears** - every agent has
desktop access, so a `desktop` connector type is a binding to nothing.

Where the source said `deepgram`, a v3 recipe says `transcription` and keeps Deepgram as
an entry in `examples`. Where the source already said `analytics`, it stays.

### Triggers are recommended, never bound

`recommended_trigger.kind` is one of `event`, `time`, `self_paced`, with a `rationale`.
No cron, no interval, no event name reaches a recipe. The adopter assigns the real
trigger at adoption or later, defaulting to the recommendation. A title that encodes a
cadence ("48-hour ...") has lost the recommendation into the name and should not.

### Titles name AREA plus ACTIVITY

"Performance review" is ambiguous. "Web analytics performance review" is not. A title
must read unambiguously in a list of two hundred recipes drawn from every domain.

## `RECIPE.md` - the rendered human view

A recipe's machine object is JSON, and JSON is not a document. `RECIPE.md` is the same
recipe as prose so a person browsing the lane in a text editor or on a git host reads a
document rather than a payload. It is a **rendered view**: when it disagrees with
`recipe.json`, `recipe.json` is right and the view is stale.

```markdown
---
name: web-analytics-performance-review
version: 0.1.0
status: seed
domain: sales_marketing
path: sales_marketing/web-analytics
---

# Web analytics performance review

**Need.** ...
**Input.** ...
**Core action.** ...
**Output.** ...

## Activities

1. Pull engagement for posts past the review window *(observe)*
...

## Outcomes
## Guidance
## Where this is worth adopting
## Connector types
## Recommended trigger
```

The five frontmatter keys are required and each must equal its `recipe.json` twin - the
gate compares them, because a rendered surface with no coupling to its input is a
document that silently stops being true. Frontmatter is ASCII, for the same reason it is
in `skills/`: every consumer parses it with a small hand-rolled parser.

## `LESSONS.md`

Required, and in the `skills/` lane's format exactly, so one reader serves both:

```markdown
## <version used> - <YYYY-MM-DD> - <project>
- What the run taught, in bullets.
```

The version slot records the version the run **used**, not the bump it argues for, so a
future reader can tell which method produced the lesson. Append-only is a property of
history rather than of a file, so it is enforced by review.

Appending to `LESSONS.md` does **not** require a version bump. A lesson records a run
against a version; it is not a change to the method. Every other file in the directory
is the method.

## `examples/`

One markdown file per concrete connector, named for it: `examples/deepgram.md`,
`examples/plausible.md`. This is where concrete-solution knowledge lives and the only
place it may. The `examples` array in `recipe.json` is the index of them; a
`recipe.json` example naming a connector with no file beside it is reported as a note.

## Versioning

Semver, `MAJOR.MINOR.PATCH`. `0.x` is seed knowledge that has not yet earned a claim to
being right; it matures with use. Bump minor or major when the craft changes, patch when
it does not.

`version_reports_staleness: true`, exactly as in `skills/`: a higher version here does
**not** displace any adopted charter. Merging a pull request in this repository must
never change what an already-adopted persona does, remotely and with nobody present. A
version across sources reports staleness; a human resolves it.

`node scripts/check-recipes.mjs --since <ref>` enforces the two rules that make the
comparison mean anything:

- **Content changed, version did not.** Fail. An unchanged version tells every consumer
  it is in sync while it holds different knowledge. A non-behavioural fix takes a patch
  bump and the level is free.
- **Version went backwards.** Fail. A consumer already at the higher version resolves as
  ahead of the registry and never syncs again.

## Dual improvement

A recipe improves from two directions and they must not be confused:

- **Charter memory** keeps the lessons specific to one adoption - this operator's
  spreadsheet layout, this account's rate limit, this team's approval step. Nobody else
  wants them and they stay in the consuming app.
- **A lesson that generalizes** is promoted **by proposal** into the recipe: a version
  bump plus a `LESSONS.md` entry, arriving as a pull request. Propose only, human
  adopted, the same governance as every other write lane in this repository.

The test for which one a lesson is: would an agent in a different organization, holding
this recipe against a different connector, be better off knowing it. If yes it is a
registry lesson. If it names a credential, an account, a file path or a person, it is
charter memory.

## The gate

`node scripts/check-recipes.mjs`. Structural, zero dependencies, and it asserts its own
measurement functions against a hand-counted fixture before it reports anything.

What it checks:

- every `recipe.json` parses, and carries the required fields;
- the closed vocabularies: `status` (`seed`, `maturing`, `proven`), `activities[].kind`
  (`observe`, `decide`, `act`, `deliver`), `recommended_trigger.kind` (`event`, `time`,
  `self_paced`);
- three to eight activities, with unique kebab-case ids;
- three to six `use_cases`, each a non-empty string (a short one is reported as a note,
  because an audience where a situation belongs is the failure this field exists to stop);
- `slug` matches its folder, `domain` matches its top folder, `path` matches
  `<domain>/<topic>`;
- `RECIPE.md` exists, opens with frontmatter, and its `name`, `version`, `status`,
  `domain` and `path` equal `recipe.json`'s;
- `LESSONS.md` exists and every heading parses in the lane format;
- no `desktop` in `connector_types`;
- no em dash or en dash in any string anywhere in the object;
- folder depth is exactly `recipes/<domain>/<topic>/<slug>/`, and no level holds more
  than ten child directories;
- with `--since <ref>`, the two version-discipline rules above.

What it deliberately does not check: whether the craft is any good (that is the
CODEOWNERS review, and it is the point of `write_path: pull-request`), whether a lesson
was actually appended after a change (append-only is a property of history), and whether
a `connector_type` exists in the consuming catalog (this registry cannot see it).

## The index

`recipes/index.json`, generated by `scripts/build-recipes-index.mjs`, verified with
`--check`. It is what makes the lane usable without opening every directory: slug to
path, version, status, domain, topic, connector types and the recommended trigger kind.
A consumer selecting a recipe reads this; a human reads the markdown.

`scripts/build-index.mjs` was not extended to cover this lane. It is not a generic
nested-lane indexer - it is the knowledge bundle's indexer, and every line of it is
about a bundle: it loads `taxonomy.json` through `scripts/lib/taxonomy.mjs`, walks
`techniques/` and `applications/`, resolves `_laws.md` anchors into law statements, and
emits `use_when` coverage. None of those exist in a recipe. Sharing the file would mean
one script with two disjoint bodies behind a lane flag, which is two scripts wearing one
name.

## Status: declared ahead of its corpus

This lane was declared on 2026-09-06 with its spec, its gate, its index builder and one
worked example, and nothing else. The corpus of recipes migrates from the consuming
application only after the operator has reviewed and approved it. A lane with a gate and
a single real item is a lane that can be validated; a lane declared with nothing in it is
a promise, and the gate would have had nothing to check.
