# Run 2026-08-22-4 - the harvest wave

One repository, every context, into an existing bundle. Ten read-only scouts over
56 contexts and 1,029 files, then twenty subject-workers: fourteen new subjects and
six extensions. `software-engineering` went 128 -> 142 subjects, 779 -> 876
techniques, 317 -> 351 applications, `use_when` 876/876, gate green.

This is the first run of a third lane. `domain-knowledge-forge` founds a bundle from
a repository's ceiling; `deepen` raises one subject above any repository; the
external-reconcile pilot [[2026-08-22-1]] tests a standing subject against a
world-class tree. A harvest is none of those: it reads one ordinary, competent
repository end to end and asks what it knows that the bundle does not. The contract
it needed did not exist, so it was written first: [`docs/harvest-brief.md`](../../docs/harvest-brief.md),
the per-wave contract for JOINING a bundle rather than founding one.

## What the shape of the wave taught

**Four territories independently proposed extending the same subject - twice.** Four
of ten scouts proposed adding to `motion`; four proposed adding to `client-state`.
Neither pair could see the other. Had those eight dispatches gone out as proposed,
eight workers would have raced one golden path each and the wave would have lost two
subjects to merge conflicts. Dedup by SUBJECT FOLDER before dispatch is not an
optimisation in a harvest, it is the thing that makes one possible - and it is
director work by construction, because only the director reads every scout.

**The same merge showed up in content, not just in scheduling.** Four scouts each
found one face of a single subject - a marketing demo simulating agent behaviour, an
operator dashboard falling back to fixtures, an API client with three interchangeable
data planes, and a nav badge that must not count fabricated incidents for a real
tenant. Carved by MECHANISM versus HONESTY, the honesty half became `demo-data-plane`
and the mechanism half was banked. The worker was asked for a verdict on that carve
as a tiebreaker and confirmed it independently.

**Nine golden paths ran 230-291 lines against a brief that says 120-220**, and one
ran 346. The corpus they joined sits at 188-275. The overage is consistent enough to
be the brief's number rather than the workers' discipline; the sample read at review
was dense throughout. Worth restating the figure from the corpus rather than from
memory next time.

## Instrument, before anything was ranked

`check-bundles`, `build-index`, `build-catalog`, then the scan - and a figure
confirmed against a real file, per the standard.

The catalog gate fired: index and catalog disagreed, 779 techniques against 781.
**It was not registry drift.** Another session was writing into the same checkout in
real time; the extra files were its uncommitted work. Confirmed by file mtimes three
minutes apart, and by a clean, self-consistent baseline in a fresh worktree from the
same HEAD. A gap reported without checking whose files they were would have sent a
repair pass at a corpus that was already correct.

That discovery also cost something and it is worth writing down: this session's first
act had been `git checkout -b` in the shared checkout, which moved the other session's
HEAD onto a branch it had never asked for. Restored, and the wave moved to a worktree
under `.claude/worktrees/`. **In a repository where more than one agent session may be
working, the worktree is the first step, not the fallback.**

## The instrument repair

The `neverSwept` clause reads `last_swept` from a subject note. Subject notes are
written with `last_touched`. Nothing has ever written `last_swept` into one, so the
clause scored every subject in the corpus and could never stop - 3 points times 142
subjects, 426 of a 584-point total, dominating the ranking it existed to inform.

It surfaced because twenty fresh subject notes moved the count by exactly zero.

Fixed to accept either spelling. Never-swept 142 -> 121, attention 584 -> 521, and
`retry-backoff` - swept by the pilot two days ago and carrying a note since -
registered for the first time. Same family as the `use_when` counter that reported
0/267 over a corpus at 267/267: **a reader asking for a shape no writer emits answers
plausibly, and nothing in the number says it is wrong.**

## What the wave measured about itself

- Version witness 0/317 -> 36/351. That line had been zero since the bundle existed.
- Single-stack subjects 67 -> 79. **The wave increased the bundle's largest debt.**
  Two were retired (`motion`, `hitl-approval`); fourteen new subjects arrived with one
  stack each, because a subject reconciled against one tree has one stack. This is the
  arithmetic of extraction and it should be stated plainly rather than netted away: a
  harvest grows the transplant debt it cannot itself pay.
- Purity beyond the denylist floor: 1,020 upper-layer files scanned for product,
  vendor, model, browser and platform-API names the gate does not list. Zero hits.
- The `software` purity profile was extended with the web-application names this
  harvest put in leaking range. Every one of them already appears legitimately in
  applications, where the denylist has never applied.

## A worker corrected the director

Six dispatches carried `verified_against: node@20`, justified by a `@types/node`
pin in the source manifest. One worker refused the instruction, checked the tree, and
wrote `node@22` - the only runtime witness anywhere is the CI workflow; there is no
`engines` field and no version file. It was right. Five sibling applications were
corrected afterwards, along with one that had repeated the bad reasoning in prose.

The trap is reusable and worth naming: **a types-package version looks exactly like a
runtime pin in a manifest, sorts next to the real dependencies, and here was off by
two majors.** `verified_against` is the only field that makes a runtime bump
computable, so a wrong major is worse than an absent one - it asserts an observation
nobody made.

The general rule was then broadcast to the rest of the wave: when a dispatch states a
fact about the tree and the tree disagrees, the tree wins and the worker says so.

## Laws: ten proposed, none minted

Every worker proposed at least one. Three cited sightings in subjects outside their
own - `guard-failure-is-not-consent` (a control that cannot complete denies rather
than forwards), `the safe default is the failure you can see`, and
`tolerance-ratchets-down`. A fourth, `a liveness claim derives from last arrival, not
from last successful open`, has four sightings including one in an existing subject.

None was added. The bar is cross-domain recurrence and every sighting was inside this
one domain. All ten are recorded in their subject notes with their evidence and their
return conditions, which is the whole point of writing them down: a law proposed by
ten independent workers in one afternoon is either a real anchor or a shared blind
spot, and one wave cannot tell which.

Also declined: widening `count-carries-predicate` from counts to claims. Well
evidenced - this wave produced its own illustration, two workers measuring the same
corpus and reporting 100% and 91.4%, both correct, differing only by denominator. But
the anchor's name would then be narrower than its scope, and it is cited by 282
files. That rename is its own change with its own review.

## Declines, and one that was a correction

`agent-memory` was dispatched for extension on the strength of the previous domain
note, which listed it as owing an application. The scan showed it already carried two
stacks and stood at nine techniques - the house ceiling. Dropped, re-banked as a NEW
subject candidate, and the slot went to `hitl-approval`, which the scan confirmed was
genuinely single-stack. **The note is a record of a moment; the scan is the
instrument.** The same stale note had also been the source of a claim, made mid-run,
that `docs-sync` had never been reconciled against real code. It carried two
applications.

`machine-enforced-house-rules` was declined for concurrency alone: another session
held `quality-gates` in the main checkout for the duration.

## Banked

Twenty-eight candidates were harvested and not built, each with a return condition,
recorded in the subject notes and the wave ledger. The strongest are
`scripted-scene-choreography` (banked on a worker's explicit verdict, with its seam
against `motion`'s two new techniques to check first), `client-error-surfaces` and
`review-sla-escalation`-style extensions that would retire rust-only debt, and
`memory-curation-surface` as a new subject rather than an extension.

Two territories reported honestly thin: the social-metadata surface (its generators
carry no transferable rule) and the shared UI primitives (components, not a
vocabulary). Both are recorded as dry rather than padded into candidates.

## For the next harvest

1. Worktree first, before the first git command, in any shared checkout.
2. Dedup scout candidates by subject folder before dispatch; expect the same subject
   to be proposed by three or four unrelated territories.
3. Check the target subject's technique count and stack list from the SCAN before
   promising an extension - not from the domain note.
4. Tell every worker that the source repo's context map may be stale and that
   re-opening each cited line is a separate step from drafting. It paid: workers
   reported roughly a fifth of anchors off by one to three lines, several files that
   no longer exist, and two anchors whose stated rationale was inverted relative to
   the code's actual effect.
5. State the golden-path length from the corpus, not from the founding brief.

## Merged, and what the merge changed about these numbers

This wave branched from the commit before two other lanes ran, and merged after them.
Every figure above is a record of what the HARVEST did against the tree it started from -
128 -> 142 subjects, 779 -> 876 techniques - and none of them describes the merged bundle,
which stands at 143 / 890 / 357 because an external-reconcile wave [[2026-08-22-2]] and a
research pass [[2026-08-22-3]] landed in between. The domain note carries the merged
shape; this note carries the run's.

Three things the merge itself taught, all of them about concurrency rather than content:

- **Two lanes numbered a run the same day and collided twice.** This run was written as
  `-2`, renumbered to `-3` when the reconcile wave's `-2` appeared on main, and renumbered
  again to `-4` when the research lane's `-3` did. A run id derived from a date and a
  counter is not safe to mint from a branch that has not fetched.
- **Two lanes extended the same two subjects on the same day**, each respecting the
  nine-technique ceiling in isolation. The union put `rate-limiting` and `hitl-approval`
  at ten, and the merge found `agent-memory` already there from a third pass. Neither wave
  was wrong; nothing enforces the ceiling; it is now a structure finding rather than a
  norm anybody is holding.
- **The other lane had evolved the subject-note format** - a dated touch log, standing
  debt, and a `touched_by` field - while this one was writing the older shape. Theirs is
  better and it was already on main, so the two colliding notes were rewritten into it
  rather than overwritten with this wave's version. A format that improves on a branch is
  a merge conflict nobody thinks to look for.

The reconcile lane retired four single-stack subjects while this one manufactured
fourteen. That is the clearest measurement of the tension between the two lanes anyone has
yet had, and it belongs in the domain note rather than here: **a harvest buys coverage
with transplant debt, and only the other lane pays it back.**
