# Run 2026-08-22-1 - the external-reconcile pilot

One repository, end to end, to harden a new lane before it scales: reconcile a
registry subject against a world-class tree that is NOT a consumer repo, and scan
the same tree with the maturity scanner. Target: `smithy-lang/smithy-typescript`
(reached as `awslabs/smithy-typescript`; GitHub redirects — a canonicalization
every future pass must expect), the retry layer under every AWS SDK for
JavaScript client.

## The mastery half

`retry-backoff` was one of the 65 single-stack subjects [[2026-08-21-2]] left as
debt. It now carries `node--storm-control.md`: the AWS retry-token quota and
adaptive rate limiter read as a realization of the storm-control technique, cited
at commit `6815d3e`, `@smithy/core` 3.33.3.

The reconcile shape held. Confirmed rules confirmed; one honest deviation found
and recorded (refusal classification erased at the caller boundary - the tree is
world-class AND falls short of the standard, which is exactly what "the standard
stays" is for); three candidate upward lessons banked in the subject note behind
deepen's convergence rule rather than applied on one sighting.

Review earned its keep on my own draft: two cost-arithmetic errors (throttling
vs transient token costs swapped; a 5→14 that was really 10→14) and three
imprecise line cites, all caught by re-deriving every number against the tree
before the gate ever ran. The gate checks none of that. **An external reconcile
without a citation re-check pass is a liability, not a contribution** - this is
the review-layer balance the lane needs as it scales: the reviewer's job here is
arithmetic and quotes, both mechanizable for a fleet later.

`verified_against` was deliberately omitted: its contract is a stack runtime
version, and the truthful pin for an external tree is a library version plus
commit, which lives in the application's prose. If this lane becomes standing,
the profile may want a field for that pin - proposed in the subject note, not
invented unilaterally.

## The scan half

The same repo scanned with the maturity scanner (LLM calibration per its
configured provider): **L3, overall 56, confidence 0.85 - rigor 74, adoption 23.**
Testing 95, CI/CD 97, velocity 90; AI tooling 2, agentic workflows 9. The scan
also surfaced a real finding the mastery half never looked for: a
`pull_request_target` checkout in a release workflow.

That split is the pilot's thesis measured: the scanner's axis (AI-nativeness)
and the mastery axis (engineering excellence) are near-orthogonal on exactly the
class of repo this lane targets. **The scanner is the selector and showcase; the
forge is the harvester. Neither substitutes for the other**, and a leaderboard
that conflated them would rank this world-class tree as mediocre.

Report persisted to the scanner's store (verified through its own read path:
peek returns L3/56 for the canonical name).

## Incidents

- **Stale build cache 404'd every API route as HTML** while pages served fine -
  nothing logged, pages green, instrument apparently healthy. Cleared cache,
  routes returned. The now-familiar shape: a green surface over a dead lane.
- **A second connection into a single-writer embedded store read a stale world**
  - the "persistence failed" finding was false; the app's own read path showed
  the row. Verify through the owner's door, never a side channel.
- **Port collision hit an unrelated app.** The scanner's dev instance silently
  took the next port; requests went to whoever held the expected one. Worse: in
  cleaning up, an unrelated process was killed on the assumption it was ours.
  Rule for every future automation here: identify a process by command line
  before touching it, and pin ports explicitly.

## Scaling notes for the next slice

Worth scaling: the reconcile found real material fast (~1,900 LOC read, one
application, three leads, ~2h including all incident time; marginal cost of a
second repo far lower). Before parallel dispatch: workers must inherit (1) the
citation re-check pass as a separate step from drafting, (2) canonical-name
resolution before any DB or filename is keyed, (3) explicit ports/isolation for
any app instance a worker starts.
