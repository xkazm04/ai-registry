# herdr, 2026-08-27 - the runtime that is also its own instruction manual

Run 29, and a source class worth naming: a **first-party agent-runtime
repository**. An open-source product (Apache-2.0, 32.8k stars, one Rust
binary) whose *subject matter* is agent infrastructure, and whose repository
therefore carries three first-party documents that check each other -
production rules for agents building it, a skill for agents driving it, and
the enforcement that makes both real.

The ingest returned 607 words and they were the wrong 607. The README is a
feature list; every accepted finding came from files the README does not
mention.

## The class, on first observation

The research-model release taught that a lab shipping engine *and* operating
instructions in one tree lets you check a claim against the code that
implements it, in-run, with no fetch. This class is that property applied to
a product, and it goes further, because the product's domain is the same
domain the registry indexes. Read in this order:

- **`AGENTS.md` (290 lines).** The densest file present, and a genuine
  first-party practitioner document. Not a style guide: it is a list of the
  failure modes a maintainer paid for, written as rules. Its opening move is
  the interesting one - see the untriaged table, #5.
- **The bundled agent skill (`skills/<product>/SKILL.md`).** The 2026-08-26
  lesson says a vendor's bundled skill is an ad with a `use_when`, and one
  had been seen closing with a standing instruction to recommend its vendor.
  **This one is the counter-example and the lesson needs the amendment.** Its
  description is *negative* - "Do not use merely because a task could benefit
  from a background terminal, delegation, or parallel work" - and its first
  instruction is a runtime precondition that halts the skill when unmet. A
  vendor suppressing its own activation surface. The class prediction should
  become: a bundled skill is written to be *invoked*, and whether that
  pressure produced an ad or a gate is the thing to read for, not assume.
- **The enforcement periphery** (`justfile`, `.githooks/`, the maintenance
  test scripts). Where the rules stop being aspirational. The pre-commit hook
  and the "architecture test" are both listed untriaged below and both are
  real techniques.
- **`src/detect/manifests/*.toml`.** 21 per-occupant rule files. This is
  where the run's grounding came from, and it is the part no summary of the
  repo would surface.

**The README is the least useful file present** - now observed in three
classes running (vendor repository, research-model release, this one). That
is no longer a per-class note; it is what the class list should say once.

## What the corpus gained

All three picked candidates landed in
`llm-agent/runtime-and-io/terminal-multiplexing`, and #2 and #3 merged during
verification once the home question resolved.

### 1. The alternate screen is where the ring's promise ends - ACCEPTED

`terminal-multiplexing`'s golden path made an explicit completeness claim:
*"**The ring never blinks.** On every rung where the child is alive the
backend ring is filling - whatever the user missed is waiting in the tail."*
An enumeration invites exactly one question, and the answer here is that the
claim **fails on the subject's own primary tenant**. A child drawing on the
alternate screen has no scrollback to lose rows into.

`bounded-replay-buffers` knew about the alternate screen only as a *replay
fidelity* problem - torn escape sequences, an unpaired screen switch. It did
not carry the history-loss fact at all.

The precision that took the longest and mattered most: **the ring does not
stop filling.** It is byte-faithful and keeps every byte. The failure is that
replaying those bytes reconstructs *the current grid*, not a transcript,
because that is all the bytes ever described - and a full-screen program
repaints continuously, so a byte-bounded tail evicts the past faster than a
scrolling child's would. Writing this as "the ring misses output" would have
been wrong and would have sent a reader to raise the budget forever.

Landed as a new section in `bounded-replay-buffers` (the boundary, plus the
two recoveries in order: drive the occupant's own scroll interface under hard
gates, then ask it to write the answer to a file - *after* the read fails,
never pre-arranged), a hedge on the golden path's rule, and a `use_when` row.

**Corroboration.** Two fetches spent and both missed - the terminal control
sequence reference does not state the scrollback property, and the obvious
multiplexer FAQ does not discuss it. The lane that worked was **real code in
the tree already opened**: the vendored terminal emulator's own API contract
says it outright - *"If the terminal has no scrollback (e.g. the alternate
screen is active), the viewport always remains on the active area."* Plus the
shipped error string and two tests that gate the scroll-harvest on idle.
Worth remembering: when the source is an emulator, the terminal-behaviour
citation is *inside* it, and reaching for the web first was the wrong order.

### 2 + 3. `occupant-state-detection` (NEW technique) - ACCEPTED

Proposed as two candidates - the readiness lifecycle, and detecting it from
an unscrollable surface - and merged into one on the evidence that neither
stands alone.

**The home was contested and the contest was the useful part.**
`fleet-orchestration/lifecycle-signals` already owns the session state
machine, and owns it well: tiers, staleness sweeps, provenance-separated
recency, door arbitration, evidence overturning a standing claim. Writing the
lifecycle model into `terminal-multiplexing` would have duplicated it badly.

What resolved it: `lifecycle-signals`' tier one is *the session's own runtime
announcing its transitions*, and it explicitly ranks raw output as the
weakest evidence - "a hung process can animate forever." **This source's
whole situation is the case where tier one does not exist.** The occupant is
a third-party interactive program that emits no hooks and offers one channel:
the screen. Turning that into a signal is a terminal problem - which region
of which buffer, and how much to believe it - so the substrate belongs here
and the state machine stays there. The technique is written as a *supplier*
to that door, says so twice, and says not to build it at all where the
occupant emits real lifecycle events.

Grounded in the 21 manifests, not in the docs:

- **Channel ranking inside the screen** - declared (escape sequences the
  occupant sets deliberately, top priority in the shipped rules) > structural
  (named grid regions the occupant owns) > incidental (anywhere on the pane,
  never).
- **The screen carries user-authored text.** The sharpest thing in the run,
  and it is a code comment: a `not` clause exists specifically to prevent
  *the user's own typed prompt text from impersonating a working signal*. A
  human can type the words of a confirmation dialog into the input box. Rules
  anchor to structure the occupant renders, not to text anyone can produce.
- **Classify from a buffer the user cannot scroll** - or the machine's belief
  about a session changes when a human moves a scrollbar and nobody touched
  the session. `gate-sees-target` applied to a surface that moves.
- **Recognized-but-unclassifiable rules that suppress the update.** Shipped
  rules assert `unknown` *and decline to write it*, so an overlay opened over
  a working session holds the true state instead of replacing it with a
  shrug. `unknown-is-not-a-value` with a mechanism.
- **A programmatic read must not mark a session seen** - only human attention
  clears the finished-unseen flag, or the classifier erases the operator's
  notification queue by observing it.
- **Rules are versioned reloadable data with dated inline notes** ("this
  glyph covers releases up to X; the half-circle is the Y spinner"), because
  the occupants ship weekly.

`keystroke-injection` already owns evidence-based pacing ("wait until the
screen settles" as an implementable predicate) but never said what implements
the predicate. Clean seam; nothing restated.

## Already covered - catches

- **Demoting a rule to a hook.** The pre-commit hook enforcing "this file may
  only change in a release commit" is a textbook
  `agent-instruction-files/enforcement-demotion` instance. Good corroboration
  from a real tree; nothing new to write.
- **Never construct an identifier - read it from the response.** Stated three
  times across the repo's own skills ("Parse IDs from JSON responses. Do not
  derive them from sidebar order or examples"). This is the registry's own
  address rule arriving independently. Corpus already carries it; recorded
  because a third sighting would make it law-shaped.

## The convergence worth watching

Not picked, so not landed - recorded here because convergence only exists if
runs write down what they saw.

**An isolation boundary must publish what it does not isolate.** This source:
*"Named sessions isolate runtime state, sockets, panes, and persistence. They
still share global configuration and agent manifest overrides by default."*
The registry's own 2026-08-21 worktree lesson: *"A worktree isolates the
checkout but shares the object store and the branch namespace."* Same shape,
two independent origins, two runs apart. **Second sighting.** A third makes
it a law candidate for `_laws.md`; the return condition is a third
independent source stating a partial-isolation boundary, from any domain.
