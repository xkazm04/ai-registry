## Design record (Phase 2d)

Grouped by system, because the routing count is per system and this tree holds
four.

### System A — durable agent-operation execution

**A1. Operation state is one total, replaceable value; large content lives at
addresses it names.**
- *forces:* a crash can land anywhere, and a journal or delta recovery must fold
  history and infer position from what is absent; but a full checkpoint that
  *contains the conversation* is quadratic in turn count.
- *buys:* recovery reads one value and dispatches to a procedure. Crash states
  become enumerable — between transactions, never inside one.
- *rejects:* event-sourced replay; delta checkpoints. Storage invariant 5 forbids
  any hot-path read that folds history or infers state from an absent value.
- *where:* `harness.md` §0.3 rule 3, §1.8, §3.2 (the 13-leaf union), §9.1 inv. 5.
- *stage:* after every durable transition.
- *corpus:* **NONE.** Nearest `agent-runtime-assembly/checkpoint-mode-custody`,
  which states the representation choice as a **binary** and does not model the
  escape — the quadratic term is a property of what is inside the checkpoint,
  not of totality. HOME IF NEW: `llm-agent`.

**A2. Two commits per uncertain effect, with the output's identities minted at
intent.**
- *forces:* an interrupted external effect must be distinguishable from one that
  never started, and the recovered record must occupy the same slot the real one
  would have or the transcript grows duplicates.
- *buys:* four durable crash positions, identical for every repeat-sensitive
  effect (`harness.md` §4.5 table).
- *rejects:* settle-only, which makes a crash during the effect and before it the
  same observation.
- *where:* `harness.md` §0.3 rule 4, §0.4 worked trace, §4.5.
- *corpus:* **PARTIAL.** `job-coordination/step-position-and-resumability` is one
  commit plus a cursor; the identity-before-the-effect half is new. HOME IF NEW:
  `llm-agent`.

**A3. Outcome durability order is not transcript placement order.**
- *forces:* parallel tool effects settle in completion order; results must be
  placed in assistant source order. Holding the finished ones in memory means a
  crash re-runs completed effects.
- *buys:* never re-run a tool whose complete outcome is durable, without
  violating order. Placement is a prefix flush, not a turn-end barrier.
- *rejects:* place-on-completion; hold-until-ordered; clear-everything-at-turn-end
  (WP09 shows why — early-placed results would exist in two projections at once).
- *where:* `tool-durability.md` "Problem"/"Goals"; `work-packages/09-*`;
  `harness.md` §9.1 inv. 28-29.
- *corpus:* **NONE.** HOME IF NEW: `llm-agent`.

**A4. Caller cancellation and durable cancellation are different, and the
admission door is one synchronous expression.**
- *forces:* a watcher's disconnect must not cancel the work, and cancellation must
  survive every watcher leaving; and a gate checked before an awaited preparation
  admits effects after cancellation was requested.
- *buys:* exactly two orders per admitted effect (admission-first, abort-first),
  each testable; a closed, enumerated catalog of what is gated.
- *rejects:* an ambient context discovered through async-local storage; a gate as
  mutex or scheduler; a gate that survives process loss.
- *where:* `harness.md` §4.2 (`:898-951`), §4.6, §9.1 inv. 23 and 36.
- *corpus:* **NONE.** `ordered-teardown` and `job-progress-and-cancellation` are
  both "the cancel path" and neither draws this line. HOME IF NEW: `llm-agent`.

**A5. Close is a controlled crash.**
- *forces:* a distinct graceful-shutdown path is a second recovery path exercised
  only on clean exits, and therefore the one that is wrong.
- *buys:* "reopening sees the same restart point as process loss" — one recovery
  path, exercised by every shutdown.
- *rejects:* a drain that synthesizes settlement, writes cancellation, or removes
  a durable operation.
- *where:* `harness.md` §4.7.
- *corpus:* **NONE.** `session-continuation/ordered-teardown` takes the opposite
  stance on a *different object* — a discriminator, not a contradiction. HOME IF
  NEW: `llm-agent`.

**A6. Streamed frames are observation and never establish completion.**
- *forces:* a reconnecting reader needs the partial; a partial must never be read
  as a settled response.
- *buys:* the committed prefix is reduced into a synthetic error response under
  the reserved ids, with an explicit unknown-outcome warning; every settlement
  deletes its frame list in the same transaction.
- *where:* `harness.md` §3.7, §4.5 orphan table row 1, §9.1 inv. 31-33.
- *corpus:* **COVERED, with a boundary.**
  `agent-runtime-assembly/indeterminate-closure-on-interruption` owns the
  synthetic-unknown rule. Landed as an amendment — see below.

**System A count: 4 NONE + 1 PARTIAL, one shared home-if-new, no existing
subject modelling the forces → the XL trigger fires.**

**2. Amendment — `indeterminate-closure-on-interruption`, the re-issue
exemption is narrower than it reads.**
The technique sorts interrupted work into four cases and puts a model request
in the side-effect-free class: *"re-issue it... because re-issuing costs
nothing."* Two things are wrong with that clause and **both were verified
corpus-internally, at zero fetch cost**:

- A generation is metered. `cost-metering/usage-ledgers:64` counts "mid-stream
  cancellations, refusals" among the consumed units the provider bills, and
  `:150` lists "a cancelled or killed call recorded with cost *zero*" as a
  defect. The clause contradicts its own bundle.
- A streamed generation leaves a committed partial the user has already seen,
  and re-issuing produces a second divergent answer to a question that appears
  once in the record.

The sort gains a fourth case rather than losing its third. Application:
`applications/node--indeterminate-closure-on-interruption.md`, written against
this source's own tree — `verified_against: node@22.19.0`, witnessed by the root
manifest's `engines.node: ">=22.19.0"` and every CI lane's `node-version: 22`,
not by a guess.

## Read second and did not pay

Round 10's declared focus said to read a vendor repository's `benchmarks/`
before its `docs/` when it carries a published protocol. This one does, and it
was read second, and **it produced no landing.** The protocol is honest and
well-written — deterministic synthetic data, fixtures prepared outside the
measured callback, one fresh process with forced GC per backend/dataset pair,
and an explicit "timing results are not CI performance gates" — but it publishes
a *method* and no *numbers*. `storage-targets.ts` registers exactly one target
(memory). So the rule from round 10 holds with a qualification worth carrying:
**a benchmark directory ranks first when it publishes results; when it publishes
only a protocol, it ranks with the other operating documents.** The
discriminator is whether a results table or a populated target list exists, and
it costs one `ls` to check.
