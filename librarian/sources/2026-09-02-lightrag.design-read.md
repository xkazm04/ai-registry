**A1 — Resume branches on observable evidence, not on the recorded status.**

```
decision:   a document re-entering the pipeline is routed by what the stores actually
            contain for it (chunks present? graph writes present?), not by the status
            field the last run wrote before it died
forces:     the status field is written by the process that is about to crash; a crash
            between "work done" and "status updated" makes the field a lie in the
            expensive direction (re-doing LLM extraction) or the dangerous one
            (skipping it)
buys:       a resumed document costs only the stages whose output is genuinely absent,
            and the invariant survives a kill -9 rather than a graceful shutdown
rejects:    a status-field state machine as the sole resume authority
where:      docs/FileProcessingPipeline.md (resume/recovery sections); pipeline.py [H]
stage:      pipeline entry, before stage dispatch
corpus:     job-coordination — knowledge/software-engineering/backend-platform/
            work-execution/job-coordination/job-coordination.md
```

**Evidence — golden path opened.** `job-coordination` carries
`step-position-and-resumability` and `terminal-state-recovery` in its `techniques:` list
`[V]`. Those two model exactly this decision's forces: a step position that survives the
worker, and recovery from a state the worker never got to write. **This is a catch.**

**A2 — A dead owner's work is reclaimed by proof of death, never by a timeout.**

```
decision:   a stalled document is only re-admitted when the prior owner is shown to be
            gone (process identity — pid plus process start time, so a recycled pid
            cannot impersonate the dead holder); there is no TTL after which work is
            simply assumed abandoned
forces:     LLM extraction on a large document legitimately runs for many minutes with
            no I/O the coordinator can see, so any TTL short enough to recover a real
            crash promptly is also short enough to duplicate live work — and duplicate
            extraction is not idempotent, it doubles the graph's merge load and the
            token bill
buys:       recovery latency is decoupled from job duration; the coordinator never has
            to pick a timeout, which is the number nobody can pick correctly
rejects:    lease-with-renewal — the standard answer, and the one the corpus holds
where:      kg/shared_storage.py, kg/scan_job_store.py [H]; FileProcessingPipeline.md
stage:      admission, when a document is found in a non-terminal state with an owner
corpus:     NONE. Nearest: job-coordination/techniques/lease-renewal.md
```

**Evidence — golden path opened.** `job-coordination`'s `techniques:` list is
`job-state-machines, lease-renewal, step-position-and-resumability,
terminal-state-recovery` `[V]`. `lease-renewal` **is the lease posture** — a holder
renews, and expiry is the reclaim trigger. `concurrency-guards` offers
`cross-process-exclusion` and `release-guarantees` `[V]`. The concept probe *"reclaiming a
lock from a dead holder without a timeout"* returned `concurrency-guards` at **6 points**
— a near-empty, which the method says to distrust in both directions, so
`concurrency-guards.md` was opened: it names `cross-process-exclusion` for the mutual
exclusion primitive and `release-guarantees` for the unlock path, and neither models
**liveness proof as an alternative to expiry**. The corpus models the lease; it does not
model the case where the lease's own parameter is unpickable. **NONE, and it is a drawn
boundary — the highest-value kind, because LightRAG rejects our default explicitly.**

> Files: `lightrag/base.py` (1,863 L), `kg/` (18 backends), `kg/factory.py`,

**B1 — A backend capability is declared in the type system when it has no fallback, and
as a runtime flag when it does.**

```
decision:   two different mechanisms carry "can this backend do X": an abstract method
            (so a backend that omits it cannot be instantiated at all) where no degraded
            path exists, and a class-level capability flag with a raising default where
            the engine can route around the absence
forces:     18 backends behind 4 interfaces, several of them community-contributed; a
            capability gap must fail at the earliest moment it can be known, and that
            moment differs by capability — a missing required operation is knowable at
            class definition, a missing optional one only when a query needs it
buys:       the "cannot be instantiated" class of gap is a startup error with a
            traceback naming the class, never a runtime AttributeError inside a query
rejects:    one uniform mechanism (all-abstract, which forbids partial backends; or
            all-flags, which defers every gap to request time)
where:      lightrag/base.py [H]; kg/factory.py [H]; the 18 kg/*_impl.py modules [V]
stage:      class definition / instance construction
corpus:     NONE. Nearest: data-access/techniques/cross-driver-invariant-parity.md
```

**B2 — Write ordering is carried by a monotonic sequence token, not by a transaction.**

```

**B3 — Migrations are driven by the shape of the data found, not by a recorded version.**

```
decision:   on open, the store inspects what the rows/documents actually look like and
            migrates forward from that, rather than reading a schema-version marker and
            replaying the steps after it
forces:     several backends have nowhere to *put* a version marker that is atomic with
            the data it describes (a JSON file's version field and its rows are two
            writes); and a store can be edited by an older library version between runs,
            which makes any recorded version a claim rather than a fact
buys:       a store that has been touched by a different version, or by hand, still
            converges; there is no "version says 4, data is shape 3" state to be stuck in
rejects:    a version table / migration-chain replay
where:      lightrag/storage_migrations.py (342 L) [V, file];
            tests/test_storage_migrations_strict_read.py [V, file]
stage:      storage open
corpus:     migrations — knowledge/software-engineering/backend-platform/data-layer/
            migrations/migrations.md  (PARTIAL → promoted, see §6 Q3)
```

**Evidence — technique opened.** `migrations/techniques/schema-drift-detection.md` was
read `[V]`. Its **Class 1** is *"two authorities for one schema"* — a fresh-install path
and an upgrade path that diverge, *"a vocabulary with two hand-maintained authorities,
which is a race with a delay fuse."* That is the two-authority problem. LightRAG's
decision is the **zero-authority** answer: derive the current shape from the data so

**C1 — Entity identity is a normalised surface form produced by the model; there is no
registry.**

```
decision:   the node key for an entity is the LLM's normalised name string; two mentions
            are the same entity iff they normalise to the same string
forces:     the corpus is arbitrary unstructured text with no authority to join against —
            there is no company register, no roster, no id scheme; refusing to create a
            node without an external identifier would mean creating no nodes at all
buys:       a graph over any corpus, with no per-domain identity infrastructure
rejects:    identifier-joined identity (the correct answer where a registry exists)
where:      lightrag/operate.py (extraction + merge path) [H]; lightrag/prompt.py [H]
stage:      per-chunk extraction, at node creation
corpus:     NONE. Nearest: civic-intelligence/civic-graph-infrastructure/
            civic-knowledge-graphs — and it REJECTS this decision explicitly
```

**Evidence — golden path opened in full `[V]`.** `civic-knowledge-graphs` § "Things, not
strings" states the opposite decision in its own words: *"the graph holds **entities, not
mentions**: a node exists only under a durable identity, and the identity comes from the
registries, not from the text… **Name similarity is never an edge.**"* It then names
LightRAG's shape as its **first listed failure mode**: *"**The mention graph** —
string-matched entities, name-similarity edges; homonyms convert an innocent namesake
into a suspect."*

This is not a conflict to resolve; it is a **discriminator already drawn**, and the
method's rule applies — *when a rule inverts across bundles, name the discriminator, do
not link.* The discriminator is: **does an external identity authority exist for this
corpus?** Where it does, the civic rule is right and the mention graph is a libel engine.
Where it does not, refusing to build the graph is not an available option, and the real
question — which the corpus asks nowhere — is *what discipline makes a name-keyed graph
honest about the identity risk it is carrying.* **NONE.**

**C2 — The merge operator is description accumulation, with LLM summarisation triggered
by a threshold.**

```
decision:   when the same entity or relation is extracted from a second chunk, the
            descriptions are ACCUMULATED (concatenated, deduplicated) rather than
            overwritten or re-decided; an LLM summarisation pass collapses the
            accumulation only once a fragment-count / token threshold is crossed
forces:     each chunk sees one facet of an entity, so last-write-wins destroys evidence
            and first-write-wins ignores it; but unbounded accumulation makes a
            frequently-mentioned entity's description grow without limit and eventually
            dominate every retrieval budget it enters
buys:       merge is associative and order-independent below the threshold (re-ingest in
            a different order converges), and the expensive summarisation call is paid
            per-entity-crossing-a-threshold rather than per-mention
rejects:    summarise-on-every-merge (cost linear in mentions); overwrite (evidence loss)
where:      lightrag/operate.py (merge/summarise path) [H]; constants.py thresholds [H]
stage:      post-extraction merge, before the graph write
corpus:     NONE. Nearest: agent-memory/techniques/consolidation.md,
            agent-memory/techniques/rollup-compaction.md  (see §6 Q4)

**C3 — Extraction is multi-pass ("gleaning"): the same chunk is re-prompted until the
model reports completeness or a pass cap is hit.**

```
decision:   after the first extraction pass over a chunk, the model is asked again
            whether entities remain, and extraction repeats; a hard cap bounds it
forces:     a single extraction pass over a dense chunk systematically under-recalls —
            the model satisfices, returning a plausible handful rather than the full set,
            and the shortfall is invisible because the output is well-formed
buys:       recall that is bounded by a declared cap rather than by the model's appetite;
            the cap is a knob an operator can price
rejects:    one-shot extraction; and unbounded re-prompting, which a model will happily
            continue forever by inventing entities
where:      lightrag/operate.py (gleaning loop) [H]; lightrag/prompt.py (continue /
            if-loop prompts) [H]
stage:      per-chunk extraction, between passes
corpus:     NONE. Nearest: structured-output/techniques/extraction-strategies.md
```

**Evidence — technique frontmatter opened `[V]`.** `extraction-strategies`' `use_when` is

### SYSTEM D — Query modes

> Files: `lightrag/operate.py` (query builders), `rerank.py` (657 L),
> `query_validation.py`, `llm_roles.py` (586 L) `[V]`

**D1 — Two-tier keyword extraction routes a query into the graph lanes.**

```
decision:   before retrieval, an LLM decomposes the query into HIGH-level keywords
            (themes → matched against relation descriptions) and LOW-level keywords
            (specifics → matched against entity names); the two tiers address different
            stores and their results are then merged
forces:     an entity index and a relation index answer different questions, and one
            embedding of the whole query is a blend that under-serves both — a thematic
            question retrieves specific entities and a specific question retrieves
            thematic relations
buys:       a query's abstraction level becomes an explicit, inspectable artifact that
            decides which lane it enters, instead of an emergent property of one vector
rejects:    a single query embedding fanned out to all lanes
where:      lightrag/operate.py (keyword extraction + mode dispatch) [H];
            lightrag/prompt.py (keyword-extraction prompt) [H]
stage:      query time, before any lane executes
corpus:     retrieval — knowledge/software-engineering/llm-agent/prompt-and-context/
            retrieval/retrieval.md  (PARTIAL → promoted, §6 Q5)
```

**Evidence — golden path read in full `[V]`.** `retrieval` is the corpus's most mature
subject here: nine techniques, and its § "The pipeline: two planes" states the query
plane as *"query → per-lane execution with overfetch → per-lane floors → fusion into one
order with cross-lane dedup → budget cut in consumer units → the slice."* **The pipeline
begins at `query` and the first thing that happens to it is per-lane execution.** There is
no stage between the query arriving and the lanes running. `retrieval-triggering` owns the
decision *whether to retrieve at all* — upstream of this — and `hybrid-lane-fusion` owns
*combining lane outputs* — downstream. The **query-decomposition stage that decides which
lane sees what** is unowned. This is exactly Phase 6's *missing stage* shape: *"a subject
that is thorough from stage two onward is exactly where a missing stage one hides."*
**A home exists and the stage does not** — a technique in `retrieval`, not a new subject.

**D2 — `naive` mode bypasses keyword extraction and the graph entirely: pure vector chunk
search.**

```
decision:   one of the query modes deliberately skips the whole graph apparatus and does
            plain vector search over raw chunks, shipped as a first-class mode rather
            than as a debug switch
forces:     the graph path costs at least one extra LLM call per query (keyword
            extraction) plus graph traversal, and for a query whose answer sits verbatim
            in one chunk that spend buys nothing; also, it is the only honest baseline
            against which the graph's contribution can be measured
buys:       a same-tree A/B arm — the graph's value is measurable rather than assumed
rejects:    graph-always (no baseline, unmeasurable value); and hiding the baseline
            behind a flag, where nobody runs it
where:      lightrag/operate.py (naive mode branch) [H]; docs/ProgramingWithCore.md [V]
stage:      query dispatch
corpus:     retrieval golden path § "No single lane suffices"
```

**Evidence — golden path read in full `[V]`.** The corpus is **ahead** here and says so
more sharply than the tree does: *"hybrid fusion is the default posture, not the upgrade
path. A system that ships vector-only retrieval has chosen to fail on every query
containing an identifier."* And on adding lanes: *"a new lane must be a strict addition:
run alongside the existing lanes and unioned in, so the richer configuration is a superset
of the leaner one — never a replacement whose own blind spot silently costs recall the old
path had."* LightRAG's modes are **alternatives the caller picks**, so choosing `local`
*is* the replacement the corpus forbids. **Catch — and the source is the counter-example
that makes our rule concrete.** Worth one sentence in `hybrid-lane-fusion` as a sighting;
not a landing on its own.

## The subject, in one paragraph

**LLM-extracted entity graph** is the discipline of building and maintaining a typed
entity/relation graph out of unstructured text when **no external authority supplies
identity**. Its unit is one chunk's extraction merged into a graph that many chunks
before it have already written, and its four recurring problems are: choosing an identity
key when the only candidate is a string the model produced, and being honest about the
homonym risk that choice imports; defining a merge operator that is order-independent and
bounded, so re-ingesting a corpus in a different order converges and no entity's
description grows without limit; getting adequate **recall** out of a model that returns
well-formed, incomplete extractions; and keeping a graph store and a vector index
describing the same facts consistent when no transaction spans them.

## Boundaries it must NOT absorb

- `retrieval` owns everything from the query onward — lanes, fusion, floors, budgets, and
  both structural lanes. This subject writes the graph those lanes read, and must not
  restate one word of the query plane. **D1 (query decomposition) lands in `retrieval`,
  not here** — unless the drafter argues otherwise, which is an open question below.
- `civic-knowledge-graphs` owns the registry-joined graph, the claim ledger, the

- `agent-memory` owns what is stored, what is believed, what decays — including

  accumulated descriptions, and must state why that unit differs.
- `structured-output` owns parsing one reply — rungs, repair, refusals. This subject owns

- `context-hierarchy` owns tiers over a **containment tree**. This graph is not a tree and

- `chunking-and-indexing` (in `retrieval`) owns chunk identity and idempotent re-ingest.

## 9. Reusable engineering

*What here is good enough to reuse, and what does it do that we do worse?* These land in
`scripts/`, `practices/` and `docs/` — the lanes the corroboration table calls "judgment,
no gate".

- **The offline oracle as a checked-in fixture.**
  `lightrag/evaluation/sample_retrieval_oracle.json` + `offline_retrieval_check.py` `[V]`
  is a frozen query→expected-ids map that regression-tests retrieval **with no model in
  the loop**. The registry has the doctrine (`retrieval-evaluation`) and **no instrument**:
  `scripts/research-map.mjs` is the corpus's own retrieval engine and nothing measures
  whether a corpus change moved its results. A `scripts/map-oracle.json` of ~20 frozen
  concept→expected-subject rows, checked by a dependency-free script, would catch the
  exact failure this run had to guard against by hand — the map silently re-ranking after
  a sibling lands a subject mid-run. **This is the single highest-value steal in the tree.**

- **A per-stage debug CLI that dumps the intermediate artifact.**
  `lightrag/parser/cli.py` + `debug.py` + `docs/ParserDebugCLI.md` `[V]` let an operator
  run one pipeline stage in isolation and inspect what it produced. Our instruments print
  conclusions (`research-map` prints rankings, `librarian-scan` prints points) but will not
  dump the intermediate — the per-document `use_when` set the ranking was computed from.
  A `--dump` flag on `research-map` is the same idea and would have shortened §3's
  golden-path verification materially.

- **A failure taxonomy expressed as filenames.** 22 root-level test modules `[V]`, each
  named for exactly one defect: `test_get_env_value_nonfinite`,
  `test_weighted_polling_nonpositive_max`, `test_sync_wrapper_guard`,
  `test_storage_migrations_strict_read`, `test_cosine_similarity_nonfinite`,
  `test_empty_int_env_field_defaults`, `test_strip_control_characters`. The taxonomy is
  readable from `ls` with no file opened. This is a **practice** worth writing up: our
  `scripts/` checkers bundle many assertions per file, so a red gate names the checker, not
  the defect.

- **A durable IR with a backfill path.** `lightrag/sidecar/` ships `writer.py`, `ir.py`,
  `placeholders.py` **and `backfill.py`** `[V]`. The fourth file is the discipline: a
  durable derived artifact is incomplete without a story for the records that predate it.
  The registry has the same shape and not the same rigour — `build-index.mjs` regenerates
  wholesale, and a new frontmatter field has no backfill lane, so subjects forged before it
  simply lack it and nothing counts them.

- **Two measurement lanes that never share a fixture.** `reproduce/` (the paper's
  protocol, `Step_0..3` + `batch_eval.py`) and `tests/` (the product's) are structurally
  separate `[V]`. The registry's `SCORECARD.md` mixes both roles — it records method
  quality *and* per-run yield — and the intake method's own v2 note (*"the scorecard
  counted landings without weighing them"*) is that mixture's symptom.
