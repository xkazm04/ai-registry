# dora, read as a system: seven decisions, four with no home

## Why this run exists

The 1.6.0 run over the same tree (`2026-09-02-dora.md`, commit `cb561cc`) mined it
with the news method and produced four amendments to four mature subjects, each
correct and each a paragraph. It never asked why the tree is shaped the way it is.
Under 2.0.0 the repository is read first for its **design decisions** - the forces
that made the obvious alternative wrong, what each decision buys, what it rejects -
and the count of decisions the corpus does not model decides whether this skill
keeps the source or hands it to `/forge`. This note is that read, and the design
record below is the handoff brief.

Tree state moved between the two runs (`cb561cc` -> `bdd1516`, same day); the
design documents read here are unchanged by the intervening commits.

## Design record

### D1 - Correlated exchanges are metadata conventions over pub/sub, not new primitives

- **decision:** service (request/reply), action (goal/feedback/result, cancel) and
  streaming (session/segment/chunk, flush) are implemented as *well-known metadata
  keys* on ordinary topic messages - `request_id`, `goal_id`/`goal_status`,
  `session_id`/`segment_id`/`seq`/`fin`/`flush` - with helper functions in each
  language binding; the daemon, coordinator and descriptor syntax are untouched.
- **forces:** four language bindings that must all speak the pattern; a daemon whose
  event loop is the latency budget; a graph whose edges are declared statically in
  YAML, so a request/reply pair is just two edges.
- **buys:** every pattern is portable across bindings and recordable/replayable as
  plain messages; a pattern can be added without a protocol change; a consumer that
  ignores the keys still receives valid data.
- **rejects:** first-class RPC/action types in the wire protocol and the descriptor
  (the alternative the robotics ecosystem it bridges to took). Stated in
  `docs/patterns.md` opening paragraph.
- **cost the tree records:** correlation state lives only in the endpoints, so a
  restarted server orphans every in-flight correlation and nothing synthesises a
  terminal event; the client-side helpers watch the supervisor's `NodeRestarted`
  event to fail pending waits (`docs/patterns.md` §6, `dora-rs/adora#148`). Flush
  discards all queued messages on an input regardless of session, so sessions may
  not be multiplexed on one input (§4 note).
- **where:** `docs/patterns.md` §1-§6; `apis/rust/node/src/event_stream/mod.rs`
  (`recv_service_response`, `recv_action_result`); `docs/architecture.md` "Well-Known
  Metadata Keys".
- **stage:** message construction and consumption at the node API, above transport,
  below application logic.
- **corpus:** NONE. Nearest: `client-architecture/realtime-events` (an in-app bus of
  discrete named facts; it models fan-out and subscription lifecycle, not
  request/response correlation across processes or the orphaning of a correlation
  on peer restart); `client-architecture/ipc-contract` (command shape and error
  mapping across one process boundary, not exchange patterns over a graph).

### D2 - The data plane bypasses the daemon; the control plane does not

- **decision:** nodes publish payloads above a size threshold directly to each other
  over a shared-memory pub/sub session, local subscribers receiving zero-copy
  references and remote ones network copies on the same code path; the daemon sees
  only lifecycle notifications. Small messages and all control traffic still go
  node -> daemon -> node.
- **forces:** camera frames, point clouds and tensors are all above the threshold;
  the previous design routed every payload through the daemon with a drop-token
  lifetime protocol (~1,200 lines, 11 unsafe blocks, 4 blocking threads per node, a
  pinned unmaintained dependency) and separate local/remote code paths.
- **buys:** 35% lower latency and 3-10x throughput above 2 KB (the tree's own
  measurement); one path for local and remote; deletion of the drop-token lifecycle;
  a daemon event loop that is no longer on the hot path.
- **rejects:** daemon-routed shared memory with reference-counted drop tokens
  (`docs/plan-zenoh-shared-memory.md` "Current Implementation"); a single-loop
  daemon that awaits network publishes inline (`docs/plan-event-loop-separation.md`).
- **cost the tree records:** 55-80% slower below 2 KB, so a threshold guard keeps
  small messages on the old path; recording is a subscriber and must copy; a
  first-message latency spike from session init (pre-warm at startup); a memory-lock
  ulimit on deployment hosts; one session per node.
- **where:** `docs/plan-zenoh-shared-memory.md` (the decision document, with the
  comparison table); `docs/architecture.md` "Node to Node (Zenoh SHM Data Plane)";
  `DORA_ZERO_COPY_THRESHOLD`.
- **stage:** transport selection at send time, per message, by size and locality.
- **corpus:** NONE. Nearest: `engineering-process/continuous-integration/ci-execution-trust`
  (`control-plane-execution-boundary` - a trust boundary, not a throughput one);
  `llm-agent/runtime-and-io/subprocess-lifecycle` (owns the process, explicitly
  hands "what flows through the pipes" to streaming-output, which owns rendering).

### D3 - Interruption is a queue semantic, carried in-band

- **decision:** a message carrying `flush: true` clears the receiver's input queue
  of every older message before it is delivered; a streaming segment that is
  interrupted simply never gets `fin`, and the next segment carries the flush.
- **forces:** voice pipelines where a user speaks over synthesised output and queued
  audio chunks must vanish now, across a process boundary, without a control-plane
  round trip.
- **buys:** interruption latency bounded by one message delivery; no out-of-band
  cancel channel; works identically for local and remote subscribers.
- **rejects:** a separate cancel/abort control message routed through the daemon;
  per-session queues (the note in `docs/patterns.md` §4 says why: flush is per
  input, so independent sessions must not share one).
- **where:** `docs/patterns.md` §4 "Queue flush behavior"; well-known key `flush` in
  `docs/architecture.md`.
- **stage:** input-queue admission at the receiver, before the node's event loop
  sees the message.
- **corpus:** partial. `llm-agent/runtime-and-io/streaming-output/cancellation-and-finalization`
  models cancellation at the *renderer* (whose output, whether it is still flowing,
  how it ended). It does not model discard-on-arrival at a transport queue between
  processes, nor the session/segment/sequence/fin envelope that makes a stream
  resumable and interruptible at once. Application-worthy against streaming-output;
  the mechanism belongs with D1/D4.

### D4 - Every input edge carries its own queue policy, and the scheduler is fair across inputs

- **decision:** each input declares `queue_size` (default 10) and `queue_policy`
  (`drop_oldest` default, or `backpressure` with a hard cap at 10x that logs and
  drops); the node-side scheduler serves inputs with least-recently-used fairness so
  a high-frequency input cannot starve a slow one; timers burst as `skip`, never as
  a storm.
- **forces:** sensor inputs at 30-1000 Hz beside control inputs at 1 Hz on one node;
  a consumer that is slower than a producer for seconds at a time; the older default
  (unbounded per-node channels) was an OOM found by audit.
- **buys:** bounded memory per edge; freshness by default (a robot wants the latest
  frame, not the oldest); a declared place to opt into losslessness.
- **rejects:** one queue per node; unbounded channels; global backpressure.
- **cost the tree records:** the policy is honoured on the daemon path and bypassed
  on the direct data-plane path (soundness audit, medium) - the two transports
  diverge here.
- **where:** `docs/yaml-spec.md` lines 151-167; `apis/rust/node/src/event_stream/scheduler.rs`
  line 137 ("fairness between inputs"); audit `P13` and the June audit's zenoh
  backpressure finding.
- **stage:** per-input admission at the receiving node, and input selection in its
  event loop.
- **corpus:** NONE. Nearest: `backend-platform/work-execution/admission-queue`
  (admission of *work items* to an executor: run/hold/refuse, depth bounds, fairness
  across tenants) - the vocabulary transfers, the object does not: these are data
  edges in a graph whose default verdict is "drop the oldest", and the fairness is
  across a node's inputs, not across requesters.

### D5 - Fault tolerance is declared per node and per edge, and upstream failure reaches consumers as typed events

- **decision:** the descriptor carries `restart_policy`/`max_restarts`/
  `restart_window`/backoff per node, `health_check_timeout` per node, and
  `input_timeout` per input; the daemon enforces them and *propagates* the outcome
  into the data plane as events the consumer's loop receives beside data:
  `InputClosed`, `InputRecovered`, `NodeRestarted`, `AllInputsClosed`. A helper
  caches the last value per input so a consumer can degrade instead of stop.
- **forces:** hardware drivers that crash on cable events; ML nodes that hang in a
  third-party library; a planner that must keep planning on stale detections; a
  fusion node whose inputs fail independently.
- **buys:** graceful degradation is a consumer decision made with information (which
  input, closed or recovered, which upstream restarted) rather than a timeout the
  consumer had to invent; restart and staleness are policy, not code.
- **rejects:** application-level heartbeats between nodes; supervisor-only
  restart with silent downstream (`docs/fault-tolerance.md` scenarios 1, 3, 4).
- **where:** `docs/fault-tolerance.md` (whole page); `docs/yaml-spec.md` lines
  42, 165-167, 323-328; event enum in `docs/architecture.md` "Node events".
- **stage:** supervision in the daemon, then event injection into each affected
  consumer's input stream.
- **corpus:** NONE for the propagation half. `llm-agent/runtime-and-io/subprocess-lifecycle`
  models the supervisor's side (the v1 run amended its liveness technique from this
  page) and `backend-platform/resilience/retry-backoff` models the restart ladder
  and breakers for *callers*; neither models a consumer graph being told, in its
  data channel, that an upstream edge went stale or came back.

### D6 - Payloads are self-describing and every message carries a wire version and a causal timestamp

- **decision:** the payload is a columnar IPC stream that carries its own schema
  (the earlier type sidecar was dropped), the metadata carries
  `metadata_version` bumped on every shape change, and every inter-component
  message is wrapped in a hybrid-logical-clock timestamp.
- **forces:** four bindings and two encodings in the wire's history; positional
  encoding that misparses silently on a shape change; multi-machine causality
  where wall clocks disagree.
- **buys:** peer version mismatch fails at register with a clear error; a schema-once
  hash lets a receiver validate type per stream rather than per message; ordering
  across daemons that no single clock could give.
- **rejects:** a per-message type descriptor; wall-clock timestamps (the tree still
  carries a per-timer private clock the audit flags as a causality break, `A2`).
- **where:** `docs/architecture.md` "Data Format and Metadata", "Timestamped
  Wrapper"; changelog "Binary wire format moved" entry.
- **stage:** message envelope construction, every send.
- **corpus:** partial. `client-architecture/client-state/persistence-and-migration`
  now carries the versioning clause (v1 run); `operations/governance-and-records/audit-logging/two-clock-records`
  and `llm-observability/.../dual-clock-event-time` model two clocks on a record,
  not a hybrid logical clock as the ordering authority across machines.
  Application-worthy; the clock half is a lead inside the handoff.

### D7 - The coordinator is off the data path and expendable; daemons outlive it

- **decision:** a single coordinator holds placement and lifecycle state behind a
  pluggable store, never touches data, and is designed to be restartable: daemons
  keep their nodes running, reconnect with backoff, re-register under their previous
  id, and the coordinator reconciles a `Recovering` status from their reports
  instead of failing everything at boot.
- **forces:** a control node that crashes must not take a robot fleet down; the
  earlier recovery marked every in-flight dataflow failed and daemons exited on
  connection loss.
- **buys:** control-plane restarts are survivable; daemons degrade gracefully
  (buffer critical reports, drop metrics) while disconnected.
- **rejects:** a highly available coordinator cluster (deferred as heavier than the
  problem); wholesale boot-fail (the v1 run's catch against the corpus's
  recovery technique, which the tree's own plan then agrees with).
- **cost the tree records:** the June audit found the reconnect path still kills
  nodes on a >20 s gap despite a comment saying otherwise.
- **correction from the scout (2026-09-02):** the decision IS implemented, not
  planned - boot marks in-flight dataflows `Recovering` and fails them only after
  a 60 s window (`binaries/coordinator/src/lib.rs:370-402`, `:2273-2308`), with
  four reconcile classes and a per-pair respawn backoff; `docs/fault-tolerance.md`
  "Startup Recovery" (lines 468-479) describes the *previous* blanket-fail
  behaviour and is stale. The v1 run's catch #5 read the stale page; the corpus
  technique and the code agree, and the doc does not. The three `plan-*.md`
  files are landed design records, not backlog.
- **where:** `docs/plan-coordinator-ha.md`; `docs/fault-tolerance.md` "Coordinator
  State Persistence"; `docs/distributed-deployment.md` "Auto-Recovery".
- **stage:** control-plane topology and recovery.
- **corpus:** partial. `backend-platform/work-execution/job-coordination/terminal-state-recovery`
  models the recovery sweep's verdicts per class (adopt/resume/park/fail) and the
  executor ceiling - this decision is that technique applied to daemons as
  executors. Application-worthy against job-coordination; not a new mechanism.

### D8 - The graph is declared, expanded, validated, and then mutated only additively

- **decision:** a YAML descriptor declares nodes, typed inputs/outputs, placement
  (`deploy.machine` / labels) and policies; `module:` nodes expand at load time
  into inner nodes and a module may carry no source fields of its own (rejected at
  expansion); validation runs before spawn; and dynamic add/remove of nodes and
  mappings is implemented as additive mutations of the single-threaded event
  loop's routing tables, with `InputClosed` sent to dependents on removal.
- **forces:** a routing table built once at spawn; agent use cases that spin up
  nodes mid-run; a static graph that made restart the only topology change.
- **buys:** a validated graph before any process exists; topology change without
  locking, because one loop owns the tables.
- **rejects:** a locked, shared routing table; fully dynamic discovery.
- **where:** `docs/yaml-spec.md`; changelog "A module node may no longer carry
  source fields"; `docs/plan-dynamic-topology.md`.
- **stage:** descriptor load and validation; then a control-plane mutation path.
- **corpus:** partial. `backend-platform/work-execution/pipeline-dag/graph-validation`
  and `valid-but-degraded-plans` model validating a user-authored step graph before
  a run exists; the subject's opening excludes long-lived process graphs by its
  own definition (steps with a fate, not processes with channels). The expansion
  rule is a boundary case of graph-validation (application-worthy); dynamic
  topology belongs to the handoff.

### Scout corrections to D1-D4 (2026-09-02, node-API territory)

- **D1:** "four bindings speak the pattern" is false today - the C binding has
  no metadata surface at all (`apis/c/node/node_api.h:74`), Python has the send
  half only; parity is Rust and C++ full. The pattern's portability floor is
  "a binding that exposes metadata", and the record's `buys` overstated it.
- **D2 missed the mechanism that makes "one path" honest:** a per-output
  route-probe handshake - acked markers inside a 500 ms grace measured from the
  readiness barrier - after which an un-acked output is *frozen* on the
  brokered path for the whole run and never upgrades
  (`apis/rust/node/src/node/mod.rs:160-182`, `:283-303`). And the daemon side
  has a rule for when the bypass is forbidden: a remote consumer declaring an
  `input_timeout` is pinned to the brokered path because only that path
  refreshes its deadline (`binaries/daemon/src/output_routing.rs:113-131`).
  "A declared policy demotes the transport" is the decision, not a cost.
- **D3 is wrong as written:** flush discards *ordinary* queued messages only;
  correlated events and the shutdown signal are flush-immune
  (`event_stream/scheduler.rs:266-295`, tests at `:518`, `:773`).
  `docs/patterns.md` §4 still states the old rule - a doc/code deviation.
- **D4's stated cost is fixed:** both transports now enter one scheduler under
  one policy (`scheduler.rs:24-33`, `:244-350`; paired tests `:838`, `:858`).
  What the record missed is that there are *two* queue layers - the node
  API's per-input policy and the daemon's 1,000-slot channel with 50 slots of
  control headroom (`binaries/daemon/src/event_types.rs:227-267`) - and that
  eviction is a *classification* (ordinary first, never the stop signal,
  correlated last and loudly; `scheduler.rs:89-107`).
- **D6 missed a side plane:** schema-once negotiation on a per-output
  subtopic with in-band re-priming and a fatal grace of three refresh
  intervals (`event_stream/mod.rs:1624-1712`).
- **Missed decisions the scouts surfaced:** a typed reply per control
  mutation, commit only on the exact variant (`daemon_to_coordinator.rs:484-513`);
  compensating rollback of a partial multi-machine spawn (`coordinator/run/mod.rs:170-245`);
  the readiness barrier's verdict is persisted and replayed to late or restarted
  subscribers (`daemon/pending.rs:18-120`); transport wiring injected into the
  child's environment as a versioned contract (`core/topics.rs:24-105`,
  `:440-452`); ordering is API-dependent (`recv()` reorders for fairness,
  `Stream::poll_next` is chronological, `event_stream/mod.rs:781-789`, `:1725-1760`).
- **Stale anchors:** `docs/architecture.md:433-494` documents the deleted
  drop-token lifecycle; `:713` says recording format 1 (code: 2);
  `libraries/shared-memory-server/` no longer exists.

## Routing

**Load-bearing decisions: 7 (D1-D7; D8 is two decisions, one of them a boundary
case). Not modelled by any subject: 4 (D1, D2, D4, D5).** Three or more, so this
source is a **forge job**. The count was written before the decision, as the method
asks, and it was not close: the corpus owns process supervision, work-item queues,
step DAGs, an in-app event bus and model-output streaming, and none of them owns a
graph of *processes* joined by *typed data channels* across machines - the thing
every one of D1, D2, D4 and D5 is a decision about. The handoff goes to
`/forge`'s harvest lane (`docs/harvest-brief.md`): the software-engineering bundle
exists, so the new material joins it as a new subcategory rather than a new bundle.

What intake keeps: the source-tree applications for the `partial` entries (D3, D6,
D7, D8), written against this clone; the v1 run's claims, which stand; and this
note. What the handoff carries: D1, D2, D4, D5 as the first candidate subjects, the
anchors above as the scouts' starting points, and the `partial` entries as
reconciliation targets.
