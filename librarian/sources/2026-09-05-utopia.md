# `deeplethe/utopia` - a bitemporal knowledge graph read under three questions

**Class.** Vendor repository, and a system: one Rust binary over one Postgres, eight
crates, a 3,000-word pipeline document that ends every stage with "where this stage drops
things", and twenty-one decision records whose README states the conventions - revisions
stay in place, the implementing PR updates the status line, superseded never rewritten.
The class prediction ("its docs' rules page and its client's types") under-predicted:
the densest surfaces were the decision records' *Dead ends* sections, the migration
files' comments (each migration is named as a sentence: `0018_a_fact_awaiting_a_nod`),
and the store's integration tests, whose module docs state the failure each was written
after and, twice, that "this test must be red on the old implementation or it proves
nothing". The README was read last and contributed the roadmap only.

**Expected yield, said before the table.** Forge-shaped tree, but the operator scoped
the run to three questions - the registry as a knowledge-base system, the memory system
for agents (and Athena, the personas companion), and Rust craft - so the yield was
predicted as: two or three techniques in existing subjects, applications against the
source tree for the Rust question, and a banked handoff for whatever falls outside the
focus. That held, with one surprise: the corpus already owned the extraction system
(`llm-extracted-entity-graph`, forged 2026-09-03 from one source), which moved the
largest system from "forge" to "reconcile counterpart" before a single entry was drafted.

**Fetches: 0 of 3.** First-party account in repository form; every claim corroborated
corpus-internally or by the tree's own tests and measurements.

## Declared focus (round 27), answered

1. **Promotion read on a contested home.** Tried once, on R1 (contradiction as an
   upstream error signal; home contested between `agent-memory` and `triage-queues`).
   One file read - the triage-queues opening - settled the *home* (an inbox whose every
   verdict is a repair is a triage queue, and the hitl-approval boundary says a repair is
   the resolution, not a lock) but did not promote the *row*: the mechanism spans the
   queue's cap-and-aggregate rule and the reasoner's derived-versus-asserted precedence,
   and writing it needs both files open plus the source's per-predicate cap number,
   which the record itself calls a guess. Recorded as a lead with the discriminator. So:
   the read works for the home and is not sufficient for the row when the row is a
   mechanism rather than a boundary case. Report: 0 of 1 promoted; the read cost one
   file and was worth it for the home alone.
2. **Falsifier grep before the record.** Done: the concept map ran before any design
   entry was written, and it changed what got written - `llm-extracted-entity-graph`
   surfaced on the first pass, so system X's six entries were drafted as *counterparts to
   an existing subject* with `corpus:` lines pointing at its techniques, not as a forge
   brief. Two entries (X3, X4) went straight to `partial` with their promoting question
   written, instead of being scored NONE and re-derived at Phase 6.
3. **Single-source debt named on day one.** Both techniques are single-sourced on this
   tree and say so in their subject notes with a counterpart: `pending-beliefs-live-apart`
   got its second sighting the same day through the apply step (the personas companion
   had two of its three rules); `record-axis-predicate` was single-sourced for about an
   hour - the apply step's seam search found politicas' as-of lens, an independent
   implementation in another language over another store that contributed a section the
   source tree did not have (the three absences). Its standard-tier counterpart for the
   reconcile lane is still the system-versioned-table clause of the SQL standard. The
   handoff names the entity-graph subject's own debt too.

## Registry as a knowledge base: the comparison the operator asked for

Read as a peer, this tree and this registry are the same kind of object - a store of
claims with provenance, a review lane, a bench, and a discipline for saying what is
built - and they disagree in four places worth recording:

- **Their decision records are our source notes plus our subject proposals**, with one
  rule we lacked and now carry: the implementing change moves the status line. Their
  audit of "said versus done" (record 0016) found 3 of 15 lagging; ours found 5 of 17.
  Same failure, same fix, applied to ourselves this run.
- **Their "where this stage drops things" sections are our scorecard funnel**, but
  theirs are per stage in the pipeline document with the reason codes counted in a table
  (`extraction_drops`, eleven codes); ours are per run. A per-stage drop table for
  intake - what Phase 3 extracted that Phase 5 never scored, what Phase 6 dropped - would
  be the equivalent, and the untriaged table is its first column.
- **Their bench refuses an answer key the model has memorised** (the Holmes corpus "must
  not" have one). Our eval-harness subject does not say this; it is banked untriaged
  (X6) rather than landed because only one source says it and the subject was not opened.
- **Their ledger is bitemporal and ours is not.** `verified_on` is a recorded-clock
  stamp with no invalidation; a technique that was corrected has its history in git, not
  in the document. Record 0019's argument applies to us in the small: "what did the
  corpus say in August" is answerable only by checkout. Not a landing - a note.

Two things they do that we do not, noted and not landed: the `docs/` root is gitignored
scratch except `decisions/` (research notes never enter the repository until they
settle); and every migration and test is named as a sentence, so a directory listing

## Rust craft: what the tree does that is worth learning from

The operator asked whether there are common best practices to learn. The honest answer:
the Rust is conventional and clean - `thiserror` in the core crate, `anyhow` at the
handlers, an orphan-rule wrapper for the framework's response trait, `strum` for
enum-string parity, `OnceLock` singletons for the sealer and runtime registries, runtime
`sqlx` queries so the build needs no database, `-D warnings` clippy and `fmt --check` in
the pipeline, zero `unsafe`, `lto = "thin"` and `strip` on release. None of that is a
finding. What is worth learning sits at the seams the language cannot check:

1. **SQL is invisible to the compiler, and the tree treats that as a discipline, not a
   complaint.** Predicates composed in one module; `IS DISTINCT FROM` after the null
   incident; `LEFT JOIN` plus fallback after the nullable-predicate change; and the rule
   "DB tests are not optional when SQL strings change", enforced by a pipeline job that
   fails when the database is missing. Landed (amendment E6, application E3, technique L1).
2. **Failure direction decides storage shape.** Three separate tables (`pending_facts`,
   `derived_facts`, `rejected_facts`) exist because a forgotten read must fail toward
   silence. Landed (technique M).
3. **A marker type in the cause chain crosses a crate boundary a typed enum cannot.**
   `Terminal` plus `chain().any()`. Landed (application E4).
4. **Tests are named as the sentence they guard and say what would make them
   meaningless** - "this test must be red on the old implementation, or it proves
   nothing" (`a_disambiguator_follows_the_ontology.rs`). A catch on
   `negative-control-tests`, and the shape the personas paired test copied.
5. **Comments carry the counterfactual with the issue number.** The workspace `Cargo.toml`
   explains why `gzip` is not optional (62 s → 21 s on one embedding response) and why
   `bigdecimal` is the only reading of `DECIMAL`. A catch on the guidance practice.
6. **Credentials sealed at rest with an idempotent prefix and a boot-time backfill**, key
   outside the database, constant-time compare from `subtle`, SHA-256 rather than a
   salted hash for a high-entropy token because a per-row salt defeats the unique index.
   `seal-and-key-hierarchy` likely owns it; not opened (budget).
