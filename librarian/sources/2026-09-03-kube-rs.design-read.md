### System A — Controller runtime

**A1 · `D-R1` The reconciler is told *that* an object changed, never *why*.**
- **decision**: every trigger — the object's own watch, an owned child's watch via owner-reference traversal, a custom mapping, a bulk `reconcile_all_on` — collapses into one `ReconcileRequest { obj_ref, reason }`, and `reason` is **excluded from `Hash`/`PartialEq`**, so an object occupies exactly one scheduler slot no matter how many distinct reasons fired.
- **forces**: watch streams lose events (the desync in A2/B1 is designed for, not exceptional). If the reconciler could branch on the reason, a lost event would mean a lost branch, and correctness would depend on delivery. Erasing the reason makes delivery an *optimisation*.
- **buys**: the reconciler is forced to be idempotent and full-state — testable by handing it the same object twice and asserting one converged result.
- **rejects**: an event-typed handler (`on_create` / `on_update` / `on_delete`). The docs say it in the tree's own words: *"This mapping mechanism ultimately hides the reason for the reconciliation request, and forces you to write an idempotent reconciler."*
- **where**: `kube-runtime/src/controller/mod.rs:628-635` `[V]`; `:298-302` (the `NOTE:` that reason is ignored for comparison, so only *the first* reason is stored) `[V]`; `:334-380` (`ReconcileReason`, kept for **tracing only**) `[V]`; `:109-120` (`Action::await_change` warns that disabling requeue forfeits this safety) `[V]`.
- **stage**: trigger → queue, before the scheduler.
- **corpus: MODELS** — `client-architecture/realtime-events` (*"Push is an optimization over refetch — never the source of truth"*) and `llm-agent/orchestration/fleet-orchestration:106,125` (*"signals first, sweeper second… the sweeper fills exactly the gaps signals leave"*), with `backend-platform/work-execution/scheduling:67` supplying the edge-trigger half. All three opened `[V]`. **A catch** — though the *reason-erased-by-`Hash`* construction is a boundary case none of them states.

**A2 · `D-R2` One slot per key: earliest-wins dedup, in-flight exclusion, trailing debounce, global cap.**
- **decision**: `Scheduler` = `DelayQueue` + a `HashMap` of scheduled entries. Re-scheduling a key already queued **mutates the existing entry to the earlier of the two times** (`reset_at`) rather than enqueueing a second copy; a key whose equal is currently executing is parked in a `pending` set instead of running concurrently; `debounce` is *added* to the expiry so a churning key coalesces; `Runner` caps total parallel executions independently of all that.
- **forces**: a controller watching a hot resource receives bursts (the object, five related-object events, an error-policy retry) that all mean *converge this key*. Running them in parallel races the reconciler against itself; running them serially without dedup does N times the work for one outcome. The two limits are genuinely independent: *"despite concurrency, a controller never schedules concurrent reconciles on the same object."*
- **buys**: work proportional to the number of *changed keys*, not of events, with per-key mutual exclusion that no reconciler has to remember to take.
- **rejects**: an unbounded channel plus a semaphore (no dedup, no per-key exclusion). Also rejects an unclamped deadline: `time.min(max_schedule_time())` exists because an unclamped one **panicked** the delay queue in the field, with the issue cited inline.
- **where**: `kube-runtime/src/scheduler.rs:36-60` (the three collections + the debounce doc) `[V]`; `:78-112` (earliest-wins, clamp at `:86-88`) `[V]`; `:114-139` (`pending` / `can_take_message`) `[V]`; `controller/runner.rs:20-25, 47-57` `[V]`; `controller/mod.rs:605-617` (the concurrency doc) `[V]`.
- **stage**: queue → execution.
- **corpus: PARTIAL** — all three forces exist; none are composed. `concurrency-guards` owns one-flight-per-key (*"Two operations are duplicates because the design says so, not because their code paths happen to collide"*) `[V]` and `admission-queue` owns finite-slot occupancy `[V]`, so the concurrency concept came back MODELS-composed-across-two. But the **requeue + rate-limit + per-key-dedup as one queue** concept came back PARTIAL: `delivery-guarantees` has counted, bounded retries escalating to a dead-letter lane `[V]`, `retry-backoff` has bounded jittered delay `[V]`, `concurrency-guards` has the key — and **no subject owns "one rate-limited queue whose unit is a deduplicated key"**. Promoting question executed in §6.

**A3 · `D-R3` Deletion is blocked by a marker on the record, removed only after cleanup, under an optimistic-concurrency guard.**
- **decision**: `finalizer()` is a two-branch state machine over `FinalizerState { finalizer_index, is_deleting }`. Not-deleting + no marker → **add the marker and return `await_change()` without applying**, because the patch itself triggers the next reconcile. Deleting + marker present → run `Cleanup` and **short-circuit on failure so the marker stays**. Both patches are JSON Patch with a **`Test` operation first**: the add tests the current finalizer list (the platform does not dedupe finalizers, so a concurrent add must fail and retry); the remove tests that index *i* still holds **our** name — *"`Test` ensures that we fail instead of deleting someone else's finalizer."*
- **forces**: several independent controllers hold markers on the same record concurrently, indexed **positionally**, with no transaction available; and the record must not vanish while a controller still owns external resources it created.
- **buys**: the stated guarantee — *"If `Event::Apply` is ever started then `Event::Cleanup` must succeed before the Kubernetes object deletion completes"* — with the cost stated just as plainly: *"Object deletes will get stuck while the controller is not running, or if `cleanup` fails."*
- **rejects**: reacting to a delete *event*. `watcher::Event::Delete`'s own doc: *"This should not be used for managing persistent state elsewhere, since events may be lost if the watcher is unavailable. Use Finalizers instead."*
- **where**: `kube-runtime/src/finalizer.rs:56-73` (the state) `[V]`; `:75-120` (the 13-step expected flow, the guarantees, and the assumption that both branches tolerate re-execution *"even if previously cancelled"*) `[V]`; `:150-176` (remove; `Test` rationale at `:161-163`) `[V]`; `:184-222` (add; no-dedup rationale at `:199-201`) `[V]`; `kube-runtime/src/watcher.rs:58-62` `[V]`.
- **stage**: inside the reconciler, wrapping every other action.
- **corpus: NONE.** Nearest neighbours, both opened `[V]`: `operations/service-operations/node-boot-and-declarative-bootstrap` uses the word — *"the finalizer is deferred at the point of acquisition"* — for **process teardown**, a different mechanism; `backend-platform/data-layer/sync-replication` has *"is reaped only when every replica has provably seen it"*, which is quorum-of-observers, not a named dependent confirming cleanup. Neither models the load-bearing force: **a record that stays alive and un-deletable, carrying one marker per owner, until each owner confirms cleanup — with the deadlock that a stuck owner wedges deletion forever.** All nine corpus hits for `finalizer` are `defer`-style. **HOME IF NEW: `declarative-resource-lifecycle`.**

**A4 · `D-R4` A child's change is mapped through an ownership edge to the *parent's* key.**
- **decision**: `Controller::owns(child_api)` traverses each child's `owner_references` and enqueues **the owner's** key. The mapper `mem::take`s the child's metadata rather than deep-cloning `ObjectMeta` *"just to read two fields."* `watches()` generalises the same machinery to an arbitrary child→parent mapping function.
- **forces**: the reconciler's unit of work is the parent (it owns the whole desired subtree), but events arrive on children. Without the edge, either the reconciler polls, or every child handler must know how to find its parent.
- **buys**: a child drifting or being deleted out from under the controller re-enqueues the parent, which re-converges the subtree. Ownership is data **on the child**, so the index needs no separate registry and survives a controller restart for free.
- **rejects**: a child-level handler; and re-reconciling everything on any child change (`reconcile_all_on` exists for that, is opt-in, and is separately reasoned).
- **where**: `kube-runtime/src/controller/mod.rs:243-267` (`trigger_owners`, allocation note at `:256-257`) `[V]`; `:186-240` (`trigger_others` / `watches`) `[V]`; `:1013-1085` (`owns` / `owns_stream`) `[V]`; `reflector/object_ref.rs` (`ObjectRef::from_owner_ref`) `[V]`.
- **stage**: trigger construction, before the queue.
- **corpus: NONE.** The map's top three were all *domain* graphs (`civic-knowledge-graphs`, `branching-narrative-graph-validation`, `visual-script-to-code-transpilation`) — none is an ownership edge used to enqueue work `[V]`. ### System B — Watch and reflector

**B1 · `D-W1` Desync is a *state* in an explicit FSM, not an error path.**
- **decision**: the watcher is a `Stream` over `enum State<K> { Empty, InitPage{..}, InitialWatch{..}, InitListed{resource_version}, Watching{resource_version, stream} }`, advanced by one `step` function returning `(Option<item>, next_state)`. Every event carries the version forward. **A 410 → `State::default()`, i.e. a full re-list from scratch**, at both points it can arrive; any other watch error keeps the version and retries the watch; a missing version is a hard `NoResourceVersion` that also resets. The consumer-visible protocol is `Init` → `InitApply*` → `InitDone`, explicitly so a downstream store can *"replace buffered store contents atomically."*
- **forces**: the server retains a bounded change window; a consumer that falls behind it cannot be caught up incrementally, and **silently continuing from a stale cursor produces a cache that is wrong rather than late.** There is no third option.
- **buys**: bounded staleness with an explicit, observable resynchronisation — and a state machine unit-testable without a server.
- **rejects**: reconnect-and-continue; and list-then-watch with no relist path. It also declines to *replace* the old strategy with the new one: `InitialListStrategy::{ListWatch, StreamingList}` both remain, because streaming lists need a server feature gate, and `page_size: Some(500)` is pinned to the reference client's default with the upstream line cited inline.
- **where**: `kube-runtime/src/watcher.rs:114-146` (the FSM; the fall-out-of-the-window comment at `:120-126`) `[V]`; `:610-623` and `:686-700` (*"HTTP GONE, means we have desynced and need to start over and re-list :("*) `[V]`; `:660-681` (version advanced per event; empty version resets) `[V]`; `:167-215` (`ListSemantic::{MostRecent, Any}` — a stated consistency-vs-server-load trade, with the argument for congested controllers) `[V]`; `:53-84` (the `Event` protocol) `[V]`; `:269-277` (defaults) `[V]`.
- **stage**: transport → event stream.
- **corpus: PARTIAL** — `backend-platform/data-layer/sync-replication` models the cursor half strongly: *"**Durable**: the cursor survives restart, because the alternative is re-delivering everything"*, plus tick + lossy wake + persistent dirty mark and a bounded first backfill `[V]`. The forced-full-resync half exists **only one layer down**, at `sync-replication/techniques/tombstone-propagation.md:104` (*"offline window, after which a replica must full-resync"*), and the golden path does not state it. Promoting question in §6.

**B2 · `D-W2` The local replica *is* the read model — and the corpus argues the opposite, under different forces.**
- **decision**: `reflector()` observes the watch stream and maintains an `Arc<RwLock<HashMap<ObjectRef<K>, Arc<K>>>>` that the rest of the program reads directly as application state, passing the stream through unmodified. Writes accumulate in a `buffer` during `Init` and are **swapped in at `InitDone`** (`mem::swap`, then the old map is *dropped* rather than `clear()`ed — *"preferred over `self.buffer.clear()`, as clear() will keep the allocated memory for reuse"*). The module docs then spend a whole section on the consequence — *"A reflector often constitutes one of the biggest components of a controller's memory use… ~2000 pods… a couple of hundred megabytes"* — and give three named mitigations: metadata-only watch (*"60% reduction seen for `Pod`"*), `Event::modify` to drop `managedFields`/annotations/status, and selectors.
- **forces**: reconcilers need whole-object reads at high frequency; per-read fetches would flood the server. The replication is only *safe* because the source publishes a totally-ordered, resumable, compacting change log with an explicit desync signal (B1). Remove that property and the decision inverts.
- **buys**: O(1) local reads of a snapshot consistent as of a known version, plus the readiness signal in B3.
- **rejects**: read-through caching with invalidation.
- **where**: `kube-runtime/src/reflector/mod.rs:18-30` `[V]`; `:63-90` (the memory section) `[V]`; `reflector/store.rs:19` `[V]`; `:107-140` (`apply_watcher_event`; atomic swap at `:129-135`) `[V]`; `:247-300` (`state` / `state_filter` / `state_filter_selector`, added in 4.0.0 *"to allow more efficient slicing of the locked cache"*) `[V]`.
- **stage**: event stream → application state.
- **corpus: NONE — and this is a *conflict*, not a hole.** `client-architecture/realtime-events` states the opposing rule in as many words: **"The durable answer is *invalidation, not replication*."** `[V]` `client-fetch-cache` owns the cache half (keys, SWR, in-flight dedup, warm remount) but its refresh channel is a refetch, not a change stream `[V]`. Neither models these forces, because neither contemplates a source that publishes a resumable ordered log with a desync signal. **A discriminator to name, not a duplicate to write** — Phase 7's rule is to state the boundary in prose on the side you are writing. It is the highest-altitude, cheapest landing in this run.

**B3 · `D-W3` Cache completeness is a one-shot readiness gate the controller waits on; one store fans out to N consumers.**
- **decision**: the `Writer` holds a `DelayedInit<()>` initialised **exactly once**, at the first `InitDone`; `Store::wait_until_ready()` awaits it and fails with `WriterDropped` if the writer dies. The applier wires it in as `Runner::delay_tasks_until(store.wait_until_ready())` — the scheduler keeps **accepting and coalescing** work while the cache fills, and **no reconcile runs against a partial cache**. Separately, `Writer::new_shared(buf_size)` attaches a broadcast dispatcher so several controllers share one watch and one store: the buffer releases an object *"only when all subscribers have seen it"*, senders apply backpressure when full, and an inactive receiver is retained so the channel survives having zero live subscribers.
- **forces**: a reconciler reading a half-filled cache concludes its children are missing and **recreates them** — a correctness bug, not a latency bug. And N controllers over one resource means N watches on the server unless the stream is shared.
- **buys**: a startup barrier with the queue already warm; one boundary handshake for N in-process consumers, with bounded backpressured buffering.
- **rejects**: a sleep-on-boot; a per-controller watch.
- **where**: `kube-runtime/src/reflector/store.rs:33-34, 47, 137-140` (ready set at `InitDone`) `[V]`; `:196-215` (`wait_until_ready`, `WriterDropped`) `[V]`; `:58-105` (`new_shared`, `subscribe`) `[V]`; `reflector/dispatcher.rs:17-59` (backpressure and no-active-receiver notes at `:40-46, 50-54`) `[V]`; `controller/mod.rs:485-490` `[V]`; `utils/delayed_init.rs` `[V]`; `examples/shared_stream_controllers.rs` `[V]`.
- **stage**: startup barrier; and stream fan-out.
- **corpus: MODELS.** `client-architecture/realtime-events`' `subscription-lifecycle` is structurally this pattern — *"one native listener per event name, fanned out to N in-process consumers"*, with bounded buffering for events arriving before the first consumer and reaping of the native listener when the last leaves `[V]`. The readiness half is carried by `background-jobs` (*"A dead supervisor with N registered loops looks exactly like a healthy quiet system"*) and `health-checks` (*"a green from an hour ago is a fact about an hour ago"*) `[V]`. A catch. The **one-shot, never-re-armed** property — a later relist does *not* un-ready the store — is a boundary worth an amendment.

### System C — Client config and transport

**C1 · `D-C1` Config resolution is an ordered chain that keeps *both* failures and names the likelier user error as the cause.**
- **decision**: `Config::infer()` tries the operator's config file (`$KUBECONFIG`, else the default path) and, only on failure, an ambient workload identity from environment variables plus a projected token file; then applies debug overrides. When both fail, `InferConfigError` carries **both**, and `#[source]` is placed on the file error with the reason written into the struct: *"We can only pick one source, but the kubeconfig failure is more likely to be a user error."* Three explicit in-cluster constructors exist because the env-var form *"matches the behavior of the official Kubernetes client libraries"* while the DNS form is a fallback. Below that, `ConfigExt` decomposes the result into **composable tower layers** (`base_uri_layer`, `auth_layer`, `extra_headers_layer`, a TLS connector per stack) behind a **sealed** trait; the token file is re-read and the in-cluster CA bundle reloaded **on rotation** as of 4.0.0.
- **forces**: one binary runs on a laptop against an operator's file and inside the cluster against an injected identity, and must not need a flag to tell which; both credential materials rotate under a running process.
- **buys**: one `infer()` for both environments, an error naming both attempts, and an auth/TLS/retry stack a caller rebuilds layer by layer instead of forking the client.
- **rejects**: an operator-chosen environment flag; a monolithic client struct with branches.
- **where**: `kube-client/src/config/mod.rs:23-31` (both errors + the `#[source]` rationale) `[V]`; `:203-229` (`infer`) `[V]`; `:231-263` `[V]`; `:33-111` (a 14-variant `KubeconfigError` plus `LoadDataError` — one variant per distinguishable cause) `[V]`; `:139` (token-file reload) `[V]`; `client/config_ext.rs:17-40` (sealed trait) `[V]`; `client/retry.rs:8-31` (the whole `ServiceBuilder` stack, as a doc example) `[V]`; `CHANGELOG.md` 4.0.0 §Config / §Client `[V]`.
- **stage**: process boot, before the first request.
- **corpus: PARTIAL.** Three of four forces are modelled elsewhere: absent-vs-malformed and per-variable blast radius by `optional-dependency-degradation` (*"An absent configuration value degrades. A malformed configuration value fails fast at boot"*) `[V]`; inherited-default-override by `settings` `[V]`; workload-credential consumption by `security/authorization`'s `machine-credential-consumption` `[V]`. **Not modelled: the ordered resolution chain itself** — explicit path → environment → ambient identity — with stated precedence and a "which layer supplied this value, and what did the others say" diagnostic. Nearest structural analogue, `agent-instruction-files`' `single-source-topology`, governs instruction text rather than credentials. **Not load-bearing** (removing it changes a feature, not the system's shape), so it does **not** count toward the NONE tally; it is a technique candidate. Promoting question in §6.

**C2 · `D-C2` Retry is a transport layer with a closed retryable set and a server-obeying delay; the watch keeps its own idle timeout.**
- **decision**: `RetryPolicy` implements the transport stack's `Policy` trait and retries **only** 429 / 503 / 504, with exponential backoff from `min_delay` to a capped `max_delay` and a bounded attempt count; `server_aware` honours the server's `Retry-After` over the computed delay. Enabled **by default** for the client in 4.0.0. Separately and deliberately, the **global read timeout was removed** in favour of a per-watcher idle timeout, and `Config::timeout` is documented as capped at 295s *"due to inherent watch limitations"*, with the upstream issue cited.
- **forces**: a long-poll watch and a point read have opposite timeout semantics — a global read timeout correct for a `get` kills every watch, and one correct for a watch hides a hung `get`. And a busy or still-initialising server communicates its own recovery window, which a client-side exponential guess overrides for the worse.
- **buys**: retries that cannot amplify a client error (a 4xx that is not 429 is never retried), and a delay the server chose whenever the server offered one.
- **rejects**: retry-on-any-error; one global timeout; ignoring `Retry-After`.
- **where**: `kube-client/src/client/retry.rs:50-80` `[V]`; `:8-31` `[V]`; `kube-runtime/src/watcher.rs:224-232` (the 290s/295s note) `[V]`; `utils/stream_backoff.rs:9-42` (stream-level backoff: reset on any `Ok`, **close the stream** when the policy gives up) `[V]`; `CHANGELOG.md` 4.0.0 §"Retry and Timeouts" `[V]`.
- **stage**: HTTP transport, beneath every API call.
- **corpus: MODELS.** `backend-platform/resilience/retry-backoff` was the strongest match in the entire probe set — four classes with contracts, *"Classify first. The failure's class — not the caller's impatience — decides whether to retry"*, jitter as herd control, a global retry budget against cross-layer amplification, five terminal states plus a non-terminal *suspended* `[V]`; `error-handling` supplies classification-on-structure-never-prose `[V]`. A catch, with two dated facts to cite **into** it (§5).

### System D — Typed and dynamic resources

**D1 · `D-T1` Writes declare an owner per field, and conflict is the default.**
- **decision**: the recommended write is an apply-patch carrying a **required** `field_manager`; the server records which manager owns which field path and **rejects** a write that would take a field another manager owns unless `force: true`. `PatchParams::validate` enforces client-side that `force` is meaningless without an apply patch and that a manager name is ≤128 characters — **the illegal combination fails before a request is sent.** `Api::entry` layers a `HashMap::entry`-shaped get-or-create / get-and-modify on top, with an explicit `commit` and a `Dirtiness` flag so an unmodified entry is not written at all.
- **forces**: several independent controllers, plus humans, plus a deployment tool, all write the same record. Last-writer-wins silently reverts other owners' fields; a lock does not exist here and would not survive a controller restart.
- **buys**: concurrent partial ownership of one record with no coordination, conflicts surfaced as errors rather than as data loss, and an explicit auditable act (`force`) to seize a field.
- **rejects**: read-modify-write over the whole object; a global write lock.
- **where**: `kube-core/src/params.rs:570-610` (the `Patch` enum; *"We recommend using (server-side) `Apply` patches"* at `:570`) `[V]`; `:634-652` (a distinct content type per variant) `[V]`; `:660-710` (`PatchParams`; `force`-requires-apply validation at `:687-690`; manager-length check at `:678-686`) `[V]`; `kube-client/src/api/entry.rs:1-59` `[V]`; `examples/crd_apply.rs`, `examples/secret_syncer.rs` `[V]`.
- **stage**: every write.
- **corpus: NONE.** Two of three forces are modelled well, and neither is this one: `recruiting/.../hiring-need-as-structured-brief` carries `per-field-provenance-stated-inferred-default` and `merge-that-never-regresses-a-stated-value` `[V]`; `llm-agent/prompt-and-context/agent-instruction-files:137` carries region ownership — *"fenced by markers, naming their generator, edited only by regenerating"* `[V]`. **Missing: ownership as durable server-side metadata, per field-path per writer; the conflict when two owners claim one path; and orphaning when a writer stops managing a field.** Corpus-wide `field manager` and `server-side apply` return 0 files. **HOME IF NEW: `declarative-resource-lifecycle`.**

### System E — CRD schema, CEL and admission

**E1 · `D-S1` The validation gate is an external network participant that blocks the write.**
- **decision**: the review type is *"both the input type received by admission controllers, and the output type admission controllers should return."* The response is `allowed: bool` plus a status consulted **only** on denial (*"This field IS NOT consulted in any way if 'Allowed' is 'true'"*), an optional **JSON Patch** that mutates the object before persistence, `audit_annotations`, and `warnings` with a documented budget (*"Limit warnings to 120 characters if possible"*). The request `uid` must be echoed, and `AdmissionResponse::from(&req)` is the only sanctioned constructor **so the echo cannot be forgotten**; `#[non_exhaustive]` keeps the struct additive. - **forces**: policy must bind **every** writer, including ones that predate the policy, so it cannot live in the clients; but the enforcement point is a separately deployed process, which puts a network hop and a new failure mode on the write path of the entire cluster.
- **buys**: one non-bypassable chokepoint that can both refuse and repair, with a machine-readable reason and a channel for non-fatal advice.
- **rejects**: client-side validation as the *enforcement* point (kept, but demoted to fast feedback — see the CEL note in §5); and a post-hoc controller that repairs bad objects after they land.
- **where**: `kube-core/src/admission.rs:37-57` (the dual-purpose review) `[V]`; `:244-275` (the three-response doc example: allow / deny-with-reason / patch-a-label) `[V]`; `:276-315` (`#[non_exhaustive]`, `allowed`, the not-consulted-when-allowed note, patch, audit annotations, warnings) `[V]`; `:316-370` (`from`, `deny`, `with_patch`; only JSON Patch is supported and the type says so) `[V]`; `examples/README.md` §admission `[V]`; `examples/admission_controller.rs`, `examples/admission_setup.sh` `[V]`.
- **stage**: server-side, between request and persistence.
- **corpus: NONE.** The *validating* half is modelled by `security/authorization` — *"moving the decision from N places that could forget to one place that cannot be bypassed"*, default-deny, fail-closed under doubt `[V]` — and the *mutating* half by `agent-runtime-assembly`'s `rewrite-before-the-gate` / `observer-and-mutator-surfaces` `[V]`. `admission-queue` is a false neighbour and its own text says so: it *"arbitrates occupancy of finite capacity"*, refusing by load rather than by validation `[V]`. `webhook-ingestion` is nearest by shape but is the *receiving* side of an async event and explicitly hands everything downstream of the mint point to other subjects — it has no synchronous verdict that blocks the sender's write `[V]`. **Missing: the gate as an externally registered, network-hop, latency- and timeout-bearing participant, whose availability policy — fail-open or fail-closed when the gate itself is down — is the central design question.** Corpus-wide `admission webhook` = 0 files. **HOME IF NEW: `declarative-resource-lifecycle`.**

**E2 · `D-S2` Two schema versions are served at once and converted on read — the corpus's stated posture is the opposite.**
- **decision**: `merge_crds(crds, stored_apiversion)` folds N single-version definitions into one multi-version definition with **exactly one** marked as stored and the rest not, refusing with a typed `MergeError` when inputs disagree on group, scope or kind, or when any input carries multiple versions. - **forces**: clients pinned to an old version must keep working while new clients use the new one; only one representation can be persisted, so every other version is a projection; and the projection must round-trip.
- **buys**: schema evolution without a coordinated client upgrade.
- **rejects**: forward-only migration of stored data, and the downgrade-is-impossible posture that comes with it.
- **where**: `kube-core/src/crd.rs:8-29` (`CustomResourceExt`, incl. the *declared*-vs-*registered* shortnames caveat at `:22-25`) `[V]`; `:31-57` (`MergeError`, six variants) `[V]`; `:59-90` (`merge_crds` and its stated assumptions) `[V]`; `kube-core/src/conversion/types.rs:32-43, 82-83, 131-190` `[V]`; `kube-core/src/version.rs:3-40` `[V]`; `examples/crd_derive_multi.rs`, `examples/crd-baz.yaml`, `examples/crd-qux.yaml` `[V]`.
- **stage**: schema publication, and every read of a non-stored version.
- **corpus: NONE — a second *conflict*.** `backend-platform/data-layer/migrations` states the opposing rule flatly: **"Downgrade is refusal, not tolerance."** `[V]` — forward-only, append-only, one-way-door over stored data. Nearest analogue to an upgrade-on-read ladder is `readiness-passports`' `fingerprint-provenance` `[V]`. **The landing is the discriminator — "who owns the readers?" — not a competing subject.**

**Structural facts, from `knowledge/software-engineering/taxonomy.json` `[V]`** — walked as `categories[] → subcategories[] → subjects[]` (**`categories` is a list**), with the cap read from `scripts/lib/taxonomy.mjs:39` (`MAX_CHILD_DIRS = 10`, enforced at all three levels `[V]`):

**The force-level argument, which is the real one.** All eight `service-operations` subjects share one stance: **an operator is looking at a service.** `health-checks` answers a human's *"does this work right now"*; `triage-queues` is explicitly an operator inbox whose healthy state is empty; `perf-instrumentation`, `usage-analytics` and `scoring-rubrics` produce numbers a person reads; `plan-entitlements` gates a tenant; `quorum-and-recovery-procedures` is stated as *"human-run rituals… a transaction whose participants are people"*; and `node-boot-and-declarative-bootstrap` — the nearest neighbour of all — **stops at one node's first start.** The territory this source occupies inverts that stance: **a machine continuously converging a fleet of declared records toward observed reality, with no operator in the loop.** The human writes desired state and leaves, and every mechanism in §3 exists to make that absence safe — idempotence because delivery is lossy, markers because the machine may die mid-cleanup, per-field ownership because writers do not coordinate, a gate because clients cannot be trusted to validate themselves. That is a different discipline, not a larger `service-operations`.

## 6. Promoting questions, executed

Per the v2 rule, **every `partial` row gets its promoting question written, answered with one file read, and advanced if the answer promotes it.** Three design rows and two claim rows were `partial`. All five questions were executed.

**DC7 (A2) — question:** *Does `concurrency-guards`' golden path state the **queue-time** force — that a key already scheduled must be coalesced to the earliest of the two times rather than enqueued twice — or only the **execution-time** force that two in-flight operations on one key must not overlap?*
**Read:** `concurrency-guards.md` `[V]`. **Answer:** execution-time only. Its load-bearing line is about *defining* a duplicate — *"Two operations are duplicates because the design says so, not because their code paths happen to collide"* — and its mechanism is one-flight-per-key with a key-granularity failure analysis (too broad → mysterious serialisation; too narrow → decorative guard). There is no rule about what a queue does with a second arrival for a key already waiting, and `admission-queue` refuses by capacity rather than by identity. **PROMOTED to `real gap`.** Lands as a technique in `concurrency-guards`: *coalesce at the queue, not at the worker* — earliest-wins on re-schedule, park-don't-run when the equal is in flight, and debounce as an added delay rather than a replacement one.

**DC8 (B1) — question:** *Does `sync-replication`'s golden path state that a cursor which has fallen outside the source's retained window forces a **full resynchronisation** — or only that the cursor is durable?*
**Read:** `sync-replication.md` and `techniques/tombstone-propagation.md` `[V]`. **Answer:** the golden path states durability, the tick + lossy-wake + persistent-dirty-mark pattern, and a bounded first backfill, and stops there. The forced-resync sentence exists **one layer down and about a different concern** — `tombstone-propagation.md:104`'s offline window, i.e. a replica that missed deletions, not a consumer whose cursor expired. **PROMOTED to `real gap`.** Lands as a technique in `sync-replication`: *treat desync as a state, not an error* — the cursor's expiry is a distinguishable server response, its only correct handling is a full re-read, and the consumer protocol needs a "the world you knew is being replaced" marker so downstream caches swap atomically instead of merging.

**DC9 (C1) — question:** *Do `optional-dependency-degradation` or `settings` state a **precedence order across configuration sources** — or only per-value semantics inside one source?*
**Read:** both golden paths `[V]`. **Answer:** per-value only. `optional-dependency-degradation` governs one variable at a time (*"An absent configuration value degrades. A malformed configuration value fails fast at boot"*) and probes the grant rather than the declaration; `settings` governs inherited-default-override **within one store**, over a closed registry. Neither states an ordered chain across independent sources, nor the provenance diagnostic that makes a chain debuggable. **PROMOTED**, at lower impact than the other two — it is a technique in `settings`: *a resolution chain that reports which layer answered*, with the corollary this tree demonstrates: when the whole chain fails, keep every layer's failure and choose the `#[source]` by which one a human most likely caused.

**DC11 (B3) — question:** *Does any golden path state that a **cache's completeness**, as distinct from a process's liveness, is a readiness signal that gates work?*

#### Why a subject and not four amendments

Because the four share one premise, and each is unsound without the others. **The record is the coordination medium.** There is no lock, no transaction and no coordinator; several independent writers converge on the same record, and every mechanism here is a contract *written onto the record* that makes their independence safe: a marker says *do not vanish yet*, an edge says *whose work this change is*, a field owner says *whose value this is*, a gate says *what may be written at all*. Land them separately and each becomes a curiosity attached to whichever subject was nearest; land them together and the premise is stateable, which is what a golden path is for.

Two independent reads reached the same grouping — the design record grouped by shared home-if-new, and a corpus sweep run on concepts alone, without seeing that grouping, closed by naming the identical set as *"one coherent unlanded mechanism family."*

#### Proposed techniques, each with the decision rule it must carry

1. **`deletion-blocked-until-dependents-confirm`** — a record carrying an owner's marker cannot be removed; the owner removes its own marker only after cleanup succeeds, and a failed cleanup **keeps** the marker. Decision rule: *the marker goes on before the first side effect, never after* — and the write that adds it is itself the trigger for the next pass, so nothing is applied in the same pass that claims custody. Must carry: the deadlock (a marker whose owner is gone blocks deletion forever) and the two operator escapes; the positional-index hazard when markers are a list (the guarded compare-and-remove that keeps one owner from deleting another's); and the requirement that cleanup be re-runnable, including from a cancellation point.
2. **`ownership-edges-that-enqueue-the-parent`** — the dependent carries the identity of the thing responsible for it, and a change to the dependent enqueues **the parent's** unit of work, never its own. Decision rule: *the edge lives on the child as data, so the index survives a restart and needs no registry*. Must carry: the choice between a declared edge and a computed mapping; why the enqueued unit is the parent even when the parent is unchanged; and the boundary against a static dependency graph (`client-state`'s `store-dependency-topology`), which is compile-time and answers a different question.
3. **`per-field-write-ownership`** — a writer names itself, the store records which paths it owns, and a write that would take another owner's path **fails** unless the writer explicitly seizes it. Decision rule: *conflict is the default and seizure is an auditable act; last-writer-wins is the thing this replaces*. Must carry: what happens to a field whose owner stops managing it; why the writer's name must be stable across restarts and deployments; and the client-side validation that makes an impossible combination unrepresentable before a request is sent.
4. **`synchronous-gate-before-persistence`** — an externally registered participant sees every write before it lands, and may refuse it with a reason or **rewrite** it. Decision rule: *the availability policy of the gate is the design question, not its logic* — a gate that fails closed can halt every writer in the system, and one that fails open is not an enforcement point; choose per rule class and state the choice. Must carry: the correlation identifier that must be echoed and the constructor discipline that makes forgetting it impossible; the advisory channel (non-fatal warnings) as distinct from refusal; and the boundary against `webhook-ingestion`, which is the *receiving* side of an asynchronous event and has no verdict that blocks a sender.

#### Boundaries it must NOT absorb

- **Durable job state, leases and at-least-once delivery** — `job-coordination` and `delivery-guarantees` own them, and correctly: every queue in the witnessing tree is in-memory, which is a real boundary and not an oversight.
- **Leader election and single-active exclusivity** — `concurrency-guards` owns it (`leadership-is-the-lock`). State the *inverse* here: this subject assumes concurrent writers and refuses to solve them by electing one. The witnessing tree ships **zero** leader-election code `[V]`, and that absence is the argument.
- **Retry classification** — `retry-backoff` owns it.
- **The convergence loop itself and its queue** — reserved for the sibling subject `convergence-loop-and-requeue` (§4). This subject is about contracts on the record; that one is about the loop that reads them.
- **The cache and its resynchronisation** — reserved for `watch-cache-and-resync` (§4).
- **Packaging and rollout of cluster workloads** — `deployment-contract` owns it.

#### Open questions the drafter must decide, not discover

1. **Does the deletion-marker technique generalise past a store that supports it natively?** The fleet's nearest analogue is a soft-delete column plus a reaper. Decide whether the technique's `use_when` admits that shape or names it as the degraded case — and say which, because the answer decides whether three fleet projects can apply the subject at all.
2. **Is `per-field-write-ownership` one technique or two?** Recording ownership and *resolving* a conflict may be separable. Decide from the evidence, not from symmetry.
3. **Where does the `entity-lifecycle` subject (`operations/governance-and-records`) end and this one begin?** Both are about a record's states over time. Proposed discriminator, for the drafter to accept or replace: `entity-lifecycle` governs the states a record moves through **for the product's sake**; this subject governs the contracts that let **independent writers** move it safely. Open it before drafting.
4. **Should `synchronous-gate-before-persistence` live here or in `security/authorization`?** It is a chokepoint, and `authorization` owns chokepoints. Proposed answer: it lives here because the mutating half and the gate's own availability are not authorization concerns — but the drafter should read `authorization`'s golden path and **override this spec if that argument does not survive contact**.

One repository is thin evidence for a whole subject, and this one is a single ecosystem's implementation of an ecosystem's conventions — the risk of writing conventions as if they were principles is exactly what a forge wave's expert-first phase exists to test. **It is not, however, a reason to wait**: the neighbours are open, the boundaries are argued, and the placement is verified. **Where the fleet is likely ahead of this tree** (for the study's inverse list): kube has **no** durable state — every queue is in-memory and a restart replays from a full relist, which is only safe because the apiserver is the source of truth. A project whose queue must survive a crash cannot copy R8 wholesale, and pumper's durable-queue design answers a force kube never faces.

- **`tracklight` — ADMITTED, and the clearest case.** Its `scope.does` already says *"serve an operator API"* and its `does_not` bars only product UI, agent runtime and other domains, so nothing excludes cluster operations — yet the chart it ships has no RBAC, no security context, no replica guard, calls itself *"UNVERIFIED"*, and deploys everything except the worker that does the work.
- **`kp` — ADMITTED, narrowly.** `scope.does` names *"self-hostable (Docker)"* and one organisation per install, which admits the Kubernetes path it already ships; the unbuilt part is not a capability but the uncovered remainder of its own gate — RBAC, ServiceAccount, NetworkPolicy and PodDisruptionBudget are absent from both the chart and the 12 policies.
- **`pumper` — ADMITTED, and it is the one with the deepest need.** Its scope bars only a UI, agent orchestration and unrelated domains, and it holds the fleet's most complete reconcile/lease/backoff/dedup machinery with **no deployment artifact of any kind** and no enforcement of the single-scheduler assumption its own overlap guard implies.
- **`personas` — EXCLUDED by its own text.** `does_not` bars *"CI/CD or deployment pipelines for other repositories"* and `does` fixes it at local-first, one operator per install; a cluster-operations capability contradicts both, so the only admissible adjacent work is the in-process kind already listed as candidates (`admission-queue`, `concurrency-guards`, `job-coordination`).
- **`politicas` — ADMITTED weakly, and not for Kubernetes.** Nothing in its scope mentions deployment, and it already carries a hard single-instance invariant enforced only by a comment in `fly.toml:4-7`; what its scope admits is **kp's gate shape applied to its own artifact**, not a cluster.
- **`gravitone` — UNDETERMINED, and that is the finding.** It has no manifest, no scope block and no fleet-map row, so there is no text to reason from — while being the only fleet project running an autoscaler against a third-party CRD; the actionable gap is the missing manifest (L5), not a missing capability.

**Directions not proposed** (recorded per the rule, so the next fleet-map sweep need not re-derive them): `personas` — excluded by scope text, do not re-propose. `gravitone` — blocked on L5, return when it has a manifest. `politicas` — admitted but out of dimension; route to `deployment-contract`, not to the new subcategory.
