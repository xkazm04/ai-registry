## Design record

Product names are allowed here; the record is the tree's own terms. `corpus:` is the
routing count: NONE means no golden path in the corpus states this decision's forces.

### D1 - Metadata travels with the tensor

- **decision:** the core data type is `MetaTensor`, a `torch.Tensor` subclass mixing in
  `MetaObj`: an affine matrix, a metadata dict, and two operation stacks
  (`applied_operations`, `pending_operations`) ride on the tensor through every
  operation; a global `set_track_meta(False)` returns plain tensors for callers that want
  none of it; arithmetic copies metadata from the first operand, shallow for batches.
- **forces:** a medical image is a sample of physical space - spacing, orientation,
  origin - and every spatial operation must update that frame or downstream code
  computes in the wrong coordinates. Before 1.0 the frame rode in a parallel dictionary
  keyed by naming convention (`image` beside `image_meta_dict`), which desynchronised the
  moment any transform forgot to update both.
- **buys:** any operation, anywhere in the pipeline, can read the current frame and the
  history that produced it; inversion (D2) and lazy composition (D3) become possible
  because the tensor knows what has been done to it.
- **rejects:** the parallel metadata dict (deprecated, still readable); a wrapper object
  that is not a tensor (would break every engine API).
- **where:** monai/data/meta_tensor.py:90 (class docstring, copy rules);
  monai/data/meta_obj.py:33 (`set_track_meta`), :66 (`MetaObj`); docs/source/modules.md
  "monai.data.MetaTensor"; whatsnew_0_9 "MetaTensor API preview", whatsnew_1_0.
- **stage:** data load - the reader's `get_data` returns the pair the tensor is built
  from - and every transform thereafter.
- **corpus:** NONE. Nearest: `client-architecture/hash-pinned-translation-pipeline`
  (provenance rides with content) and `llm-observability/llm-call-telemetry-model`
  (server-owned fields on a record); neither models a data object carrying its own
  coordinate frame and operation history through a transform chain.

### D2 - Transforms are traceable, and therefore invertible

- **decision:** every transform that changes geometry pushes a record (class, id,
  whether it fired, the parameters needed to undo it) onto the tensor's applied-operations
  stack via `TraceableTransform`; `InvertibleTransform` pops and undoes; model outputs are
  **decollated** from the batch back into per-item tensors before inversion, because
  items had different original shapes; tracing is thread-local and stripped on pickling.
- **forces:** a prediction is only useful in the patient's original frame, and a
  preprocessing chain of ten spatial steps cannot be inverted by hand per pipeline;
  batching destroys per-item shape.
- **buys:** `Invertd` maps any prediction back through the exact chain that produced its
  input; test-time augmentation and ensembles become mechanical.
- **rejects:** hand-written inverse pipelines; inverting on the batch tensor (impossible
  when shapes differ); a global trace (not thread-safe under data-loader workers).
- **where:** monai/transforms/inverse.py:43 (stack), :74-105 (thread-local tracing and
  the pickling rule), :133 (push); whatsnew_0_6 "Decollating mini-batches" (the four
  reasons); docs/source/modules.md "Decollating and invertible transforms".
- **stage:** post-processing, between the model output and the metric or the writer.
- **corpus:** NONE. Nearest: `ui-surfaces/input-and-editing/undo-history` (an undo stack
  for edits) - a UI concern, not a data-pipeline one; the forces (batching, frame
  recovery, worker processes) are absent.

### D3 - Lazy resampling: defer geometric ops, compose, materialise once

- **decision:** transforms implementing `LazyTrait` append a pending operation (a
  homogeneous matrix plus resampling parameters) instead of executing; `Compose` fuses
  the pending list into one resample when a non-lazy transform, a transform declaring
  `requires_current_data`, an explicit `ApplyPending`, or the chain's end forces it.
  Three pipeline modes: `lazy=True` (all lazy-capable transforms defer), `False` (none),
  `None` (honour each transform's own flag). Per-key `overrides` set interpolation and
  padding at apply time.
- **forces:** each intermediate resample costs time, memory and interpolation error, and
  an early crop throws away data a later rotation would have brought back into view.
- **buys:** one resample instead of up to N; less accumulated interpolation noise; crops
  applied after the geometry so no in-bounds data is lost.
- **rejects:** eager execution (the default until 1.2, still available); transparent
  laziness with no escape hatch (transforms that read voxel values must see current
  data, hence `requires_current_data`).
- **where:** docs/source/lazy_resampling.rst (whole document: the traditional vs lazy
  walk-through, the three `lazy` values, `requires_current_data`, `ApplyPending`);
  monai/transforms/transform.py:305 (`LazyTransform`); monai/transforms/compose.py:65
  (`execute_compose` lazy/overrides args); tests/lazy_transforms_utils.py (the lazy-vs-
  eager consistency oracle including inverse round-trip).
- **stage:** preprocessing execution - the point where a chain of declarative transforms
  becomes work.
- **corpus:** NONE. Nearest: `backend-platform/work-execution/pipeline-dag` - models a
  user-authored graph with human gates, not a transform chain whose steps can be
  algebraically fused; the forces (interpolation error, memory per intermediate) are absent.

### D4 - Array/dictionary duality with pass-through semantics

- **decision:** every transform exists in an array form and a dictionary (`d`-suffixed)
  form; the dictionary form is a `MapTransform` over declared `keys` with an
  `allow_missing_keys` switch and a pass-through obligation (unused keys are copied
  through); `Compose` maps over lists when a transform emits multiple samples
  (`map_items`, with a nesting depth); randomised transforms carry their own random
  state (`Randomizable`) and draw once per sample so image and label receive the same
  crop; thread-unsafe transforms are marked.
- **forces:** supervised medical training needs the same random geometry applied to an
  image and its label, and patch-sampling transforms return many samples from one.
- **buys:** one random draw governs all keys of a sample; multi-sample transforms
  compose with everything after them; the array form stays usable standalone.
- **rejects:** separate pipelines per key with shared seeds (fragile); tuple-based
  positional pipelines (unreadable at ten keys).
- **where:** monai/transforms/transform.py:249 (`Transform` contract: thread safety,
  pass-through, memory), :377 (`MapTransform`); monai/transforms/compose.py:141
  (`Compose` docstring: the two usage modes and the multi-sample example);
  `Randomizable` docstring (independent random state, not thread-safe, deepcopy warning).
- **stage:** transform authoring and chain composition.
- **corpus:** NONE. Nearest: `test-input-generation/seed-is-not-a-reproduction` (random
  state discipline in tests) - one clause of D4, not its pipeline shape.

### D5 - Deterministic-prefix caching

- **decision:** dataset classes cache the output of the chain **up to the first
  randomised transform** and run only the random tail per epoch (`CacheDataset` in
  memory, `PersistentDataset` on disk keyed by a hash of the deterministic prefix,
  `SmartCacheDataset` as a running window replaced by a background thread); a
  thread-based loader replaces the multiprocess one when transforms are light.
- **forces:** thousands of epochs re-read and re-preprocess the same volumes; the random
  tail must not be frozen or augmentation dies; multiprocess loaders pay IPC per item.
- **buys:** order-of-magnitude epoch speedups (the docs carry the chart); one rule for
  authors - put deterministic transforms first.
- **rejects:** caching the whole chain (kills augmentation); no caching (the default
  engine's dataset); it also lists where it does not work (spawn-context loaders,
  persistent workers, one platform's default start method).
- **where:** monai/data/dataset.py:162 (`PersistentDataset`), :727 (`CacheDataset`),
  :962 (`SmartCacheDataset` with the running-window example and the four failing
  configurations); docs/source/modules.md "Cache IO", "ThreadDataLoader vs DataLoader".
- **stage:** dataset construction - between the transform chain and the loader.
- **corpus:** NONE. Nearest: `llm-agent/prompt-and-context/prompt-assembly` (prefix
  caching of prompts) - the same shape, a stable prefix and a variable tail, in a
  different substrate; and `build-economics` (build caching). Neither states the
  randomness boundary as the cache boundary.

### D6 - The bundle: a self-describing model package with a declarative object-graph config

- **decision:** a model ships as a directory with a fixed layout, a metadata contract
  (schema URL inside the file; version floors; tensor formats from an open vocabulary;
  spatial shapes as shared-variable expressions; post-processed outputs declared apart
  from raw ones), one or more config files in a small object-graph language
  (`_target_` instantiation, `@` references, `$` expressions and imports, `%` textual
  macros, `+key` merge-versus-override across files, `_requires_` for ordering
  dependencies no argument carries, `_disabled_`, `_mode_` default/callable/debug), and a
  `BundleWorkflow` that declares **required properties** per workflow type which a
  consumer checks before running.
- **forces:** a model zoo, an annotation tool, a deployment container and a federated
  client must all consume models whose authors they never meet; the training recipe has
  to travel with the weights; and higher-level paradigms (federated learning, AutoML)
  must be able to drive a model without knowing its components.
- **buys:** a program can read what a model is for, what it takes, and how to run it;
  configs are diffable and overridable from a command line; the same bundle trains,
  infers and federates.
- **rejects:** ad-hoc scripts per model; a deployment container as the unit of sharing
  (the docs draw the Bundle-versus-MAP boundary explicitly: description and recipe
  here, containerisation and clinical integration there); and, since 1.5, config-only -
  a `PythonicWorkflow` exists for authors who want code with the same property contract.
- **where:** docs/source/mb_specification.rst (whole page); docs/source/config_syntax.md
  (whole page); docs/source/mb_properties.rst + the three properties CSVs;
  monai/bundle/workflows.py:55 (`BundleWorkflow`, incl. the logging-config eval
  advisory), :390 (`ConfigWorkflow`); docs/source/bundle_intro.rst "Bundle vs. MAPs".
- **stage:** packaging and consumption - the boundary between a model's author and
  every program that runs it.
- **corpus:** partial. `repo-manifest-standard` models the metadata half's forces
  (spec-ships-with-artifact, must-ignore-unknown, semver-additive-evolution) for a
  *repository's* self-contract; a source-tree application was written there. NONE for the
  object-graph config language and the required-properties contract: `settings` is a
  runtime key-value store, not file composition; nothing models `+key` merge markers or
  a consumer-checked property list.

### D7 - Workflow as an event-driven engine with attachable handlers

- **decision:** trainer, validator and evaluator share one `Workflow` class over an
  event engine; everything that is not the iteration (checkpointing, logging, metrics,
  learning-rate schedules, validation triggers) is a handler attached to an event; a
  `key_metric` and a comparison function decide checkpoints; outputs are decollated
  before post-processing.
- **forces:** decouple the domain components (transforms, losses, metrics) from the
  generic loop so AutoML and federated learning can drive the loop without owning it.
- **buys:** a training run is a config of handlers; the same loop serves three roles.
- **rejects:** a monolithic training function with flags.
- **where:** monai/engines/workflow.py:47 (`Workflow` docstring: every argument is a
  seam); docs/source/modules.md "Workflows".
- **stage:** the training loop.
- **corpus:** partial - the corpus holds hook-and-handler shapes in several subjects
  (`pipeline-dag`, `background-jobs`), none for a training loop; the forces here are
  modest and the decision is the engine's, not the tree's. Counted as NONE for routing
  with low weight.

### D8 - Windowed inference with blended seams over inputs larger than memory

- **decision:** inference over a large volume runs a window of a declared size across
  it with an overlap fraction, blends overlapping predictions (constant or gaussian
  weights), pads when the window exceeds the input, keeps windows on one device and the
  stitched output on another, switches stitching to CPU above a voxel threshold, and
  buffers window rows before writing; generalised in 1.2 into a modular patch inferer.
- **forces:** volumes do not fit accelerator memory; window seams produce visible
  artefacts; the network's shape constraints (divisibility) and the window's size
  interact, which the bundle's shape expressions exist to state.
- **buys:** bounded memory independent of input size; seam quality tunable.
- **rejects:** downsampling the whole volume; model parallelism (linked as the
  alternative research direction).
- **where:** monai/inferers/inferer.py:446 (`SlidingWindowInferer` argument docstring:
  overlap, mode, sigma_scale, cpu_thresh, buffer_steps); docs/source/modules.md
  "Sliding window inference".
- **stage:** inference.
- **corpus:** NONE. Nearest: `llm-observability/usage-limit-governance` (a sliding window
  over time) - the phrase, not the mechanism.

### D9 - Optional dependencies invoked lazily, proven by a minimal-install lane

- **decision / forces / buys / rejects:** see the source-tree application written this

- **where:** CONTRIBUTING.md "Adding new optional dependencies"; tests/min_tests.py
  (190 exclusions); monai/utils/module.py `optional_import`.
- **stage:** import time versus call time.
- **corpus:** `backend-platform/resilience/optional-dependency-degradation` - its golden

### D10 - AutoML as bundle generation

- **decision:** an automated segmentation solution analyses the dataset (intensity,
  dimensionality, resolution statistics), fills algorithm **templates** into bundles
  from those statistics, trains every generated bundle, and ranks and ensembles the
  checkpoints; algorithm state moved from native pickling to structured text in 1.6.
- **forces:** non-experts cannot choose architectures and hyperparameters per dataset;
  the bundle (D6) is the unit that makes generated recipes runnable and shareable.
- **buys:** a dataset in, a ranked ensemble out, every intermediate a first-class bundle.
- **rejects:** hand-tuned recipes; opaque AutoML that emits only weights.
- **where:** docs/source/modules.md "Auto3dseg"; whatsnew_1_0, whatsnew_1_1, whatsnew_1_2
  (benchmarks, HPO, multi-node); whatsnew_1_6 "JSON-Based Algo Serialization".
- **stage:** recipe generation, upstream of training.
- **corpus:** NONE (uncapped: `automl` returns zero subjects; "template generation" maps
  to prompt composition in media-generation, a different substrate).

### D11 - The federated client as an abstract algorithm over bundles

- **decision:** an abstract client (`initialize`, `train`, `get_weights`, `evaluate`,
  `abort`, `finalize`) that any federated platform can host; the concrete client runs a
  bundle; a statistics client computes shareable dataset summaries; an exchange object
  types what crosses the wire.
- **forces:** hospitals cannot share data; a platform vendor should not have to know the
  model; the bundle's required properties are what let a generic client drive it.
- **buys:** the same bundle trains locally and federates unchanged.
- **rejects:** a platform-specific client per model; sharing raw statistics untyped.
- **where:** docs/source/modules.md "Federated Learning"; monai/fl/client/client_algo.py
  (`ClientAlgo`); whatsnew_1_0 "Federated Learning Client".
- **stage:** distributed training.
- **corpus:** NONE. `llm-observability/federated-benchmark-sharing` shares aggregate
  benchmark digests across installations - a cousin in the sharing half, absent in the
  training half.
