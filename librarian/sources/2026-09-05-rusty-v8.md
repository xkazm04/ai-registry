# rusty_v8 — Rust bindings for the V8 JavaScript engine

Operator aim, stated in the invocation: **improve our Rust code design
proficiency.** That framing decided the run. A binding layer's whole product is
design, so the design read (Phase 2d) was the extraction rather than a step
before it, and the claim lane produced almost nothing — correctly.

**Class and expected yield, said before the triage table.** A vendor
repository, design-deep, and a *system*. The class predicts the README is the
least reliable surface and the types are the most, and it predicted the ratio
almost exactly: **2,606 words on the landing page against 33,590 words of

which argues the whole lifetime model before a line of it appears. A run that

## Declared focus (round 26), answered

1. **Apply the measurement test to the DESIGN RECORD, not only to papers.**
   Executed on every one of the nine entries, and it is the thing that decided
   the run's shape. The question — *what would this tree have to show for this
   decision to be wrong, and does it show it?* — has an unusually crisp answer
   in a tree like this one, because a binding layer's falsifiers are **tests
   named after the hazard**. Three entries showed theirs
   (`global_off_thread_drop_is_drained_on_home_thread`,
   `global_drop_from_cold_tls_destructor`,
   `global_clone_inside_unlock_window_panics`), and those three became the
   subject's spine. Two entries could not answer and are untriaged below. **The
   sharpening worth carrying forward: in a repository, the falsifier test is
   usually discoverable by NAME, so this check costs one grep, not a
   reconstruction.** That is much cheaper than the equivalent check on a paper
   and should be run first, not last.
2. **Report the instrument self-catch as `selfcatch=<n>`.** One this run, and it
   is in the apply arm rather than in a registry instrument: the paired test was
   written with arm A (no queue) inside it precisely so the harness has a
   built-in known-negative. Without arm A, arm B passing would have proved only
   that a channel works. Counted.
3. **A `not-better` that means "unexpressible, not absent" must name what would
   make it expressible.** No `not-better` row this run — the apply came back
   `better` — but the rule was applied to the row's *residue* instead, which is
   the same discipline: the shutting-down-runtime case is named, and what would
   close it (a teardown path the consuming engine does not have) is named with
   it.

## The gap, stated precisely

`backend-platform/language-runtime` held nine subjects and **every one of them
is engine-side**: designing an engine's heap, its strings, its bytecode, its
hook surface, what it exposes to guests. Verified uncapped and on concepts
rather than proper nouns, because both of the method's absence traps applied
here — a capped grep and a denylisted vocabulary would each have produced a
confident wrong answer.

Nothing was host-side: **writing the memory-safe binding layer over an engine
you did not write and cannot change.** `engine-host-contract` is the mirror and
says so in its own words — *the design of that contract from the engine's side*
— and the asymmetry is the whole finding: the engine-side subject can change
the contract, and a binding author cannot.

## Accepted

**X1 — new subject `engine-binding-surface`** (10th in its category, which is
now full; the next one there needs a subdivision). Five techniques:

- `address-sensitive-construction` (D1)
- `capability-deferred-release` (D3)
- `ask-the-authority-not-the-shadow` (D4)
- `hierarchy-as-three-relations` (D5)
- `phantom-capability-parameter` (D8)

Three source-tree applications written against the clone, one per entry whose
falsifier the tree shows.

**The strongest of the five, and why it is a technique rather than an
amendment.** `concurrency-guards/release-guarantees` enumerates five ways a
release fails to fire and answers all five with *bind the release to the
destruction of a scope*. This case is the one where that answer is complete and
still wrong: the scope is destroyed, the destructor runs on every path exactly
as designed, and it runs somewhere it is not permitted to act. Reading it as a
sixth member of that list sends the repair to the wrong place, so the boundary
is stated in the new subject rather than as a paragraph inside the old one —
the v2 rule that a mechanism gets a technique and only a boundary case gets an
amendment.

**A1 — amendment to `constraint-deletion-is-silent`.** The technique's remedy
for the altitude with no liveness signal is a negative artifact asserting a
known-bad construction is rejected. This tree keeps fourteen of them and then
gates the whole suite twice — `#[cfg(not(target_os = "android"))]` and
`#[rustversion::attr(not(nightly), test)]`. Both guards are honest: diagnostics
differ on a pre-release toolchain and the emulated target cannot run the
harness. The consequence is that on those configurations the only instrument
that can see the constraint's deletion does not run, and deleting a structural
constraint makes strictly more programs valid, so nothing else goes red either.
**The remedy, applied naively, reproduces the disease.** Landed with two rules:
a guard on a negative artifact is a written coverage statement, and at least one
blocking configuration must run it.

## Already covered (2) — catches, and one of them is a good one

- **D2, the build-time layout assertion.** `assert_layout_subset!` checks size,
  alignment and per-field offsets in a `const` block so a reordered field fails
  the build rather than producing a reinterpretation that reads one member as
  another. This is exactly `build-time-evaluation-of-cross-value-invariants`'
  stated class — its *containment* and *alignment and stride* members. Cited
  from the new technique rather than restated.
- **D6, the compile-fail fixtures.** `constraint-deletion-is-silent` explicitly
  advises against pinning rendered diagnostic text, and this tree pins fourteen
  `.stderr` files. It is not a refutation: borrow-checker and lifetime
  diagnostics carry no stable identifier, so only text exists, and the
  technique's own third fallback is *keep the artifact anyway and keep the count
  small enough that a regeneration is read*. **The corpus priced this tree's
  choice before the tree was read**, which is the strongest form a catch takes.

## Untriaged (2) — extracted, reached the table, nobody verified these

- **D7 — the undecidable provenance check.** `HandleHost::match_host` decides
  whether two handles share an isolate and sometimes cannot; its comment says
  *"a bit too forgiving […] it just returns `true` […] needs to be tightened
  up"*, and the adjacent assert turns that value into an authorisation. Read
  against `unknown-is-not-a-value` the tree gets one half right (the optimistic
  branch is its own arm with a stated `TODO`, not a catch-all) and one half
  wrong (the return type is `bool`, so *cannot tell* and *yes* are the same
  value by the time a caller sees them). The observation is recorded inside
  `ask-the-authority-not-the-shadow`'s closing section and in the application,
  but as a **candidate for its own technique it scored 2/1/2 and did not clear
  +2** — the home is contested between the new subject and
  `marked-unverifiable-region`, and nobody read the latter's fourth property
  against it. Anchors: `src/handle.rs:687-730`.
- **D9 — thread affinity as a negative auto-trait.** `Opaque` carries
  `_not_sync: PhantomData<Cell<()>>` so a shared reference obtained from a
  handle cannot cross threads, with the reason in a comment above it
  (`src/data.rs:20-27`). Scored 1/2/1. Thin on its own; it is one line and a
  language-specific trick, and the general rule it would carry — encode a
  negative capability structurally rather than documenting it — may already sit
  inside `invariant-placement`'s shape altitude. Nobody checked.

## Applied (1)

`capability-deferred-release` → **pumper**, mode `code`, verdict **better**,
proof `ab-paired`. Full row in `librarian/applied.md`; the seam, the arms and
the residue are in the application document and in the project's own
`.ai/applied.jsonl`.

The row's value is that **the tree refuted the reading that selected it**. The
seam was picked expecting an unguarded destructor; the project had already
reasoned carefully about this exact family, aborts the capability-free half
unconditionally, and states its failure modes in comments instead of hiding
them. What it lacked was the third answer between *perform* and *abandon* —
record the debt and settle it where the capability provably exists — and its
own `acquire` was a checkpoint waiting to be used. Measured 0 of 1 against 1 of
1 on closes observed after a runtime-less drop, on the crate's own harness, with
the old behaviour as arm A inside the same test so the instrument is shown to
distinguish rather than merely to pass.

Shipped to a branch rather than the default branch: ~110 lines across a new
type, a field, a constructor, a call site and a checkpoint is past what a
reviewer reads in one sitting, which is Phase 8 step 4's second exception. Not
pushed. The project's checkout was returned to its own branch afterwards.

## Directions not proposed

None. The direction pass asks which project has *no seam at all* for a
capability the source shows matters; here the fleet's only project that embeds
a foreign engine at a trust boundary is the one that already got the coverage
change, and proposing a binding-surface capability to a project that consumes an
engine through a CLI would be citing the source's features rather than its
forces.
