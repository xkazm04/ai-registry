## Design record

### A. Interactive transactions over a single-writer store beneath a consensus log

- decision: The storage interface gains Go-database-style interactive
  transactions; on the integrated Raft backend a transaction is a local
  bbolt read snapshot plus a verify-then-write log entry re-validated at
  FSM apply time, never a bbolt write lock held across the Raft round trip.
- forces: bbolt allows one write transaction at a time with no upgrade or
  nesting; holding it while awaiting consensus means "problems with Raft
  could result in the bbolt transaction being held indefinitely"; only one
  node writes cluster-wide, so no distributed lock is needed; the server
  is co-located with its data (unlike etcd/rqlite one-shot APIs).
- buys: A plugin interleaves code with reads and writes at one consistent
  point in time and gets all-or-nothing commit, refused (not merged) when
  any read it depended on changed. Test: two handlers read-then-write one
  key concurrently; exactly one commits, the other gets a commit failure.
- rejects: a global write lock around Raft; persisting the open bbolt tx
  until apply (both in "Implementing Writable Transactions"); keeping the
  one-shot transactional interface ("Rationale and alternatives");
  client-driven long-lived transactions.
- where: `community/rfcs/transactions.mdx` (Survey of Requirements,
  Implementing Read-Only / Writable Transactions, Verification Hashes);
  Raft ops `verifyReadOp`, `verifyListOp`, `beginTxOp`, `commitTxOp`;
  `physical/raft/fsm.go`, `sdk/logical/storage_view.go`, `physical/crosstest`.
- stage: between the plugin's `logical.Storage` call and `fsm.Apply`.
- notes: a new client retry class ("transaction commit failure"); the log
  grows one 48-byte hash per verified read; transaction size capped at
  ~8x `max_entry_size`; write transactions "best reserved for limited,
  high-assurance cases" because they serialize behind the global writer;
  File and InMem backends are non-transactional, so plugins type-assert
  and fall back.
- corpus: **NONE.** Nearest `backend-platform/data-layer/data-access/
  transactions-and-units-of-work` (unit-of-work boundaries, serialization
  verdicts) models application-level transactions over an engine that
  already has them; it does not model building the transaction on a
  single-writer embedded store under a replicated log, nor the
  verify-at-apply shape.

### B. Storage-limit-shaped core structures: split tables and bounded enumeration

- decision: The mount tables are stored one entry per mount under a
  transaction instead of one compressed JSON blob, and LIST becomes a
  bounded, policy-governable operation (`ListPage(prefix, after, limit)`
  from bbolt to CLI; ACL `pagination_limit`, required `limit`, a separate
  SCAN verb with its own capability; opt-in filtering of results to
  accessible keys).
- forces: `max_entry_size` 1 MB "usually works out to about 14k mounts";
  an unbounded list "requires the collection of items fits in memory of
  the server" - observed "100k-1m leaf certificates per mount ... 100MB+
  of memory just for the list, per mount"; filtering costs a policy
  evaluation per key so it is safe only under a limit.
- buys: mount count bounded by memory and storage speed, not one entry's
  size (PoC 360k mounts); every enumeration path can be bounded by
  policy, and a limit-less request either fails or is clamped at the
  operator's choice.
- rejects: upstream's larger-entry tunable; a segmented pseudo-transactional
  table; server-side search instead of pagination; `recurse=true` on LIST;
  always-on filtering; a `next` cursor for filtered pages (would leak
  present-but-inaccessible keys).
- where: `split-mount-tables.mdx` (Technical Description, Downsides,
  Proof of Concept); `paginated-lists.mdx`; `acl-paginated-lists.mdx`
  (`ACL.AllowOperation`, `HandleListPage`); `scan-operation.mdx`;
  `filtering-list.mdx` (`ACLResults.ResponseKeysFilterPath`).
- stage: mount-table persistence; the ACL check before routing; a response
  post-processor after the plugin returns keys.
- notes: no downgrade path for split tables; pagination is not bound to a
  transaction, so pages can miss or duplicate entries created mid-iteration;
  a filtered page can come back empty while accessible keys exist later
  (unresolved); the `max` literal collides with endpoints that accept a
  real value `max`.
- corpus: **NONE.** Nearest `backend-platform/resilience/rate-limiting`
  (limit-derivation) governs request rates, not the size of a single
  enumeration; `embedded-db/storage-accounting-and-pruning` governs growth,
  not entry-size-shaped data layout.

### C. Read-scaling standbys: forward on error, invalidate from the committed-write stream, carry the index in the client

- decision: Every unsealed standby runs the full post-unseal and serves
  reads locally; a read-only storage shim turns any write into
  `ErrStandbyPleaseForward` and the HTTP middleware forwards on that
  error rather than on the verb; invalidation is driven by the backend's
  own committed-write stream (Raft `fsm.ApplyBatch` hook; a standby-to-active
  gRPC stream carrying keys plus a storage index for non-Raft backends);
  read-your-writes is client-side via an opaque `X-Vault-Index` header
  with per-listener behaviour (fail / forward / await).
- forces: active-passive left standby compute idle while "the system
  continually invests in I/O ... to synchronize all state changes";
  separate node types add flags and forwarding special cases; the
  physical backend had no invalidation hook and several layers cache;
  PostgreSQL LISTEN/NOTIFY "does not work across PostgreSQL replicas ...
  and would not work with PGBouncer"; server-side waiting on all standbys
  after each write stalls on the slowest replica; tokens are immutable so
  they cannot carry a moving index.
- buys: read throughput scales with node count while write ordering stays
  single-leader; a standby never serves a cached value older than a
  write it has already replicated; a client echoing its last index
  observes its own writes on any node without the server blocking on
  the slowest replica.
- rejects: a distinct performance-standby tier; TTL invalidation (cannot
  invalidate LIST/added/deleted); LISTEN/NOTIFY, logical replication,
  `updated_at` polling; the index inside server-side consistent tokens;
  write-side waiting for standby acknowledgement.
- where: `standby-nodes-handle-read-requests.mdx` (PostUnseal
  Implementation, Enhanced Forwarding Logic; `vault/ha.go`,
  `http/handler.go`); `invalidation.mdx` (`HABackend.HookInvalidate`,
  `Core.Invalidate`); `grpc-invalidation.mdx` (`connectedInvalidationPeers`,
  `standbyAwaitedInvalidations`); `index-headers.mdx`
  (`physical.ReplicationIndexBackend`, `consistency_fallback_behavior`).
- stage: the forwarding middleware (on the storage error, not the verb);
  immediately after a write is durable; a middleware early in the HTTP
  stack comparing the request's index against storage index plus drained
  invalidation queue.
- notes: "We won't be able to detect all requests that will write to the
  storage in the middleware"; a standby whose queue grows too old steps
  down from read-enabled; standbys without gRPC connectivity cannot be
  read-enabled; the 1.6.0 run's twelve one-per-cache bugs are the paid
  cost of this decision.
- corpus: **NONE.** Nearest `backend-platform/data-layer/sync-replication/
  topology-declaration`, whose "mirror's derived state" section was
  written *this morning from this source's fragments* - a paragraph about
  the failure, not a model of the forces (idle standby compute, one node
  type, forward-on-error, client-carried consistency). The golden path
  reads sync as client data sync.

### D. The barrier: a three-key hierarchy over untrusted storage, rotated by layer, with rotation behind authentication

- decision: Every byte leaving the server passes a barrier (AES-256-GCM,
  random 96-bit nonce per object) keyed by a keyring wrapped by a root
  key that is never stored in plaintext; unsealing is exclusively
  recovering the root key (unseal key -> root key -> keyring); the
  keyring rotates online by appending a key, the root key rotates by
  re-wrapping the keyring, standbys catch up through a short-lived
  "upgrade" entry; root and recovery rotation sit behind sudo-gated
  authenticated endpoints and auto-unseal init may return zero recovery
  shares.
- forces: the storage backend and transport are untrusted by design;
  "a single malicious attacker with access to it can decrypt the entire
  OpenBao", hence Shamir by default; AES-GCM must rotate before ~2^32
  encryptions so keyring rotation must be cheap and quorum-free; the
  unauthenticated rekey endpoints let an attacker cancel rotation
  silently (v2.3.1 bulletin); declarative provisioners cannot store a
  secret minted as a side effect of init.
- buys: the raw backend yields only ciphertext with verifiable tags and
  no single object or person yields the root key; old values decrypt
  after rotation without re-encryption; a standby unsealed with key N
  takes leadership without re-unseal; no long-lived privileged secret
  exists at bootstrap.
- rejects: trusting the backend for confidentiality; one key to one
  operator; re-encrypting storage on rotation; one undifferentiated
  "rekey" verb; the upstream nonce-on-delete patch ("doesn't solve the
  issue that the initialization endpoint remains unauthenticated").
- where: `docs/internals/security.mdx`, `docs/concepts/seal.mdx`,
  `docs/internals/rotation.mdx` (upgrade key, NIST guidance);
  `authenticated-rekey.mdx` (`SealConfig.ValidateRecovery()`).
- stage: init, unseal, per-request encrypt/decrypt, rotation (active node
  only), post-unseal periodic check on standbys.
- notes: memory analysis is declared out of scope and mlock removed;
  recovery mode does not work until recovery keys exist; operators
  estimate encryption counts from four metrics.
- corpus: **credential-vault / encryption-at-rest** models the hierarchy's
  forces (envelope layering, where the master key lives, one seal door).
  Rotation by layer, the upgrade key and quorum-gated rotation are not
  modelled there - the source-tree application written this run
  (`go--encryption-at-rest`) records them as the tree's extension of the
  standard. Counted as modelled.

### E. Seal plurality and pluggability: any one seal unseals, the seal boundary is a plugin, tenants get their own chain

- decision: Multiple seals may coexist, each holding an independent
  encryption of the one root key under `core/seals/<name>/`, so any one
  seal - including a break-glass Shamir emergency seal - unseals the node
  while recovery keys never become an unseal path; a static AES key from
  the environment is a first-class seal; vendor KMS wrappers ship as
  out-of-process `kms` plugins registered only in the config file because
  seals initialize before storage is readable; a sealed namespace gets its
  own KEK -> root -> keyring chain and mount-level HSM keys are bound
  through namespace-scoped, grant-gated external keys.
- forces: auto-unseal alone is "a strict OpenBao lifecycle dependency" -
  a deleted KMS key means the cluster "cannot be recovered, even from
  backups"; upstream requires all KMSes co-online, which multi-cloud DR
  cannot promise; Kubernetes-style platforms have a secret store and no
  KMS, and the KMS credential would live in that store anyway; nine
  built-in seals plus eight pending vendors couple vendor fixes to server
  releases; `sys/plugin/*` is storage-driven and unusable before unseal;
  global sealing means "tenants lack independent control over the
  availability of their specific namespace".
- buys: with the primary KMS unreachable a Shamir share set still unseals;
  the two-seal form is a strict subset of N-seal; a KMS plugin crash does
  not take the core down; the global root key cannot decrypt a sealed
  namespace's data and sealing cascades to children; an HSM key is usable
  by a mount only through an explicit grant.
- rejects: recovery keys as unseal keys (overloads key functions);
  1:1 compatibility with the commercial seal-HA design; m-of-n seal
  requirements; helper daemons automating Shamir; compiling every seal
  into the binary; namespace lock/unlock as a substitute for sealing;
  double-encrypting under the parent chain; a KMS secrets engine that
  bypasses PKI/SSH role controls.
- where: `parallel-unseal.mdx` (New Storage Layout, New Unseal Process),
  `emergency-seal.mdx` (Storage, Rekeying, Alternative: recovery keys),
  `static-auto-unseal.mdx`, `auto-unseal-plugins.mdx` (OCI download
  before unseal), `namespace-sealing.mdx` (Key Hierarchy, Storage
  Considerations), `external-keys.mdx` (SystemView `ListKeys`/`GetKey`).
- stage: server start before core creation; init per seal; unseal in
  priority order; rotation with per-seal catch-up; tenant creation.
- notes: overall security drops to the weakest seal; emergency seal blocks
  root rotation while the primary is offline; static keys are not reloaded
  on SIGHUP; all tenant KMS/HSMs must be online at restart; namespace-seal
  failover is unresolved.
- corpus: **NONE.** `encryption-at-rest` models one master key in one
  custody; it does not model N independent custodies of one root, a
  break-glass path that is not a recovery path, the seal as a pre-storage
  plugin boundary, or per-tenant key chains. `optional-dependency-
  degradation` is the neighbour for "the KMS is unreachable" and does not
  reach it.

### F. Authority is a priced artifact: persisted tokens and leases, one escape that never persists, and single-use wrapping

- decision: Every unit of authority is a token (or a lease bound to one)
  whose cost is a storage write - three writes per login, re-read by
  standbys on leadership change - and the system offers exactly one escape
  from that cost, authority that is never persisted (batch tokens; inline
  authentication that authenticates the main request without returning or
  storing the token); a response-wrapping token is a single-use unsigned
  service token whose cubbyhole holds the response and whose validity only
  the server can attest; control groups park a blocked request in a
  wrapping token's metadata until approvers act.
- forces: login is "one of the few non-scalable requests"; CI workloads
  discard the token after one run; signing wrapping tokens was rejected
  because an attacker who redirects you "could trivially give you the wrong
  signing public key"; an approver "should not be able to grant their own
  personal access".
- buys: an inline-authenticated request leaves zero rows in the token store
  and expiration manager, so a leaked value is worthless outside the
  request; anything that creates a lease must take the persistent path
  (inline auth revokes and errors); `sys/wrapping/lookup` is unauthenticated
  and reports the creation path so a client verifies origin before unwrap;
  a second unwrap fails; the approver can approve but never read the data.
- rejects: longer-lived application tokens; heavier service tokens for
  everything; signed wrapping tokens; second-party approval by temporary
  policy grant.
- where: `inline-auth.mdx` (`core.handleInlineAuth`), `docs/concepts/
  tokens.mdx` (token type comparison), `docs/internals/token.mdx`,
  `docs/concepts/response-wrapping.mdx`, `control-groups.mdx`
  (`sys/control-group`, `approve-accessor`).
- stage: request entry before dispatch; token/lease creation at login and
  issuance; response serialization; ACL application before the result is
  released.
- notes: quota counts once, so up to 2x amplification against
  unauthenticated endpoints is accepted; batch tokens lose accessors,
  renewal, cubbyhole and child tokens; revoke-by-tree and revoke-by-prefix
  work only because service tokens persist source path and parent - the
  write cost is the price of the break-glass procedure.
- corpus: **NONE.** `credential-vault/token-refresh-lifecycle` is the
  consumer's side of a lease; `authorization/delegated-authority` carries
  authority across hops but does not price it, and neither models the
  issuer's ledger, a never-persisted class of authority, or a single-use
  cubbyhole as the primitive for secure introduction and second-party
  approval.

### G. Operator-authored policy and bootstrap: an embedded expression language, a request-chain config, and out-of-process plugins over a split trust model

- decision: Where the static role vocabulary runs out, CEL is embedded
  in-process as a separate `cel/` role type that must return the final
  output object; server bootstrap and privileged device management move
  from stateful API calls to the config file as an ordered chain of
  ordinary API requests applied once on first start (self-init) or
  reconciled on start and SIGHUP (audit devices); plugins are separate
  gRPC processes distributed as OCI images and declared in config, where
  the config author is trusted as a host-level operator so `sha256sum` is
  optional there and mandatory in the API catalog.
- forces: "OpenBao cannot know how to parse, validate, or generate
  everything"; a webhook adds latency and an availability dependency; a
  one-time init returns a root token "valid indefinitely"; two CVEs showed
  "any API-driven audit device creation is unsafe" because file and socket
  devices write to host paths - a system-operator privilege; a plugin
  crash must not crash the server; a dedicated registry needs a CDN and
  DDoS protection; the pre-exec digest check is TOCTOU and host code
  execution is outside the security model.
- buys: a protocol feature is adopted by editing a CEL program, sandboxed
  and non-Turing-complete, with protocol checks still in Go; a fresh node
  comes up with audit, policy and auth configured and no root token ever
  exposed; config-defined audit devices cannot be altered via the API; an
  OCI manifest digest pins a multi-arch plugin and `plugin_version =
  "latest"` upgrades N mounts with one reload.
- rejects: CEL limited to selecting role attributes; regex on bound claims;
  webhooks; a bespoke DSL ("we should not attempt to build a new DSL");
  continual config re-initialization; a dedicated plugin registry; direct
  HTTPS downloads; in-process plugin loading.
- where: `cel-best-practices.mdx` (tenets 1-3), `cel-jwt.mdx`, `cel-pki.mdx`
  (`ValidationOutput`); `self-init.mdx` (`ServerCommand.Run`),
  `docs/concepts/profiles.mdx`, `config-audit-devices.mdx`;
  `config-plugins.mdx`, `plugin-improvements.mdx` (`.oci-cache/sha256:`),
  `docs/plugins/plugin-architecture.mdx`.
- stage: inside the backend at login/issue time after transport checks;
  server start and SIGHUP; mount enable/reload; node step-down.
- notes: "Operators are solely on the hook" for CEL correctness; self-init
  output at Trace "will contain privileged information"; the OCI cache
  does not defend against manipulation of its entries; two in-flight CEL
  PRs had divergent semantics and the best-practices RFC exists to force
  convergence.
- corpus: **NONE.** Nearest `authorization/declarative-requirements`
  (requirements as data the gate reads) does not model a user-supplied
  program as the decision; `operations/.../settings` and
  `continuous-integration/deployment-contract` do not model bootstrap as a
  replayed request chain; `llm-agent/runtime-and-io/sidecar-provisioning/
  process-isolation` models a sidecar, not a versioned plugin protocol
  with a split trust model.
