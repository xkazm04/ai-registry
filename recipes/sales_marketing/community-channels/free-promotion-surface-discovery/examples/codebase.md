# A local code repository as the grounding source

What was learned mapping this recipe onto a checked out code repository as the thing it
reads the product from. Written about the class rather than about one product's repo:
swap the grounding source for a live site, a pitch deck or a product brief and this file
stops applying while the recipe does not change.

## What the mapping has to decide

**The README was written for the wrong audience, and the failure is silent.** A repository
describes a product to contributors and to people who already arrived. A promotion surface
search grounded on that text will find developer communities no matter who the product is
actually for, and the suggestions will look convincingly specific because they cite real
technical details. This is the single most dangerous property of this grounding source:
the output passes this recipe's own test, that a candidate could not have been suggested
without reading the product, while still being aimed at the wrong people entirely.
Establish at adoption who the product is for, separately, and treat the repository as
evidence about the product rather than about its audience.

**The dependency list is the underrated half.** It names the ecosystems the product
genuinely belongs to, and those ecosystems have their own forums, awesome lists and
directories that almost never appear on a generic promotion list. Where the README
misleads about audience, the manifest is usually honest about neighbourhood.

**Check staleness before deriving anything.** The commit history and the last change to the
descriptive files are both available, and a README that has not moved while the code has is
the ordinary state of a working repository. Every suggestion in this recipe rests on the
description being current, and the check costs almost nothing compared with a pass of
candidates justified against a product that no longer exists.

**A repository with nothing descriptive in it is a real answer.** No README is a finding,
not an error, and the correct response is to ask the adopter what the product is rather
than to substitute a plausible generic description. A generic description produces exactly
the generic candidate list this recipe exists to avoid, and it will not look generic
because it will have been written to sound specific.

**Grounding material is not publishable material.** A private or internal repository may
contain nothing that can appear in a public post. Reading it to decide where to go is a
different permission from quoting it once you get there, and if the adopter has asked for
drafted approaches the second permission has to be asked for separately.

**A checkout cannot see usage.** It says what the product can do, never what anybody
actually does with it, so a fit argument built on a feature may be built on a feature
nobody uses. Where the adopter has usage evidence, it beats the code every time.

## What transfers to any grounding source

- Ask who the source's text was written for. A description aimed at contributors will find
  you contributor communities and will look specific while doing it.
- Verify the source is current before deriving from it. The whole output rests on that one
  fact and checking it is cheap.
- An empty source is an answer worth reporting. Substituting something generic is how a
  grounded search quietly becomes an ungrounded one.
