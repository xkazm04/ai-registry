# No fixture for live footage

A film, a screenshot or a clip that shows a stream tool acting on the platform is a live
claim in picture form, and it is believed more readily than any sentence. This technique
holds footage to the same rule as a written claim: what is shown as live was captured from
a live run, and anything else — a rehearsal, a recorded response replayed, a composite —
is labelled in the picture as what it is.

## The tempting substitutes

Each of these is legitimate material, and each becomes fabrication the moment it is
presented as live:

- **The rehearsal.** The tool's own dress rehearsal produces convincing footage: real
  overlays, real moderation decisions, a crowd that behaves. It has no platform session.
- **The replayed fixture.** A response recorded from the platform once, fed back through
  the tool on cue, so the timing is perfect for the camera.
- **The composite.** A capture of the tool from one run cut against a capture of the
  platform from another, so that the two halves line up.
- **The mock-up.** The platform's page reconstructed or edited to show the outcome the
  tool should produce.

The pull toward them is real and specific: live runs are slow to set up, need the owned
accounts, may need platform approval that has not arrived, and do not repeat. A fixture
does. The rule exists because the viewer cannot tell the difference, which is exactly why
the maker must.

## What live footage requires

Footage presented as live shows a live run end to end on the owned channel: the action in
the tool and its result on the platform, captured in the same session, with a shared
marker or clock that ties the two halves together so that nobody, the team included, can
cut one run against another by accident. Where the footage supports a row in the team's
evidence list, the capture is attached as that row's evidence, and the row's date is the
capture's date.

## When live is not possible

Film the rehearsal or the fixture and **label it in the picture**, by the same code that
draws the tool's own provenance labels, in words from the same vocabulary: simulated,
recorded. The narration says the same thing. The claim the footage illustrates stays
pending; the film may illustrate it but cannot verify it
([law: output-never-outruns-evidence](../../../../_laws.md#output-never-outruns-evidence)).
A label added in editing, after the fact, is weaker than one the tool drew, because it can
be left off the next cut; prefer footage in which the tool's own state put the label
there.

## The shot list carries the readiness

The plan is where this is won or lost, because the substitution happens under deadline in
the edit, not during capture. Every shot in the shot list carries a readiness column:
**capturable now** from labelled material, or **live-dependent**, naming the run and the
evidence it needs. Every narration line that says live, or describes a platform result,
is marked conditional on that evidence. When the run does not happen, the line is cut or
rewritten — the label is never the thing that gives way. A shot whose live run passed but
whose subject was narrower than the narration — a connection test with a stub decision,
a static page standing in for the real overlay — is captioned for what it showed, not for
the feature it foreshadows. And a plan states at its top that it is a plan: a shot list is
not evidence that anything in it works.

Capture itself follows the consent rules of live testing. The channel holds only the
owned accounts; if anyone else enters, capture stops. Sign-in dialogs, device codes,
credential stores and private account details never appear in frame; the success state
after sign-in is what is filmed. An acknowledgement in a log is not the picture: where a
shot claims the broadcasting software shows something, a person confirms it on the
composed picture before the shot counts.

## Procedure

1. Before filming, mark each shot as live or labelled, and for each live shot name the
   owned accounts and the live run it needs.
2. Capture live shots with the tool and the platform in one session on one clock.
3. For labelled shots, confirm the label is visible in every frame that shows the
   simulated or recorded result.
4. Attach each live capture to the evidence row it supports.
5. Review the cut for any shot whose label was cropped, covered or edited away.

## Decision rules

- **When a shot shows a platform result, it is live or it is labelled.** There is no third
  kind.
- **When the live run fails on the day, ship the labelled shot or no shot.** Never
  substitute the fixture silently, and keep the claim pending rather than narrate
  success over the gap.
- **When one half of a shot is live and the other recorded**, label the recorded half;
  one live half does not make the shot live.
- **When the film's narration says "live"**, every frame under that line is from a live
  run.

## When not to use it

Footage of the tool's own interface with no platform claim — a settings screen, a layout,
a tour of features — makes no live claim and needs no live capture. Internal recordings
that never leave the team need the label but not the full discipline.
