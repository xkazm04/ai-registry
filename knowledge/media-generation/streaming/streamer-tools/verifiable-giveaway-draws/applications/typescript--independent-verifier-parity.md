# An offline browser verifier at parity with a Rust proof core (CastleControl)

CastleControl's giveaway proofs ("writs") are drawn by the Rust crate `cc-verify` and
re-verified by `packages/verifier-web`, a TypeScript reimplementation bundled into one
self-contained HTML file a viewer can save and open offline. Citations were resolved
against the main checkout at commit `8ef2d8e` on 2026-11-02; the workspace pins
`"typescript": "6.0.3"` (`package.json:26`).

## Independence, graded honestly

The web verifier does not import the Rust code; it reimplements the specification, whose
authority is the byte-exact doc comment at the top of the proof core
(`crates/cc-verify/src/lib.rs:3` "Byte-exact v1 algorithm"). The rejection limit appears
twice, once per language:

- `crates/cc-verify/src/cast.rs:14` "let limit = ((1_u128 << 64) / u128::from(total)) * u128::from(total);"
- `packages/verifier-web/src/index.ts:18` "const limit = ((1n << 64n) / total) * total;"

So does the round schedule (`packages/verifier-web/src/index.ts:75` "(after - genesis) / BigInt(chain.period_s) + 2n").
On the technique's scale this is the middle grade: a different language and runtime, but
the same team and repository.

## Parity is a test suite, not a claim

- `packages/verifier-web/src/verifier.test.ts:13` "same_winners_as_rust_across_1000_generated_simulated_writs"
  — 900 commit/reveal and 100 BLS-authenticated beacon draws generated by Rust.
- `crates/cc-verify/tests/quicknet.rs:90` regenerates `public-writs.json` from real rounds and
  asserts the committed web fixture matches it, so a stale fixture is a red build.
- `crates/cc-verify/tests/fixtures/drand-quicknet/README.md:5` "cross-checked byte-identical

  beacon mirrors, which is also the compiled anchor's build-time check.
- `packages/verifier-web/README.md:67` "self_contained_html_verifies_all_bundled_writs_and_rejects_bad_bls"
  runs the built page "with dynamic code generation disabled".
- `packages/verifier-web/src/verifier.test.ts:142` "offline_file_control_validates_imports_and_never_passes_bad_or_stale_files"
  and `packages/verifier-web/src/html-check.ts:92` "a stale pass must be cleared".

## The anchor and the unverified state

The web page carries its own anchor and never reads one from the file
(`packages/verifier-web/README.md:15` "Official quicknet imports use the independent bundled official").
Without it the verdict is explicitly not a pass:
`packages/verifier-web/src/index.ts:84` "UNVERIFIED: BLS signature authentication requires a separately trusted chain."
Only a verified result can drive an animation:
`packages/verifier-web/src/index.ts:96` "Unverified result cannot feed an animation".
The desktop's tamper bench uses the same vocabulary and refuses to certify past a failed
step: `apps/desktop/src/rooms/lottery/lab-copy.ts:69` "so its BLS signature is not authenticated here."
and `apps/desktop/src/rooms/lottery/lab-copy.ts:73` "the lab refuses to certify this writ."
Its label is derived from the chain identity, not a flag:
`apps/desktop/src/rooms/lottery/lab-copy.ts:76` "Only the public quicknet chain hash earns 'Public beacon'".

## Deviation: input bounds differ between the two verifiers

The Rust door caps a writ at two million bytes
(`crates/cc-verify/src/model.rs:282` "if json.len() > 2_000_000 {"), the web page at two
mebibytes (`packages/verifier-web/src/page.ts:13` "const max_bytes = 2 * 1024 * 1024;").
A writ between 2,000,000 and 2,097,152 bytes verifies in the browser and is rejected by the
command-line verifier. No winner vector can catch this; the cap belongs in the specification
in one unit, with a boundary vector on both sides.
