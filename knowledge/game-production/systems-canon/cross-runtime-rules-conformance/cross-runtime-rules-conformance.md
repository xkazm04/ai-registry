# Cross-runtime rules conformance

A game's rules often live in two places. A reference simulation, written in a language that
is quick to change and cheap to run thousands of times, is where designers balance the game
and where the rules are first true. The shipped engine carries a port of the same rules,
written for the frame budget, the device and the engine's own types. From the day the port
starts, two runtimes claim to compute the same game. This subject owns the machinery that
makes that claim checkable: which rules data both runtimes load, what evidence shows they
compute the same thing, how close "the same" has to be, how anyone knows the evidence can
fail, and what happens on the day it does.

It is not where thresholds and tables are authored. That belongs to
[design-canon-as-executable-law](../design-canon-as-executable-law/design-canon-as-executable-law.md),
which owns one source for every number. This subject starts after that source exists and
asks whether two consumers of it agree. It is also not an optimisation proof. Showing that a
faster version of one runtime still computes what the slower version did is
[equivalence-before-the-saving](../../engine-integration/perf-regression-gating/techniques/equivalence-before-the-saving.md).
Here the two sides are different programs, in different languages, maintained by different
people at different speeds.

## The four ways two runtimes drift apart

1. **The data drifts.** One runtime loads a newer copy of the tables than the other. Every
   rule is ported correctly and the game still disagrees, because the inputs differ. This is
   the most common divergence and the cheapest to prevent.
2. **The logic drifts.** A rule is ported with an off-by-one tick, a different rounding, a
   clamp in the wrong place, or an iteration order that differs. Each looks harmless and
   compounds over a long session.
3. **The arithmetic drifts.** Floating-point results differ between languages, compilers,
   instruction sets and optimisation levels. Most of these differences are below anything a
   player could perceive. A few are not, because a threshold comparison turns a difference in
   the ninth digit into a different branch.
4. **The authority drifts.** After a mismatch, somebody makes one runtime agree with the
   other by editing whichever is easier. Nobody records which one was right, and the next
   mismatch is decided the same way.

Each technique below answers one of these. The fourth needs a technique of its own because no
test can catch it: it happens in the response to a failing test.

## What a principal practitioner holds true

**Pin the data before comparing the logic.** A conformance failure between two runtimes that
load different tables says nothing about the port. Both runtimes load rules data from one
pinned revision, verified by content hash, and the pin moves only on purpose, in a change of
its own. A port that begins from a copy of the data has already forked it.

**The reference writes the vectors; the port only replays them.** Expected values are
generated by running the reference runtime, never by running the port and saving what it
said. A vector carries the scenario's seed, its inputs per tick, and the expected state at
intermediate checkpoints as well as at the end. A suite that checks only final states can
pass while two runtimes take different routes to the same score, and when it fails it cannot
say where.

**"Equal" is a declared number, not a feeling.** Integers, enums, identifiers, tick counts
and event sequences match exactly. Continuous quantities match within a relative and
absolute tolerance that is written in the vector, enforced by the replayer, and bounded by a
ceiling the replayer refuses to exceed. A tolerance that can be loosened to make a vector pass
has stopped being a tolerance.

**A suite that has never failed is unmeasured.** That rule is owned by
[flag-your-own-shipped-defaults](../design-canon-as-executable-law/techniques/flag-your-own-shipped-defaults.md)
and holds here unchanged. What this subject adds is where to plant the fault for a
conformance suite: in the port's rules, one constant or one branch at a time, followed by a
record of which vectors caught it and a restored run that returns to green. The result is a
sensitivity map, not a pass mark. One planted fault caught by a few vectors shows the suite
can bite. It does not show that the other vectors can.

**A mismatch is a finding about the rules, not a test to make pass.** When the runtimes
disagree, the first question is which one is right, and the answer is recorded with its
reason before either runtime changes. Sometimes the reference is wrong and the port found a
bug in the design. Quietly copying the reference's value into the port destroys that
information.

## The load-bearing distinctions

- **Pinned versus copied data.** A pin names a revision and a hash and fails loudly on drift.
  A copy is a fork with no alarm.
- **Generated versus recorded expectations.** Generated by the reference, a vector is
  evidence of equivalence. Recorded from the port, it is evidence that the port agrees with
  itself.
- **Exact versus tolerant fields.** Discrete state is compared exactly. Only declared
  continuous quantities get a tolerance, and the tolerance has a ceiling.
- **A green suite versus a sensitive suite.** Green is the result on the unmodified port.
  Sensitive is the result on a planted fault. Only both together say the suite measures
  something.
- **Divergence versus defect.** A divergence is a recorded difference between runtimes with a
  verdict about which is authoritative. It becomes a defect in one runtime only once that
  verdict exists.

## What the naive build gets wrong

- **It ports from a copy of the tables**, then spends a week chasing "logic bugs" that are
  data drift.
- **It saves the port's own output as the golden file** after a first manual check, so every
  later run compares the port with itself.
- **It compares only the final score**, so a vector fails with a number and no tick, field or
  first point of disagreement.
- **It widens the tolerance on the failing vector** until it passes, with no ceiling to stop it.
- **It cites the green suite as proof of equivalence** without ever having seen it fail.
- **It plants one fault, watches it fail, and generalises**, treating three catching vectors as
  proof that all of them catch.
- **It names the vector after the rule and assumes that vector tests the rule.** A scenario
  that stops before the rule's limit is reached cannot see a change to the limit.
- **It fixes a mismatch by editing whichever runtime is easier**, so authority moves with
  convenience and nobody can say which runtime defines the game.

## Procedure, end to end

1. Declare which runtime is the reference for the rules, in writing. The other is the port.
2. Pin the rules data both runtimes load: one revision, a content hash per file, and a check
   that fails on any byte difference ([pinned-rules-data-across-runtimes](./techniques/pinned-rules-data-across-runtimes.md)).
3. Generate vectors from the reference: seed, per-tick inputs, checkpoints, final state and
   event log, covering each rule family and running each scenario long enough to reach the
   limits it is meant to test ([golden-trace-conformance-vectors](./techniques/golden-trace-conformance-vectors.md)).
4. Write the tolerance into each vector, enforce it in the replayer, and put a ceiling on it
   ([declared-numeric-tolerance](./techniques/declared-numeric-tolerance.md)).
5. Run the suite green on the unmodified port, then plant a fault in the port, record which
   vectors fail and with what, restore the port and run green again
   ([planted-mutation-proves-the-suite](./techniques/planted-mutation-proves-the-suite.md)).
6. Keep a divergence log. Every mismatch gets an entry with a verdict before either runtime
   changes ([divergence-log-not-silent-correction](./techniques/divergence-log-not-silent-correction.md)).
7. Report what the suite does not cover: rule families no planted fault has reached, vectors
   not regenerated since the pin last moved, and any runtime or device the suite did not run on.

## Seams with neighbouring craft

Where thresholds are authored and how a checker earns trust belong to design canon as
executable law. Scenario presets for the reference simulation come from encounter balance
simulation. Replay determinism inside one runtime, a fixed timestep and a seeded generator,
belongs to the runtime observation subject. Scoring a generated artifact against a reference
is reference parity gating, which grades closeness on a scale. This subject is about rules
equivalence within a declared tolerance, which is pass or fail per field.
