# Headless replay against the rules

The named concern: a rule that reads tracked input needs a regression test that runs without
a device, and that test is only worth anything if it runs the rule the game runs.

## When an input rule must be regression-tested without a device, feed recorded samples to the shipped rule code, because a test double proves only the double

The replay drives the same rule path the live game uses, from the sample stream onward, with
no rendering and no sensor. Determinism of the run itself is owned by the deterministic
headless timestep technique; this technique only requires that the replay use it. The
expected outcome of each clip is written down by a person who watched it, not derived from
the rule's own output on that clip.

## When a replay diverges from the live session it recorded, find the input-path difference before changing any rule, because the divergence is a finding

Compare what the live game saw with what the replay fed it: sample order, timestamps, held
samples, dropped frames, confidence. A replay that cannot reproduce its own session is not
yet evidence about the rule. Record the cause, and fix the replay path or the recording
before judging the rule.

## When wiring recorded input into an automated gate, bind the verdict to the clips and the rules revision, and place it on the evidence ladder

The gate output names the clips read and the rules revision judged. A replay pass is
headless evidence about the rules. It is reported as that, per tiers of truth, and never as
device evidence. A gate that has no clips for a rule reports the rule as unmeasured, not as
passing.

## Decision rules

- **When a rule has no clip that exercises its failure path, add one** before trusting the
  replay for that rule.
- **When the replay passes and a person finds a regression, add the person's session to the
  corpus** and record the miss. That is the raw data for the evidence gate this subject owes.
- **When the expected outcome was generated by running the rule, the test is circular.**
  Relabel it a snapshot: a change detector that says the behaviour moved, not a check that
  it is right.

## Boundary: where the circularity rule inverts, and where it misses

The rule above holds for the same rule on the same input. It does not hold for the two cases
below, and an application against a real tree found both.

**An expectation taken from the rule on a different input path is a check, not a snapshot.**
Run the shipped rule on the clean clip, then on the same clip passed through a model of the
device's input path: held samples, a lower camera rate, extrapolation. Compare the two
verdicts. This is the divergence section above, done before any device exists. The rule's
output is the reference, but the claim being tested is that the input path does not change
the verdict, and a wrong rule does not make that claim pass. Keep it as a check, with two
conditions.

- **It needs an anchor on the reference.** If the rule fires nothing on the clean clip, it
  also fires nothing on the degraded one, and the two match. The test must fail when the
  reference itself is empty or wrong. A differential with no such guard passes for a rule
  that never fires.
- **It needs a known-miss list that fails both ways.** A case that is expected to diverge is
  listed. A listed case that stops diverging also fails, so the list cannot go stale.

**An oracle that recomputes the rule's own threshold is a copy of the rule.** An expected
value can be written in the test rather than captured from a run, and still be derived from
the rule's own constant, for example an expected onset found with the rule's speed
threshold. If that constant is wrong, the test and the rule move together. This is the
"replay against a copy of the rule" failure, moved into the oracle. Take the expected value
from the clip's authored intent or from a spec number. Where the constant is the very thing
under test, name the test a consistency check.

A pinned snapshot is still useful when the claim is "this change moves nothing", as in a
refactor guard. Label it a snapshot in its name or its output, not only in a comment. A
two-sided ratchet, where a gain also fails until the table is edited and each figure carries
its cause, is the strongest kind of snapshot. It is still not evidence that the figure is
right.

## When not to use it

Not for judging feel, comfort or the sensor's behaviour. Those need a person on the device.
