# Seed determinism contract

A seed is only worth exposing if it is a stated contract. This technique writes that
contract, makes it mechanically true, and — the part teams skip — states its limits.

## The four terms

**The same seed, the same algorithm, the same generator version, and the same parameter
set produce the same plan.** Drop any one term and the guarantee is void. All four must be
named in the promise and all four must be stored with the output, because a seed alone is
a number without its basis, and a number without its basis is not information
([a-number-carries-its-unit-and-basis](../../../_laws.md#a-number-carries-its-unit-and-basis)).

State the negative half in the same breath, in the interface where the designer sees the
seed:

- The same seed on a **different algorithm** produces an unrelated level. Nothing is
  shared but the number.
- The same seed with a **different parameter set** produces a different level. This is the
  point of parameters.
- The same seed on a **different generator version** may produce a different level, and
  routinely will.

## One stream, and nothing else

Every draw in the pipeline comes from the seeded stream. Not the layout pass only — the
decoration pass, the tie-breaks, the shuffle that picks which of two equally good corridors
to keep, the jitter on a prop offset. One call to an ambient global generator anywhere
makes the whole run irreproducible, and the failure is nearly undetectable because most
runs still look plausible; the level differs in ways no one photographs.

This is [one-authority-per-quantity](../../../_laws.md#one-authority-per-quantity) applied to
randomness: exactly one stream owns the run's entropy, and every consumer draws from it.
The enforcement that works is structural, not cultural — the generation code is given a
generator handle and has no access to a global one, so an unseeded draw is a compile-time
impossibility rather than a review comment. Where the language cannot enforce it, a lint
rule banning the ambient call inside the generation module is the next best thing; a
convention documented in a wiki is not an enforcement mechanism.

Two secondary disciplines protect the stream once it exists. **Draw order is part of the
contract** — inserting a new draw ahead of an existing one shifts everything downstream, so
new passes append rather than interleave where that is achievable. And **consume a draw
only when the outcome depends on it**; a draw taken for a branch that was never in play
costs nothing in the result and silently shifts every draw after it.

## Resolve the seed once, and declare determinism per generator

Two structural rules keep the contract from being re-litigated at every call site.

**The designer types a label; the pipeline resolves it to a value exactly once**, at the
moment the request is built, and stores both. Re-deriving the numeric seed from the label
at each call site is the classic way two stages of one run diverge — a second hashing
implementation, a different trim of the whitespace, a different treatment of the empty
string, and the preview and the bake disagree while both claim the same seed. One authority
per quantity, and the quantity here is the resolved seed.

**Determinism is a declared property of each generator, not an assumption about all of
them.** A pipeline stage where a language model authors the generator freehand is *not*
deterministic and must say so — `unenforced` is a legitimate and necessary value, and it is
far better than a determinism claim that quietly does not hold. A caller reading the
declaration then knows whether it may offer a seed field at all.

## The version bump

A seed that survives a generator upgrade is a promise nobody can keep. Improving a corridor
router, changing a tie-break, adding a pass — each legitimately changes the output for a
fixed seed. Teams that promised stability across versions ship a silent regression the first
time they optimise, and then either freeze the algorithm or break the promise quietly.

The contract that works instead:

- **The generator version is stored with every plan**, alongside the seed and the parameter
  set.
- **A stored plan's stored output is the authority for that plan**, not a regeneration.
  Regenerating an old plan under a new version is a *new* plan and is labelled as one.
- **When the stored version differs from the current one, say so rather than silently
  regenerating.** "This plan was generated by an earlier version; regenerating will produce
  a different level" is a sentence the designer can act on. Silently producing a different
  level under the same seed destroys trust in the seed permanently.
- **Bump the version whenever draw order or algorithm behaviour changes**, including for
  changes that "should not matter". If the team cannot tell whether a change matters, it
  matters.

## Decision rules

- **When a designer wants a specific level kept, store the plan, not the seed.** The seed
  is a compact regeneration recipe; the plan is the artifact. Storing only the seed makes
  the level hostage to the generator's future.
- **When a seed is not supplied, generate one and show it.** An unshown seed is an
  irreproducible run wearing the word "seeded"; the designer who liked that result has no
  way back to it.
- **When exposing a seed as text, keep it exact.** A seed rendered through a lossy display
  format — truncated, reformatted, rounded — reproduces a different level, and the report
  will be "the seed does not work".

## When not to use this

- **Where reproducibility is not wanted** — a per-session variation intended to differ for
  every player. Then say so explicitly rather than exposing a seed nobody can use; a seed
  field on a deliberately non-reproducible surface is worse than none.
- **For output that is not fully determined by the generator**, such as a plan a
  language model contributes to under sampling. There the seed governs only the
  deterministic stages, and the contract must say which stages it covers rather than
  claiming the whole pipeline.
