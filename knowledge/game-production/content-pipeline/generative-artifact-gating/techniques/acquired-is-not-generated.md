# Acquired is not generated

## The concern

The origin field this subject carries has three values - generated, constructed, stand-in -
and all three describe work done by the line itself. There is a fourth way a slot gets
filled, and it happens without anyone deciding it should: the asset was **acquired**.
Somebody, or some agent, downloaded it, bought it, or pulled it from a library of assets
the project already holds. A producer that is given network access and no stated rule about
where assets may come from will do this on its own, because a ready-made asset is the
shortest path to a filled slot.

An acquired asset slips through the representation rule. The disjointness rule says that a
generated asset is always a reference to a served location and a stand-in is always a
locally computed value. A downloaded file is also a served reference. So the gate follows
the pointer, finds a real file, and passes it at the advancing tier as generated work. In
fact nothing behind it matches that label: there is no generation history, no producer and
no prompt. It also carries one thing a generated candidate of this line does not have. It
has a **licence**, set by someone outside the line, and that licence decides whether the
asset may ship at all.

## The rule

Acquisition is **declared by whatever brought the asset in**, as its own record on the
candidate: the source, the reference that was acquired, and the licence exactly as the
source stated it at the moment of acquisition. The gate reads that record **before** it
applies the served-reference rule, and it grades the asset on the record:

| What is in the slot | Verdict | Why |
| --- | --- | --- |
| Acquired, licence recorded | **pass, naming the source and the licence**, never labelled generated | the evidence of an acquired asset is its acquisition record, the way a history is a generated asset's |
| Acquired, licence blank or missing | **defer, naming the missing licence**, at the rung a person resolves | an unrecorded licence is unknown, not unrestricted; no generator run and no config edit fixes it |
| No acquisition record, served reference | the existing generated-asset row | unchanged |

The licence field is never defaulted. When a blank licence renders as nothing, readers take
it as *no restriction*, and that is the reading the deferral is there to prevent. The same
applies at every later boundary the asset crosses. A package, manifest or delivery that
includes an acquired file carries that file's licence with it. Clearing the licence is
someone else's decision. This gate only guarantees that the facts needed for that decision
reach the person making it.

## Declare it; never infer it from where the file sits

The cheap repair is to infer the origin from the file's location: anything under the
generators' output directory counts as generated, and anything else counts as acquired. That
repair fails in both directions, and neither failure is rare:

- An acquired asset gets copied or re-served into the location the generators write to (a
  library import, a cache, a normalising step). The inference then reads it as generated and
  passes it without any licence.
- A generated asset gets recorded by some other address, such as the object path it was
  given after an engine import, or a path in a content tree. The inference then reads it as
  acquired and defers finished work over a licence that was never owed.

Only a declaration tells the two apart, and the declaration has to be written at the moment
of acquisition, the one point when the source, the reference and the terms are all still in
hand. This is the rule the subject already holds for the other three origin values, and
acquisition does not relax it.

**Which origins a class accepts is also a declaration.** It lives next to the class's
terminal producer: generate only, construct, or acquire from a named source.

That declaration matters because of what the gate cannot see. It cannot catch an
acquisition nobody declared. An undeclared download still looks like a served reference and
still passes as generated. This technique gives the gate a correct verdict for an
acquisition that has been recorded. Getting it recorded in the first place is the job of the
producer and its instructions. So a producer allowed to acquire must write the record, and a
producer that is not allowed to acquire must be told so explicitly.

## When not to use it

- **Output of a paid generation provider.** The provider's terms for generated output are a
  question about which providers are allowed at all, and the neighbouring provider-auditing
  subject owns that. This technique covers assets that no generator in the line produced.
- **A line whose producers cannot acquire.** If no producer can reach a network or a
  library, state that in the class declaration and skip the record. Do not add an empty
  acquisition field to every candidate.
- **As a licence decision.** A recorded licence is evidence. It is not clearance. A gate
  that passes an acquired asset has confirmed that the terms are known and named, not that
  they allow the intended use.
- **As a quality verdict.** An acquired asset still has to be graded on the class's own
  rubric. Knowing where it came from says nothing about whether it fits.
