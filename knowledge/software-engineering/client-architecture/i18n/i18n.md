# Localization

Localization is the discipline of treating every string a user reads as
**data with an audience**, not as an incidental byproduct of writing code.
The moment a product ships in more than one language — and the decision to
do so is almost always made after thousands of strings already exist — every
piece of display text becomes a record in a catalog: authored once in a
source language, translated into each shipped locale, resolved at runtime by
the viewer's preference. A product that gets this right feels native in
every language it claims to support. A product that gets it half right is
worse than one that never tried: a screen that is 80% translated and 20%
source-language reads as *broken*, not as *in progress*, because the user
cannot tell whether the mixed language is a bug, a stale build, or contempt.

The subject decomposes into a small number of load-bearing convictions.

## The catalog is one authority

All display strings live in **one catalog**, keyed, with the source language
as the authoritative text and every other locale as a derived translation of
it. Every consumer — components, notification templates, error surfaces,
exported documents — resolves strings through the catalog by key. This is
[one authority per vocabulary](../../_laws.md#one-authority-per-vocabulary)
applied to the largest vocabulary a product has: its entire voice.

Two corollaries follow immediately:

- **A hardcoded display string is a bug, not a shortcut.** Text typed
  directly into markup is invisible to translators, to completeness gates,
  to copy review, and to every future language. It works perfectly in the
  source locale, which is exactly why it survives review — the defect is
  observable only from a locale the reviewer is not using. Enforcement
  therefore cannot be cultural; it must be mechanical (the
  [string-extraction-enforcement](./techniques/string-extraction-enforcement.md)
  technique).
- **Keys are addresses, not sentences.** A key names the *place and purpose*
  of a string (`section.save_button`), never its current wording. Keys named
  after their source-language text go stale on the first copy edit and force
  a rename across every locale for a wording change in one.

## Two species: tokens and strings

Systems traffic in **machine tokens** — status enums, category identifiers,
mode strings — that cross process boundaries, land in storage, and drive
logic. Users read **display strings**. These are different species and the
boundary between them is a design decision, not an accident:

- Tokens are stable, language-agnostic, compared and persisted. They never
  change when copy changes.
- Display strings are per-locale, owned by the catalog, and free to be
  rewritten by a copywriter without any system consequence.

Rendering a token raw ("EXEC_QUEUED") is the visible failure; the subtler
one is the reverse — branching logic on a translated label, which breaks in
every locale but the one the author tested. The mapping layer between the
species is the [token-label-separation](./techniques/token-label-separation.md)
technique.

## The completeness question — key parity is not value parity

"Are we fully translated?" hides three different questions, and conflating
them produces the classic localization lie:

- **Key parity**: does every locale define every key the source defines,
  and nothing more? This is cheap to check and most gates check only this.
- **Value parity**: does every locale's value differ from the source where
  it should? A locale file mechanically seeded by copying the source passes
  key parity at 100% while being **byte-identical source text** behind a
  green "0 missing" report.
- **Domain coverage**: does the catalog's key space cover the vocabularies
  it exists to label? A token minted in a backend enum but never given any
  label is absent *identically from every locale* — a symmetric absence
  that no locale-vs-locale comparison can see, by construction.

A completeness gate that reads key sets is observing a proxy for the thing
it gates ([the gate must see its target](../../_laws.md#gate-sees-target)), and
the proxy diverges precisely when someone bulk-seeds a locale to silence the
gate. "0 missing" is a count, and [a count carries its
predicate](../../_laws.md#count-carries-predicate): missing *keys* is not
missing *translations*, and neither is a missing *label for a vocabulary
member the catalog never met*. All three are gated, extras (stale keys that
survived a rename) fail as hard as gaps, and each gate attaches to the edit
that creates its defect — catalog edits for parity, vocabulary edits for
domain coverage — at commit, not in a weekly report. The full standard,
including the extract → per-locale fill → validating merge pipeline that
makes closing gaps cheap enough to demand in the same change, is the
[completeness-gates](./techniques/completeness-gates.md) technique.

## Fallback is a safety net, not a shipping state

At runtime, resolution must be **total**: every key access produces
renderable text in some language, in every reachable state — missing
translation, catalog section still in flight, locale added mid-session.
The fallback chain (requested locale → source language) exists so that
translation lag degrades to *readable source text*, never to a raw key
(`section.save_button` on a button is the localization equivalent of a
stack trace in a dialog) and never to an empty string. One boundary on
that totality: it is the *label* path being promised. A key that carries a
record's own content rather than a label on one is allowed to resolve to
*absent* — the consumer then omits the record and shows a real empty state,
because a card whose text is its own address is not a degraded card.

But fallback semantics create a moral hazard: a good fallback makes gaps
invisible in the source locale, which is where the whole team lives. That
is exactly why fallback is a runtime safety net and completeness is a
*build-time* gate — the two are a pair, and a team that ships on the
strength of its fallback has quietly repealed its completeness standard.

## Structurally complete is not fit to ship

Every gate named so far reads the catalog's **structure**: which keys
exist, whether a value differs from the source, whether the placeholder set
matches. A locale can pass all of them and still be unfit for a reader, in
two ways no parity board has any way to express.

The first is corruption *below* the level of structure. A catalog file read
once in the wrong character encoding and saved back parses cleanly, holds
every key, and differs from the source in every value — so key parity,
value parity and placeholder integrity all report green while every
accented word in it has become punctuation soup. No type system can see
this, because the damage is inside string values and a string is a string;
the only detector is a byte-level signature, and because one careless save
re-introduces it, that detector is a standing gate rather than a cleanup
task ([encoding-corruption-ratchet](./techniques/encoding-corruption-ratchet.md)).

The second is trust. A locale can be structurally whole and still be
unreviewed, terminologically inconsistent with the glossary, or freshly
repaired by nobody who reads the language — so the product needs a control
that withdraws it from readers entirely rather than exposing it and hoping.
Whole-locale withdrawal is the honest move for exactly the reason a
partially translated screen reads as broken: a reader cannot grade a
language, they can only trust it or not
([incomplete-bundle-kill-switch](./techniques/incomplete-bundle-kill-switch.md)).

Both of these sit on the **consumption** side of localization — is this
bundle fit to reach a reader, and what does the reader see when it is not —
while the production side of the same material, where translated units are
pinned to the source text they were made from and a source edit is
classified into the units it forces back through translation, belongs to
the `hash-pinned-translation-pipeline` subject. The rule for picking is
whether the question is asked while the bundle is being made or once it
already exists.

## Bundle economics

A mature catalog is large — tens of thousands of keys, megabytes per locale
— and a user session touches a fraction of it in exactly one language.
Shipping every locale in the main bundle taxes every user for every
language; shipping the whole active locale up front taxes first paint for
strings behind screens the user may never open. The standard is
**sectioned lazy loading**: the catalog splits along the product's
navigation seams, each section becomes an independently loadable unit, the
active route's sections preload, and the rest load on first access. Note
what splitting creates: a **delivery layer** with its own completeness
obligation — a string that is present and translated but never *fetched*
renders fallback text forever and looks identical, at every catalog gate,
to one that is shown. The
generated artifacts this requires — typed key trees, per-section files —
are derived values, and [a stored derivation names its
recomputation](../../_laws.md#derivation-names-recomputation): the build
pipeline regenerates them; nobody edits them. Architecture and mechanics
are the [catalog-architecture](./techniques/catalog-architecture.md)
technique; what the user experiences at startup, on language switch, and
in right-to-left locales is the [locale-runtime](./techniques/locale-runtime.md)
technique.

## Type is a property of the script, not of the product

A catalog that resolves correctly can still be unreadable. Line height,
font stack and letter spacing were all chosen by looking at one script and
none of them transfers: a script with stacked marks clips at the leading
that flatters the source language, a dense logographic script suffocates at
it, and the tracking that tightens a Latin headline pulls a connected
script's letters out of their joins. State the corrections **per script**,
resolved from the active locale — never as a list of per-locale overrides,
because that list grows with the number of languages, which keeps growing,
while the values are determined by the number of scripts, which barely
moves; the fourth language of an already-solved script then silently
inherits source-language typography the day somebody adds it. The
[script-aware-presentation](./techniques/script-aware-presentation.md)
technique carries the rule and the reader-of-the-script review that is the
only way to verify it, no gate being able to.

## Grammar is not string surgery

Translated sentences are not built by concatenation. Word order, plural
category counts, gender agreement, and punctuation all vary by language, so
the unit of translation is the **complete message** with typed placeholders
— and placeholder integrity is a merge-gate invariant, because a translator
deleting `{count}` is a runtime defect delivered through a copy change. The
[interpolation-and-plurals](./techniques/interpolation-and-plurals.md)
technique carries the standard, including the glossary of terms that must
*not* be translated (brand names, protocol names, technical identifiers).

## What rides the catalog and what never does

Everything user-facing rides the catalog — including failure copy. Error
messages are product copy with the same completeness obligations as any
button label; the error-handling subject's
[user-facing-mapping](../../backend-platform/resilience/error-handling/techniques/user-facing-mapping.md)
technique specifies the registry side of that contract (entries store
catalog keys, never sentences), and this subject supplies the catalog it
rides on.

Never in the catalog: user-generated content (names, descriptions, prompts
the user wrote — translating their words is corruption, not service), log
and telemetry text (its audience is operators and aggregation tooling, and
translated logs shard one cause into fourteen wordings), and machine tokens
themselves (they are identity, not copy).

## The techniques

- [catalog-architecture](./techniques/catalog-architecture.md) — one source
  catalog, typed access via codegen, section splitting for lazy loading,
  fallback merging.
- [completeness-gates](./techniques/completeness-gates.md) — key parity AND
  value parity, extras-always-fail, commit-time gap blocking, the
  translation pipeline.
- [token-label-separation](./techniques/token-label-separation.md) — machine
  tokens never rendered raw; per-category token→label maps; logic never
  branches on labels.
- [interpolation-and-plurals](./techniques/interpolation-and-plurals.md) —
  complete messages with typed placeholders, plural variants, glossary
  exclusions, locale-aware formatting.
- [locale-runtime](./techniques/locale-runtime.md) — first paint in the
  user's language, section preloading, switch-intent prefetch,
  right-to-left, pseudo-locale testing.
- [string-extraction-enforcement](./techniques/string-extraction-enforcement.md)
  — mechanical detection of hardcoded display text, enforcement posture,
  fix-as-you-touch migration.
- [encoding-corruption-ratchet](./techniques/encoding-corruption-ratchet.md)
  — the byte-level defect every structural gate is blind to, its detection
  signature, a per-file baseline nobody may exceed, a hard-zero lane for
  what every reader receives.
- [incomplete-bundle-kill-switch](./techniques/incomplete-bundle-kill-switch.md)
  — one flag per locale that gates the switcher, no-ops the setter, and
  scrubs the persisted value on rehydration.
- [script-aware-presentation](./techniques/script-aware-presentation.md)
  — per-script font stack, line height and tracking, keyed off the resolved
  locale rather than enumerated per language.
