# External anchor versus internal id - React/Next.js implementation (a marketing article page)

The page is a long-form article with a table of contents, per-heading
permalinks and an FAQ whose questions each carry a copy-link button. Two
vocabularies sit under it, and they were not built the same way.

## What the tree showed

- **Headings: all nine carry an authored id.** The id is a declared field
  beside the heading text; rewording a heading moves nothing. This is the
  technique's external address, owned by history, already in place.
- **FAQ items: none of the four carried one.** The effective id was derived
  from the question text, one function shared by the renderer, the hash-open
  island and the validator. That function is the single authority the
  technique asks for, and it is also why the failure was invisible: every
  consumer agreed with every other, so no consistency check could fire.
  The copy button publishes that derived id into URLs.
- The validator checks that ids are unique, non-empty and not shadowed, and
  that every in-page link resolves. It checks nothing about an id's stability
  over time, because a stable-over-time rule needs a reference to compare
  against.

## A/B (seam chosen to falsify)

Question that could kill the finding: has a derived FAQ id ever actually moved,
or is the risk only theoretical? Replay of the article data over its four
revisions (positive control: the replay's slug function reproduces a known
published id): effective heading and FAQ ids, 13 each revision, **0 vanished
across 3 transitions**. The risk is latent, not an incident; no question has
been reworded yet. That bounds the claim: the change is prevention, and the
tree gives no evidence of a broken link in the wild.

Target: does rewording a question move its published id. Floor: rendered
ids unchanged for all four items, and the unit suite green.

| Arm | Reword one question | Unit suite |
| --- | --- | --- |
| A, ids derived from question text | the id changes; **4,384 of 4,384 pass, 0 fail** - nothing notices | green |
| B, ids authored, equal to the slugs already published | id unchanged; a new test pins the four-id set and fails if any item loses its id | 4,385 pass, 0 fail |

The new test was also run against the unpinned article with the reword
applied: it fails (6 of 7 pass), so the guard can see the drift and is not
passing by construction. The pinned values are the slugs already in
circulation, not tidier names - choosing nicer ids would itself have been the
broken-link event.

## What the realization cannot do

- It does not alias an id after a deliberate retirement; the page has no
  alias table, and the one place a retired address would be mapped (a
  resolution point at hash time) does not exist yet. Today the test makes the
  change loud; it does not make it safe.
- Articles generated from live data (a performance snapshot, per-visitor
  microsites) still derive their FAQ ids from the question text, correctly:
  there the text is regenerated by the pipeline and the id is a function of
  it. The pin applies to the hand-authored article only.
- It was not run in a browser; the check is on the data and the shared id
  function, not on the rendered DOM.
