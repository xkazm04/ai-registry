# Post-merge regeneration

Some derived artifacts cannot survive being regenerated by every concurrent
change. The signature is specific: the artifact's content carries
**positional references into its sources** — line numbers, offsets, ordinal
keys — so any edit anywhere upstream shifts references for entries that
have nothing to do with that edit. Two authors touching unrelated parts of
the tree both regenerate, both get large diffs, and the diffs collide on
lines neither of them wrote. Every merge then costs a manual resolution
whose only correct outcome is to throw both copies away and regenerate
again.

That is not a coordination failure to be managed. It is a property of the
artifact, and the fix is to change *when* it is produced: **forbid the
artifact from the change entirely, and regenerate it once, after the merge,
in a serialized job.**

## Forbid it where changes are described, not only where they are reviewed

The rule has to reach the author before the artifact exists, because the
expensive moment is not the review — it is the contributor who ran the
generator locally, committed what it produced, and now has a change nobody
can merge cleanly.

Three places, and all three are cheap:

- **The contribution guide** states the rule as a prohibition with its
  reason and its recovery: do not include this artifact; if you ran the
  generator and it changed, revert it before proposing the change.
- **The change template's checklist** carries the same line, so it is in
  front of every author at the moment they open the proposal. A checklist
  item is not enforcement, but this rule's violations are visible in the
  diff, which is the one shape where a reviewer's eye is a real
  detector — the forbidden path either appears in the file list or it does
  not.
- **A path-based check**, where the population is worth it: the proposed
  change fails if it touches the generated root at all. This is the only
  form that actually refuses, and it is worth having precisely because the
  rule is otherwise enforced by attention.

Naming the exception is part of the rule. There is usually one legitimate
class of change that *does* carry the artifact — the change whose entire
purpose is that artifact's content. Say which, so the prohibition does not
read as absolute and get quietly ignored the first time someone needs the
exception.

## Regenerate once, on the merge, serialized

After the merge, one job regenerates and commits the result. Three
properties make it work and each has a failure attached:

- **Serialized, never cancelled.** The job runs one at a time, and a queued
  run is *waited for*, not superseded. Cancelling the in-flight run on a
  newer merge is the tempting default and it drops the regeneration for
  whatever merged first, leaving the artifact stale with nothing red.
- **It does not trigger itself.** The commit it pushes is a change to the
  branch it watches. Break the loop explicitly — skip runs whose author is
  the job's own identity, or mark the commit so the trigger declines it —
  and prefer the identity check, because a marker in a message is one
  careless edit away from an infinite loop.
- **The artifact is stale between merge and commit.** That window is real
  and must be tolerable: anything consuming the artifact reads a version
  one merge behind for the length of one job. Where that is not
  acceptable, this technique is the wrong choice and the artifact belongs
  in the change with a drift gate in front of it.

## The allowlist is what makes an automated commit safe

This is the reusable half, and it applies to any job that commits
generated output anywhere.

A regenerating job that stages the whole tree and commits it is a writer
with no validation door. The generator is code; code has defects; and a
generator that writes outside its declared output root, or a compromised
one that writes a source file, gets that write committed and pushed under
an automated identity nobody reviews. The credential was scoped to
"contents: write" because the job legitimately needs to commit — the scope
is not the control.

The control is downstream of the generator and upstream of the commit:
**stage everything, then enumerate what got staged and fail if any path or
any change status falls outside an allowlist.**

- **Paths are matched against a declared pattern**, which is the
  generator's output root and nothing else. The registry already declares
  that root ([task-registry-design](./task-registry-design.md)); the
  allowlist is that declaration used as an assertion.
- **Statuses are constrained too**, not only paths. Additions and
  modifications inside the output root are expected; deletions and renames
  usually are not, and a generator that suddenly deletes half its own
  output has failed in a way an add/modify-only allowlist catches and a
  path-only allowlist does not.
- **Anything outside is a hard failure**, printed with the offending
  entries, before any commit is attempted. Not a warning, not a filter that
  quietly drops the extra paths — dropping them would hide the exact event
  worth investigating.

This is [one-validation-door](../../../../_laws.md#one-validation-door)
applied to a branch: the automated writer is enumerable and it passes
through one place that checks what it is about to write. It costs a few
lines and it is the difference between a generator defect producing a
noisy failed job and producing an unreviewed source commit on the main
line.

## Boundary: drift check or merge regeneration

The obvious alternative is the one this subject already owns — a drift
gate that regenerates in the pipeline and fails the change until its author
commits the fresh output
([drift-gating](./drift-gating.md)). Both are legitimate; the artifact
decides which.

| | drift check on the change | regenerate after the merge |
|---|---|---|
| **right when** | the artifact is stable under unrelated edits: two authors regenerating from different branches produce diffs that do not overlap | the artifact is unstable under unrelated edits: positional references, global ordering, or ordinal keys shift on any upstream change |
| **conflicts** | real — a collision means two changes genuinely touched the same derived content | manufactured — a collision between authors who wrote none of the conflicting lines |
| **the artifact on the main line** | always current | one merge behind, for the length of one job |
| **who regenerates** | the author, locally, with a named command | one job, once, with the same command |

The discriminator is one question, and it is answerable by experiment
rather than argument: *regenerate this artifact from two branches that
touched unrelated things — do the diffs overlap?* If they do not, keep the
drift check; it is the stronger control and it keeps the artifact current.
If they do, no amount of merge discipline will fix it, because the conflict
is being produced by the generator's own output shape.

The two do not compose on the same artifact. A drift check *plus*
merge regeneration means the change is refused for not containing the
artifact it is forbidden to contain.

## Decision rules

- Decide by experiment: overlapping diffs from unrelated branches means the
  artifact is unstable and belongs after the merge.
- Forbid it in the contribution guide, in the change template, and — where
  the population warrants — with a path check that actually refuses.
- Name the one class of change that legitimately carries the artifact.
- Regenerate in a serialized job that queues rather than cancels, and that
  cannot trigger itself.
- Stage everything, then fail on any staged path or status outside the
  generator's declared output root. Never filter; always fail.
- Accept and state the staleness window; where it is unacceptable, use the
  drift check instead.
