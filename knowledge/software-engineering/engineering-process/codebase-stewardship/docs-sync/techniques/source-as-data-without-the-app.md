# Reading source as data, without the application

The moment documentation becomes typed records inside the application rather
than files on disk, every gate over it faces the same question: **how does a
checker read the application's own declarations without becoming part of the
application?** The registry of topics, the catalog of categories, the map from
identifier to body, the translation tables — all of them are now source
modules, and the checker needs their contents.

The obvious answer is to import them, and it is the one wrong answer. An
importing checker inherits the whole build: the bundler, the path aliases, the
environment variables read at module scope, and every transitive import the
registry happens to pull in — a component, a client library, something that
touches a browser global. From that moment the gate is **unavailable exactly
when the build is broken**, which is the only time anyone urgently wants to
know whether the catalog is still consistent. It also acquires a second
failure surface with nothing to do with what it checks: a change to module
resolution breaks the documentation gate, and the person who made it will
never guess why.

The gate must read **the authority itself**
([one-authority-per-vocabulary](../../../../_laws.md#one-authority-per-vocabulary)
— the registry in the source is the definition, and a checker reading a
hand-maintained mirror of it is checking the mirror) but read it as **data**,
through a door the application's build does not stand in
([gate-sees-target](../../../../_laws.md#gate-sees-target)). Two strategies do
that, and they have opposite failure modes.

## Strategy A — pattern-scrape the source

Read the file as text and match the declarations with patterns. No compiler, no
dependencies, no build, runs on any machine that can read a file. It is
genuinely the right tool more often than its reputation suggests: it is fast,
it survives a broken build entirely, and it works across many files at once,
which is what you want when the thing you are counting is spread over a tree
rather than declared in one authority.

Its failure mode is one word: **silently partial**. The pattern matches every
entry written in the shape it expects and skips, without a sound, every entry
written any other way — an entry spread from another object, a computed key, a
block generated by a helper, a record that moved to a second file last month,
one whose fields were reordered so a two-line pattern no longer spans them. The
scrape then hands the checker a population, and the checker does its work
correctly over that population, and reports success.

**That is the trap, stated plainly: a partial scrape reports success over the
fraction it managed to parse.** Nothing errors. The exit code is zero and it is
honestly earned — everything the checker was given did check out. The defect is
that the denominator was chosen by a regular expression and never disclosed
([failure-not-empty-success](../../../../_laws.md#failure-not-empty-success): the
result and the instrument's reach are being reported as one number).

So a scrape is only admissible with the denominator defended:

- **Assert the parsed population against a real floor.** The floor most
  implementations write is "at least one", which catches a total parse failure
  and nothing else — it cannot tell twelve records from a hundred and sixteen.
  A useful floor is a second, independently derived count: the occurrences of
  the declaration keyword, the number of top-level delimiters, the count another
  tool already knows. Disagreement between the two is the finding.
- **Print the count with its predicate every time**, pass or fail, so the number
  travels with what produced it and a reviewer can notice it halving.
- **Never make a completeness claim from a scrape alone.** Coverage, bijection,
  "every record has a body" — those are census questions, and a census over an
  unknown denominator is the exact lie this subject exists to name.

## Strategy B — transpile and evaluate with module resolution refused

Strip the type annotations from the single source file, evaluate the result in
an isolated context, and install a module resolver **that throws on every
request**. You get the real values: the actual records, with their actual
nesting, exactly as the application will see them. It is exact, and it fails
loudly.

The refusal is the design, not a limitation to apologise for. A registry is
supposed to be self-contained data; a resolver that throws turns that
expectation into an assertion. The day someone adds an import to the registry —
a helper, a shared constant, a locale object pulled from elsewhere — the gate
stops with a message naming the specifier it was asked for, at the exact line
that reached outside. That is the correct outcome twice over: the checker
refuses to guess, and the team learns that their data module has quietly become
code, which is a fact worth learning before something else depends on it.

Three disciplines make the sandbox safe to run in a gate. Give it **no ambient
capability** — no filesystem, no network, no process handles — so the evaluated
file cannot do anything but produce a value. Give it a **step or time bound**,
because a file that loops takes the build with it. And **assert the export you
expected actually came back**, with the shape you expected: an evaluation that
succeeds and yields nothing must be an error, not an empty result, or the
strategy has quietly reinvented Strategy A's failure with more machinery.

## Choosing, and the third option to reject

Reach for **evaluation** when the artifact is meant to be a pure data module,
when exactness is the point — coverage, counts that travel, bijection between
two registries — and when a refusal carries useful information. Reach for the
**scrape** when the data is a fragment embedded in genuine code, when you are
sweeping many files rather than reading one authority, when a *lower bound* is
all the claim needs, or when no parser for the dialect is available at all.

The rule that decides the ambiguous cases: **if the check's conclusion is a
statement about the whole population, the reader must be exact.** A gate saying
"none of these are broken" is making a claim about a set, and a scrape does not
know the set.

There is a third option that looks like it dominates both — have the build emit
the registry as a plain data file and let the gate read that. Sometimes it is
right, and it is the natural move when several tools need the same data. But it
reintroduces precisely the dependency the technique exists to remove, one step
further away where it is harder to see: the emitted file is a derived artifact
that can be stale, and a gate reading a stale derivative is reading a proxy
([gate-sees-target](../../../../_laws.md#gate-sees-target) again). If you take
this route, the gate regenerates the file itself as its first act and fails when
regeneration fails — never reads a committed copy and trusts it.

## What evaluation buys that scraping cannot: shape

The strongest reason to pay for the sandbox is that it returns **structure**,
and structure enables the comparison a scrape can only approximate: walk a
reference record and the candidate record together, and report every place
their shapes diverge — a missing key, a value of the wrong kind, a list of the
wrong length, a nested object flattened to a string.

One rule inside that walk earns its own sentence, because it is the one most
often missed: **an empty value is a failure, not a pass.** A key that exists and
holds an empty string satisfies "the key is present" and satisfies nothing a
reader cares about. Placeholder-shaped content is the characteristic residue of
a half-finished record — a topic scaffolded and never written, a translation
stubbed to unblock a build — and a checker that tests only for key presence
certifies it as complete. Test presence *and* content, name the two conditions
differently in the output ("missing" and "empty" are different work for
different people), and the gate reports the state of the corpus rather than the
state of its key set.
