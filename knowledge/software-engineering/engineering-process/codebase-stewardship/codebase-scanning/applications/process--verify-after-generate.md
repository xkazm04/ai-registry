# A consuming repo's audit protocol for a model-generated context map

`gravitone-gcloud` does not own the scanner that produces its context map — an
external app generates the map from its own database over a loopback bridge,
and the repo holds only the exported artifact. The whole protocol therefore
lives in the repo's own agent instructions, `CLAUDE.md:24-168`, and it is
written as a consumer's contract rather than a generator's.

## The artifact is scoped by its readers, not its author

The framing sentence does the work: a hand edit to the map "is erased by the
next scan, and until then it is a lie that three skills read as truth"
(`CLAUDE.md:26-30`). Three named consumers read it at task start, which is what
makes a silent corruption expensive. The same boundary is stated twice more so
neither a human nor a tool can miss it — in prose for the reader
(`README.md:68-76`, "two artifacts here are generated by it and must not be
hand-edited"), and machine-readably as `boundaries.neverTouch` in
`.ai/manifest.yaml:36-39`, which repeats the lie-read-as-truth reasoning in its
own comment.

## The audit exists because a scan corrupted the map, on a date

The section is titled "ALWAYS verify the map after a scan — a scan can corrupt
it" (`CLAUDE.md:82-89`), and the paragraph under it is a measurement rather
than a caution. On 2026-08-11 a subtree scan over a one-file directory did the
*correct* thing at the policy level — it refused to create an under-band
context and re-emitted the sibling instead — and then emitted a create where an
update was called for, inserting the row a second time with a null group while
the self-heal pruned the moved paths out of the original. Two contexts under
one name, one of them ungrouped, five files double-mapped. The generator
succeeded; nothing was malformed; every consumer would have read it.

The document then refuses to scope the bug to the mode that revealed it:
"Every scan mode can do this" (`CLAUDE.md:89`). That single sentence is what
turns a post-mortem into a standing audit.

## Four checks, inlined where the operator already is

The audit ships as a runnable snippet in the same section as the trigger
instructions (`CLAUDE.md:91-102`), and its four checks map one-to-one onto the
invariant families: duplicate names, contexts with no group, mapped paths that
no longer exist on disk, and source files under the tracked directories that
appear in no context. The coverage check is computed from the tree by globbing
the source patterns and subtracting what the artifact claims — the artifact is
never asked about its own completeness.

Running it against the checked-out tree on 2026-08-24 returns 10 contexts, no
duplicates and no stale paths, and **five ungrouped contexts**. That is the
protocol's own honest weak point rather than a corruption: the null-group arm
is the one finding class with no bridge repair (`CLAUDE.md:111`, "UI-only. Say
so; the user assigns it"), and a finding class whose only remedy is a human in
a different application is the one that accumulates.

## The anti-remedy is named before the remedy

The repair for a duplicate is to retire the **husk** — "the row whose file list
is now wrong" — after reading both rows. Immediately before that, in bold, the
document forbids the tool whose name matches the symptom: "Do NOT use
`/dev-tools/dedupe-contexts` here: it keeps the *oldest* row by `created_at`
regardless of content, which in this exact case would have deleted the correct
copy and left the husk" (`CLAUDE.md:106-110`). Selection by age against a
corruption defined by content is precisely the trap; the protocol closes it by
name.

Two further constraints match the standard. Consolidation — the operation that
would merge the small per-step contexts the project is deliberately growing —
is "the user's call, never a cleanup step" (`CLAUDE.md:131-133`). And because
the bridge's mutation routes change the database and leave the exported file
untouched, every repair path ends in an explicit re-export, "and a stale file
is read as truth by the next agent" (`CLAUDE.md:113-115`).

## The drift journal, and evidence it is actually drained

When the bridge does not answer, the instruction is "do not edit
`context-map.json`, and do not write your own" — append one dated line naming
what changed and which scan is owed, and the next session that finds the bridge
alive "drains that file: it runs the scans listed, then clears the lines it
satisfied" (`CLAUDE.md:117-127`). The journal is live: `.vault/map-drift.md`
carries two open entries and a `## Resolved` section of three, each recording
which scan cleared it and what the post-scan audit returned — including the
2026-08-11 entry that notes it "required retiring a duplicate row it created".
One open entry goes further and reasons *against* the obvious scan on the
grounds of the recorded incident, choosing a full rescan over a subtree scan of
the same shape that duplicated last time.

## The metering that makes the audit necessary

A generation "costs a real LLM run, so it is a once-per-session act, not a
reflex" (`CLAUDE.md:75-76`), and a lost run id is recovered from the scan list
rather than relaunched, "never relaunch blindly, that scans the same scope
twice at full token cost" (`CLAUDE.md:78-80`). The floor is measured too: a
subtree scan of a directory under roughly eight source files "will not give you
a context; it will merge, and it may duplicate — don't spend a scan on one"
(`CLAUDE.md:147-150`). Re-running to check is exactly what this repo cannot
afford, which is why the cheap invariant audit is the instrument.
