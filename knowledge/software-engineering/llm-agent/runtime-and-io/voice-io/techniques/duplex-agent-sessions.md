# Duplex agent sessions

The two pipelines of this subject — capture→transcription and
text→synthesis→playback — assume the product owns the middle. A **duplex agent
session** is what you get when a vendor offers to own it too: one live session
that listens, decides what to say, and speaks, with the product reduced to
opening the session and reading the transcript afterward. The offer is real and
often correct: barge-in, endpointing, echo cancellation, and turn-timing are
weeks of work each, and a vendor that does nothing else does them better.

The offer also relocates the product's conversational logic into someone else's
account. That is the whole subject of this technique: **which half of the
conversation you are handing over, and what has to stay on your side of the line
so the handover stays reversible.**

## Transport or brain — decide it explicitly, once

There are exactly two shapes, and the failure mode is drifting between them
without noticing:

- **Vendor as brain.** The vendor holds the persona, decides each reply, and
  speaks it. You supply configuration and receive a transcript. Fastest to
  working speech; the conversation's behavior is now a remote configuration
  object.
- **Vendor as transport.** The vendor transcribes, detects turn boundaries, and
  speaks text you hand it — nothing more. Every reply is generated by your own
  service from your own state. Slower to build, and it must be built with speech
  pacing in mind, because a reply pipeline that takes tens of seconds is unusable
  aloud even though the same pipeline is fine in text.

The decision is not primarily about quality; it is about **where the conversation
lives when the vendor is gone**. Under the transport shape the persona, the
state, and the transcript are already yours and swapping vendors is a credential
change. Under the brain shape a swap is a rebuild.

Both shapes are legitimate. Writing down which one a given surface uses is not:
it is mandatory, because every rule below applies differently to each, and a
system with two surfaces on two different shapes and no statement of which is
which will grow code that assumes the wrong one.

## Configuration splits in two, and only one half is per-session

Every hosted agent platform divides its configuration the same way:

- **Account-side**, on the vendor's stored agent: voice, synthesis model,
  language default, the reasoning model, safety settings, and — importantly —
  *which fields a client is even allowed to override*. Changing these is a
  deploy, sometimes one that mints a new agent identity.
- **Session-side**, sent when the connection opens: the fields the account-side
  configuration has unlocked, typically the prompt, the opening line, the
  language, and voice-level parameters.

Two rules follow, and both are routinely violated.

**Never treat the split as fixed.** It moves. A field that was account-only last
quarter becomes per-session this quarter, and the workaround built against the
old boundary — a static account-wide list standing in for what should have been
per-conversation — silently stays in place long after it stopped being necessary.
Re-read the session-configuration contract on every dependency upgrade; the
capability you gave up on is the one most worth re-checking.

**The unlock is separate from the use.** Sending an override that the stored
agent has not unlocked does not fail loudly — it is ignored, and the session runs
the account-side default. That is a silent, correct-looking session with the
wrong behavior: exactly the shape of failure a gate must see
([failure-not-empty-success](../../../../_laws.md#failure-not-empty-success)). The
unlock flags and the code that sends the overrides must be derived from one
declaration, so enabling a new override cannot be half-done.

## Vendor-held configuration needs a drift gate you can run

Configuration you deploy but cannot see is configuration that drifts. Someone
edits the agent in the vendor's console to debug a call, a migration rewrites a
default, a redeploy silently mints a different identity — and the repository
still claims the old intent. The discipline that fixes it is small:

1. The intended configuration is **one structure in the repository**, consumed by
   both the deploy path and the verification path
   ([one-authority-per-vocabulary](../../../../_laws.md#one-authority-per-vocabulary)).
2. A **read-only check command** fetches the live configuration and diffs it
   field by field, printing what differs. It creates nothing and it distinguishes
   *matches* from *differs* from *could not verify* — three states, not two, or
   an unreachable vendor reads as agreement
   ([gate-sees-target](../../../../_laws.md#gate-sees-target)).
3. Deploys are treated as deploys. When creating an agent also rotates its
   identity, every environment pinning that identity is part of the change, and
   sessions already in flight keep running against the old one — which is a
   feature to state, not a bug to hide.

## The brief is not the same thing as the prompt

Under the brain shape the vendor needs a prompt, and the nearest available text
is usually the internal one: the interviewer's private notes, the agent's
knowledge of what to probe, the reviewer-only annotations. Two properties of the
session make sending that text a disclosure:

- session configuration is assembled **by the client** on most platforms, so
  anything the server sends the browser for the session is visible to the user
  who is talking to the agent;
- transcripts and configuration are retained on the vendor's side under the
  vendor's retention policy, not yours.

So the text the session carries is a **derived, audience-safe brief**, produced
from the internal one by an allow-list — enumerate the fields that may be spoken
aloud, rather than stripping the ones that may not, because a deny-list silently
passes every field added later. Where the vendor accepts server-side session
configuration instead, use it: it removes the exposure rather than sanitizing it.

## Transport choice is a reachability decision with a quality bonus

Duplex sessions arrive over either a plain socket or a peer-connection stack. The
peer-connection path usually carries the vendor's echo cancellation and
noise-suppression chain, which improves recognition — a real quality gain,
upstream of every accuracy trick you might otherwise attempt. It also demands UDP
and peer-connection support, and it is the path that restrictive corporate
networks, hardened browsers, and virtual-desktop environments break.

Treat the transport as a **capability, probed before use, with a fallback that
still works** — the ladder from the golden path, applied to transport rather than
to features. Concretely: keep the socket path viable, choose the peer-connection
path where it is reachable, expose the relay-only mode the stack offers for
networks that drop direct flows, and never let the better transport become a
requirement for talking to the product at all. Credentials differ per transport,
so the mint step branches too — one more reason the choice belongs in one place
and not in the surface that renders the call.

## The session's end is a verdict, not an event

A duplex session ends in several ways that look alike at the socket and mean
opposite things: the conversation completed, the connection failed before
anything was said, an error fired and the socket closed behind it, the user hung
up mid-sentence, a late connection arrived after the product had already given
up. Downstream — scoring, billing, retry eligibility — depends on telling them
apart, so the close handler must compute a **verdict** from what actually
happened during the session, never from the fact that a close arrived.

Two failure shapes are worth naming because both cost money or trust:

- **Errors that close cleanly.** Many stacks fire the error callback and then the
  ordinary disconnect callback. A close handler that finalizes optimistically
  will record a failed call as a completed one and bill for it.
- **Late arrivals after abandonment.** A connection that succeeds after the
  product's own timeout must be actively torn down, not adopted. Otherwise the
  user is talking into a session whose output has nowhere to go.

Because minutes are the billing unit and each session's cost is set by its
duration, the same close path is also where usage attribution belongs — with the
vendor and the session identity recorded on the record, not just a minute count
([cost-metering](../../../evaluation-and-cost/cost-metering/cost-metering.md)). Guard the *credential
mint* as the expensive operation it is: it is the step that starts the meter, so
it sits behind the lifecycle checks and a per-credential rate limit, not behind
the page that renders the button.

## Expressiveness is a product decision, not a settings upgrade

Vendors ship increasingly expressive synthesis: context-aware tone, emotion tags
emitted by the reasoning model, delivery that adapts to how the user sounds. It
reads as a pure upgrade and it is not, because **delivery carries meaning the
product may not intend to send**. Warmth after one answer and flatness after
another is feedback, whether or not the product meant to give feedback; in any
setting where the conversation is also an assessment, that is a fairness problem
before it is an aesthetics problem. Expressive tags are usually emitted by the
model, i.e. outside review, and expressive models typically cost latency against
their fast counterparts.

The evaluation is therefore behavioral, not preferential: run both
configurations over the same scripted conversations and compare on the properties
the product actually promises — language consistency, interruption count,
neutrality of delivery, time to first audio — before adopting. When the setting
is account-side only, that comparison requires **two agents**, which is a cost to
plan for rather than a reason to skip the comparison.
