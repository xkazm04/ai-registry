# Agent browser control

A coding agent that can read and write files is half a QA engineer. The other
half needs a browser: to load the page it just changed, find the button, click
it, read what happened, and try again. This subject is the discipline of giving
an agent that browser — a real one, driving real pages nobody on the team wrote
— as a **tool it addresses through a thin command surface**, with the agent's
peculiar limitations designed in rather than discovered in production.

Three of those limitations decide everything. The agent has **no eyes**: it
cannot glance at a screenshot and "just see" where the button is, so every
element it acts on must be named in text, and the naming must be reliable
under the page's own change. The agent has **no patience budget of its own**:
a two-second cold start per command is invisible to a human and ruinous to a
loop that issues twenty commands per task. And the agent has **no judgment to
fall back on when a tool fails**: a human reads "timeout" and tries something;
an agent reads "timeout" and, unless the message says what to do, either
repeats the same command or gives up. Every technique in this subject is a
consequence of taking one of those three seriously.

> The browser is the agent's hands. The command surface is the nervous system,
> and it must carry both directions: what to do, and what just happened.

## Why the browser stays alive between commands

The naive design starts a browser per command. It is simple, it needs no state,
and it costs two to five seconds of startup per call plus every cookie, tab and
login the previous call established — over a twenty-command QA run, most of a
minute spent launching and a login lost at every step. Worse than slow, it
cannot be made *stateful*: an agent testing a checkout flow must arrive at step
three still logged in from step one.

So the browser is a **daemon**: one long-lived process per workspace, started
by the first command that needs it, addressed by every later command over a
local socket in the hundred-millisecond range, holding tabs, cookies and
storage across the whole session, and retired by an idle timer nobody has to
remember. Discovery goes through a small state file — the process identity, the
port, a bearer token, the binary version — written atomically with owner-only
permissions so a sibling process on the machine can neither race it nor read
the token.

The daemon inherits every obligation of a spawned child from
[subprocess-lifecycle](../subprocess-lifecycle/subprocess-lifecycle.md) and
adds three of its own, each learned expensively. **Busy is not dead**: a
process that is alive but not answering the health probe is chewing a heavy
page, and killing it loses the session it was built to keep — so the probe is
bounded, the report is "busy" with a non-zero exit, and only an explicit force
from the operator kills a live daemon. **A version mismatch restarts**: a
daemon serving an old binary is a bug class that must not be able to exist, so
the state file records the binary version and the next command compares it.
**A crash means exit, not self-heal**: when the browser process disconnects the
daemon exits, and the next command's ordinary start path is the recovery,
because a half-reconnected browser is worse than a clean restart. The daemon's
state file, port range, liveness rules and bounded event buffers are
[persistent-browser-daemon](./techniques/persistent-browser-daemon.md).

## Naming what the agent cannot see

The agent must name an element to act on it, and the obvious vocabulary is the
one web automation has always used: a selector the agent writes. This fails in
a way that is specific to agents. A human writes a selector after looking at
the markup; an agent writes one after reading a text dump of it, guesses at a
class name that was generated by a build, and either misses or — far worse —
matches the wrong element and clicks it confidently.

The alternative is to make the **runtime** do the naming. A snapshot walks the
page's accessibility tree, assigns each node a short sequential reference, and
stores a locator per reference *outside the page* — role plus accessible name
plus a disambiguating index, held in the daemon's memory. The agent reads the
annotated tree, acts on a reference, and the daemon resolves it to a live
element at action time. The agent never writes a selector, and the page is
never modified to carry the references: injecting attributes into the document
breaks under content security policy, is stripped by framework reconciliation,
and cannot reach inside shadow roots. A locator held outside the document has
none of those problems.

References have a lifetime, and the lifetime is where the design is either
honest or dangerous. **References are cleared on navigation**, because after a
navigation every locator points at a page that no longer exists, and a stale
reference must fail loudly rather than resolve to whatever now occupies that
role and index. Applications rewrite themselves without navigating, so **every
use is preceded by a presence check** that turns a thirty-second action timeout
into a millisecond failure whose message says what the element *was* and what
to run next. And because the accessibility tree is a model of semantics rather
than of clickability, a second namespace collects the elements that are
interactive by styling or handler but absent from the tree. All of this is
[references-over-selectors](./techniques/references-over-selectors.md).

The neighbour here is the mirror image, and the two are easy to confuse.
[agent-addressable-ui](../agent-addressable-ui/agent-addressable-ui.md) is an
application **stamping its own interface** at build time so a person can hand
an agent a source location. This subject reads references **out of a page the
team did not build**, at runtime, from the tree the browser already maintains.
The rule for picking: if you own the build that renders the page, stamp it and
read that subject; if the page is anyone's, snapshot it and read this one.

## Commands carry their effect

Every command the agent can issue is declared, in one registry, as one of three
classes: a **read** (no mutation, safe to retry), a **write** (mutates page
state, not idempotent), or a **meta** operation (the daemon itself — tabs,
status, restart). The classification is not documentation. The daemon
**dispatches by it**, which is what keeps it true: a command added to the wrong
set is routed to the wrong handler and fails in the first test, where a comment
saying "read-only" would have drifted silently for a year. The same registry
generates the help the agent self-discovers from, and the prose that teaches
the agent its commands is validated against the registry in the cheapest test
tier, so a documented flag that does not exist cannot ship. That is
[effect-classed-commands](./techniques/effect-classed-commands.md); the
freshness rule for writes after reads is owned next door by
[write-freshness-gate](../mcp-tools/techniques/write-freshness-gate.md) and is
cited, not restated.

## Errors are the recovery

The last of the three limitations produces the technique most often skipped.
When an action fails, the message that reaches the agent is the entire
recovery: there is no person to read the driver's stack trace and translate it.
So every error is rewritten to carry the next command — a stale reference says
to snapshot again, an ambiguous selector says to use references instead, a
timeout says *which* of navigation or interaction timed out and what that
usually means. Driver internals are stripped. The decision rule is blunt: **an
error the agent cannot act on without a human is a defect in the tool, not in
the agent.** The neighbour,
[user-facing-mapping](../../../backend-platform/resilience/error-handling/techniques/user-facing-mapping.md),
maps failures for a person who has judgment and a support channel; the reader
here has neither, and the standard is correspondingly stricter. The rewriting
door, the shape of an actionable message and what must never be in one are
[agent-actionable-errors](./techniques/agent-actionable-errors.md).

## When the browser must be reached from outside

A daemon bound to the loopback interface is reachable by every process on the
machine and by nothing else, and a bearer token in an owner-only state file is
the whole authorization story. The moment a remote agent must drive the same
browser — through a tunnel — that story collapses, because a single listener
that serves both the local operator's privileged surface (health, token
bootstrap, cookie import, inspectors) and the remote agent's command surface
has exposed the former to whoever reaches the latter.

The wrong fix is to infer "remote" from headers: a forwarded-for address, an
origin. Proxies rewrite those, local proxies add them, and the tunnel provider
changes its behaviour between versions. The right fix is **structural**: bind
a second listener, forward only that one, and give it a locked allowlist of
paths and commands. A tunnel caller cannot reach the cookie surface because
that path does not exist on the socket the tunnel points at. The root token is
refused on the tunnel listener outright; remote agents pair for a scoped token
whose command set is a subset. The liveness endpoint never carries a token in
any mode, and the one endpoint that hands out the root token pins the caller's
identity. Every rejection on the remote surface is logged with its reason,
rate-capped so the log itself is not a denial-of-service target. That is
[socket-scoped-surface](./techniques/socket-scoped-surface.md).

Two boundaries sit close to this one and stay outside it.
[browser-credential-boundary](../../../security/browser-credential-boundary/browser-credential-boundary.md)
is about a web application's shipped bundle holding credentials — a different
force. This subject touches credentials in one place only: importing a person's
cookies into the agent's browser, which must read a copy of the store rather
than the live one, decrypt in memory, cache the key for the daemon's lifetime
and never write a value to any log. And
[prompt-safety](../../prompt-and-context/prompt-safety/prompt-safety.md) owns
what happens when page text reaches the agent: every read command returns
attacker-authored content, and the daemon fences it at the egress door — but
the fence, the nonce and the ladder are that subject's, not this one's.

## Protocol or plain surface

Two realizations of this subject exist and disagree on the transport, and the
subject is honest only if it says what decides. One reaches the browser as a
set of MCP tools — schema-described, tab-addressed, consumed by a host that
already federates tool servers. The other rejects that for the same job and
uses a plain local HTTP surface with plain-text output: a per-call schema
costs tokens on every one of hundreds of calls, a persistent connection is one
more thing to keep alive, and the agent already knows how to run a command.

The discriminator is **who else consumes the surface**. When the browser is one
capability among many that a host discovers, lists and gates uniformly, the
tool protocol earns its overhead and [mcp-tools](../mcp-tools/mcp-tools.md)
owns the design. When the browser is the agent's primary instrument for a
long, chatty loop and the only consumer is a command-running agent on the same
machine, a plain surface with a self-describing help command is cheaper per
call and simpler to keep alive, and the classes, references and errors here
carry over unchanged. Neither answer is wrong; choosing without asking is.

## Where this subject stops

This subject owns the loop between the agent and the browser: the daemon, the
reference vocabulary, the command classes, the error contract, the remote
surface. It owns nothing about the pages the browser loads, the credentials a
web application ships, or how an agent reaches tools in general. A product
built *on* the daemon — a sidebar, an extension, an injection classifier — is
out of scope, and the continuation of the *agent's* session across restarts
belongs to the fleet and orchestration subjects; here the session that
survives is the browser's.

## The techniques

- [persistent-browser-daemon](./techniques/persistent-browser-daemon.md) — one
  browser per workspace behind an atomic owner-only state file; busy is not
  dead, version mismatch restarts, crash means exit; ports below the ephemeral
  pool; bounded event buffers.
- [references-over-selectors](./techniques/references-over-selectors.md) — the
  runtime names elements from the accessibility tree and holds the locators
  outside the page; cleared on navigation, presence-checked before every use,
  a second namespace for the clickable-but-unnamed.
- [socket-scoped-surface](./techniques/socket-scoped-surface.md) — a second
  listener for the remote agent with a locked allowlist; privilege is which
  socket a path exists on, never which header a proxy forwarded.
- [effect-classed-commands](./techniques/effect-classed-commands.md) — read,
  write and meta declared once, dispatched by class, discoverable by the agent,
  and validated against the prose that teaches them.
- [agent-actionable-errors](./techniques/agent-actionable-errors.md) — every
  error that reaches the agent carries the next command; a message the agent
  cannot act on is the tool's defect.
