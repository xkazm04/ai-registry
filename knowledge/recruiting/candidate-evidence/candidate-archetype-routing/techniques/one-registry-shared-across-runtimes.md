# One registry, shared across runtimes

## The concern

The archetype taxonomy is consumed by nearly every component that has an opinion about a
candidate: the intake form that adapts its questions, the parser that produces a first
guess, the scorer that selects a rubric, the fairness gate that decides what may happen
unattended, the recruiter display, the analytics. In any real system these do not share
a runtime — at minimum a candidate- and recruiter-facing layer and an analysis pipeline,
often a batch process and a reporting layer besides.

Each of those places is a natural home for a copy of the archetype list. The moment
there are two copies, there are two definitions of who is protected. They agree the day
they are written. They diverge on some later day, when one is edited and the other is
not — and the divergence produces **no error at all**: no exception, no warning, no
failing test. Just a protected candidate routed as unprotected, and a scorer running the
wrong rubric, indefinitely.

A safety mechanism whose failure mode is silence is not a safety mechanism. The technique
is one declarative artifact, read by every runtime, with no second copy anywhere.

## The procedure

1. **Put the whole taxonomy in one declarative artifact:** the archetype keys, their
   human-readable labels, per-population dimension names and weights, the signal table,
   the confidence tiers, the review threshold, the conservative default, and the
   protected flag.
2. **Make it data, not a shared library.** A library is code; code gets vendored,
   forked, reimplemented in the other language when the dependency is inconvenient. A
   declarative file read at startup by each runtime cannot be partially reimplemented
   without somebody noticing they are typing the values again.
3. **State the reason inside the artifact itself.** A header saying that this file is
   read by every runtime so the fairness gate cannot desynchronize, and that the
   protected flag is compliance-critical, is the cheapest possible defence against the
   next well-meaning refactor. The person about to add a convenience copy is the person
   who needs to read it.
4. **Validate on load, in every runtime.** Weight vectors sum to one; every archetype has
   dimensions; the conservative default names a real archetype; the review threshold sits
   between the tiers. Refuse to start otherwise. The validation is duplicated across
   runtimes deliberately — that is not a second definition, it is a second enforcement of
   the same one.
5. **Derive every protected-cohort set from the flag in the artifact.** No consumer
   declares its own set, in any form. The characteristic bug is a hand-written literal
   added "temporarily" in one runtime and never removed.
6. **Pin the single source with a test that scans the sources**, not only one that checks
   behaviour. A behavioural test passes while a shadow copy agrees; only a scan finds the
   shadow copy before it drifts. Cover every literal form the language allows —
   a class of this bug survives precisely because the scan checked two bracket styles and
   the shadow used a third.
7. **Archive, never delete.** A retired population is marked archived: it disappears from
   every picker so no new candidate can be routed into it, and it stays fully loadable so
   routing, scoring and display keep working for everyone already there.

## Decision rules

- **When a consumer needs the archetype list, it reads the artifact.** Not a constant,
  not an enum mirroring it, not a type generated by hand. If a runtime's type system
  needs a generated type, generate it from the artifact in the build, so it cannot be
  edited independently.
- **When two runtimes cannot literally read the same file, generate both from it in one
  build step and fail the build if either is stale.** The invariant is one editable
  source, not one physical read.
- **When a hand-written copy is discovered, treat it as an incident, not a cleanup.**
  Ask what diverged while it existed and which candidates were affected — a silent
  failure that was live for a month has a population.
- **When a population is retired, archive it and keep loading it.** Deleting a class
  strands the candidates already routed there: their scores stop reproducing, their
  rubric is unresolvable, their record renders as an unknown class. Their process must
  not stop because your taxonomy changed
  ([a candidate's process never stalls on your constraints](../../../_laws.md#a-candidates-process-never-stalls-on-your-constraints)).
- **When a display label changes, the key does not.** Rules, stored classifications and
  historical scores reference the key; labels are presentation. Renaming a key is a
  migration with a data component, never an edit
  ([meaning does not live in a label](../../../_laws.md#meaning-does-not-live-in-a-label)).
- **When an archetype is added, check what silently gets nothing.** Extending the
  taxonomy is advertised as a pure data change, and it mostly is — but any consumer that
  switches per archetype now has a class it does not cover: an intake lane with no
  questions, a rubric with no dimensions, a display with no label. Give every such switch
  a general fallthrough, so the failure of an addition is a generic experience rather
  than an empty one, and pin it with a test that iterates the registry rather than a
  hard-coded list.
- **When an archetype key crosses a boundary, canonicalize it first.** Trim and case-fold
  before keying any lookup, especially a safety predicate. A stray case variant should not
  be able to make a known class look unknown — and the fact that failing closed would
  make that harmless is not a reason to leave it.
- **When the artifact fails validation in production, fail loudly and stop.** A routing
  system running on a configuration it could not validate is making unreviewed decisions
  about people. There is no safe degraded mode for a corrupt taxonomy — but do ensure the
  failure blocks *your* automation, not the candidate's own actions.

## What belongs in the artifact and what does not

**In:** archetype keys and labels; the protected flag; per-population dimension names and
weights; the signal table with its weights; confidence tiers; the review threshold; the
conservative default; archived status.

Labels deserve a note: an archetype usually needs several, for different audiences and
different lengths — a full display name, a compact badge, an internal analysis label, and
a candidate-facing phrasing. Keep them all in the entry rather than deriving them, and
treat the candidate-facing one as **also a switch**: an archetype without it is not
offered as a self-declaration option, which lets the taxonomy carry classes that the
system routes into but does not ask a stranger to identify with.

**Out:** anything environment-specific, anything a workspace configures per tenant, and
anything that is a *decision about what to do* rather than a *definition of the
taxonomy*. Automation thresholds, queue policies and stage rules consume the taxonomy;
they are not part of it. Keeping the artifact to definitions is what lets you say "this
file is compliance-critical" and have it stay true — a file that also holds operational
knobs gets edited weekly and stops being read carefully.

The protected flag is the one entry that deserves an explicit comment saying so, because
it is the field whose silent divergence has the highest cost and the lowest chance of
being noticed.

## When NOT to use it

- **Not for values that legitimately differ per tenant.** If different workspaces need
  different archetypes, the artifact holds the schema and the defaults, and the per-
  tenant overrides live in configuration with the same validation applied. Do not fork
  the artifact per tenant.
- **Not as a place for scoring logic.** The registry declares the weights; it does not
  compute the score. A registry that grows behaviour becomes code again, and a shared
  code artifact across runtimes is exactly the thing you were avoiding.
- **Not where only one runtime exists and no second is plausible.** The single-file
  discipline still helps, but the load-time validation matters more than the sharing. Do
  not build cross-runtime generation for a system that has one runtime.
- **Not as a substitute for a migration plan.** Adding an archetype changes what the
  intake form asks and what rubrics exist; the artifact makes the change atomic across
  runtimes, but it does not tell you what to do with candidates already in flight. That
  is a decision, and it needs an owner.
